# Language server tests

`cargo xtask test -E 'binary_id(cheby_cli::lsp)'` runs `cheby lsp` the way an editor does, over stdio, one process per trial (D-1352). The harness is `tests/lsp_harness/main.rs`, and its client is `cheby_test_support::lsp`.

## Trial groups

The examples group sends only what the server's `capabilities` advertise, so it grows stricter as features land (D-1379). Position requests go to the start of every identifier: hover, definition, declaration, typeDefinition, implementation, references, documentHighlight, codeAction, whose actions that carry `data` are then resolved ("Code actions" below), prepareCallHierarchy, selectionRange, rangeFormatting and prepareRename, then rename where prepareRename accepted, at most 50 renames per example, each a `verify` run in the server (D-1677, D-1725). Beyond that budget the trial keeps every n-th accepted point, the same on every run, and says on standard error how many it dropped. A `RequestFailed` answer of prepareRename or rename is how they refuse a name, so it passes. Any other error answer fails the trial, `InternalError` always. Completion goes to the end of every identifier and after every `.` and `|>`, with the context a typed trigger character sends, and every item of its answer must have an edit on one line that holds the position (D-1394). The first item of each answer is then sent to `completionItem/resolve`, if the server advertises it. Signature help goes inside every argument list: after its `(`, after each of its own commas, and at its `)`. Each of the two has a budget per example, 600 points: beyond it the trial keeps every n-th point, the same on every run, and says on standard error how many it dropped. Each item a prepareCallHierarchy answer holds gets `callHierarchy/incomingCalls` and `callHierarchy/outgoingCalls`. Each file gets the document requests: documentSymbol, formatting, foldingRange, documentLink, codeLens, inlayHint, and `semanticTokens/full` and `semanticTokens/range` over the whole text, as the provider's `full` and `range` say. `workspace/symbol` is asked once with an empty query and once with every distinct name of the example. A `…Provider` the harness does not know fails the trial, so a new capability cannot go unswept.

### The rename sweep

`rename_sweep/*` and `rename_run/*` are the rename sweep of `features.md` §13, cut to what CI can carry (D-1677). Each example gets one trial of each, except as said below.

- `rename_sweep/<name>` asks prepareRename at every identifier, then renames each symbol once to a fresh name of the same case, `renamed_<n>` or `Renamed<n>`, which no identifier of the example uses. A point that an earlier edit covered, or that the references of an earlier refused rename hold, is the same symbol and gets no rename, and an edit whose ranges an earlier one had is not checked again. It sends at most 30 renames, from the accepted points taken by a fixed stride, every `n`th from the first, then every `n`th from the second, and so on, so the renames spread over the example and are the same on every run (D-1716, D-1725). Each edit goes through the applied-edit check of "Edits" below, with rename's narrowing of the fixed point, and is then undone. A fresh name binds nothing, so a refusal fails the trial unless it is `verify`'s E0063 for a satisfier in use (D-1391, D-1671) or, in an example whose `cheby check` fails before any rename (030), a D-1390 gate. A `null` answer where `prepareRename` accepted fails too, and so do a `prepareRename` that accepted no point, as when every request failed, since every example declares `main`, and a sweep that checked no edit. It runs on every platform, since it needs only the server.
- `rename_run/<name>` takes the declarations of safe kinds, those whose new name cannot reach the output: parameters, type parameters, local bindings that are not a module's constants, and private functions other than `main` and the functions an operator or a prelude interface is satisfied by (`features.md` §3.4). The harness cannot reach the checker, so it tells them apart by the semantic token at the name and its `declaration` modifier, and a function by its line, which starts with `fn`. Of these it takes 8 by a fixed stride, renames each in a copy of the example, and runs `cheby check`, which must pass, and `cheby run` with the example's `stdin`, `args` and `env`, which must print its `expected.stdout` and exit with its `expected.exit`. `prepareRename` must accept each, a parameter of a function with no body, such as an `@external` one, included, which renames as its one occurrence (D-1717). A rename refused for an E0063 (D-1391) is skipped and named on standard error. Any other refusal, a `null` rename after an accepted `prepareRename`, and a trial where no picked symbol ran fail. So does a trial that finds no candidate, except in `001_hello_world`, which declares only `fn main`, since no candidate elsewhere means the `declaration` modifier or the legend regressed. It leaves out `034_logging`, which prints the source positions of its log calls, the examples that wait for real time (`timing`), and the `skip-run` examples, such as 030, whose `cheby check` fails before any rename. It is ignored on Windows (D-545, D-641).

### The quality gate

`quality/hover_on_mutants` measures what `facts.md` §0.1 measured in process, through the real server. Its mutants are §0.1's ten body edits: `dot`, `new_dot`, `open_call`, `half_let`, `open_case`, `pipe_end`, `drop_brace`, `typo`, `drop_arg` and `mismatch`. They sit at the sites §0.1's probe chose, found from the syntax tree: a local is a one-segment path whose name a pattern or a local function of the same item binds, since no name is shadowed (D-051). Every site of every example is shuffled with §0.1's seed, and the first 50 of each kind are kept, so the run is deterministic and a drop is a real change. An example whose clean text has an error, such as 030, which needs a dependency, is left out before the sample is drawn, so every kind gets its full 50.

Each example gets one server, which keeps it warm as an editor would. Every source is opened, and the hover at each identifier of an edited item is asked on the clean text. Each mutant is then sent as an edit of its file, and the hovers are asked again at the same identifiers, moved by the edit. Identifiers in the replaced text are skipped. What is graded is every code block of the answer, joined, so an item's instantiated form counts with its header. An answer whose only block is a header, such as a non-generic function's signature, a module's import or a type parameter's bounds, is not graded: it comes from interfaces, and no body edit can change it. `facts.md` §0.1 graded the type from the facts. An identifier whose clean blocks hold a `_` standing alone is not graded either.

- **Same**: the block is unchanged. The floor is 90%.
- **Key probe**: hover on what an editing feature needs at the cursor. For `dot` it is the receiver, for `new_dot` the name just typed, for `pipe_end` the left side's last name or its callee, and for `open_call` the callee. It passes when the answer still shows a type that is not wholly unknown: not `_`, and not the bare name that a local of unknown type shows when its clean block had `: T`. For `open_call` it needs more, as §0.1 asks: the callee's call signature, the instantiated `fn(…) -> …` block of a generic item or the `fn(…)` type of a local, with no parameter whose type is `_` at the head. An open call whose callee shows no call signature on the clean text, such as a non-generic function, has no key probe. A `pipe_end` whose left side ends in no name, such as a literal, has no key probe. The floor is 95%.

The trial prints both numbers and §0.1's table, by kind: mutants, those with a grammar error, graded identifiers, same, partial, other and missing, same before and after the edit, and key probes.

A frame whose body is not a JSON-RPC message ends the server with status 1 and one line on standard error, and the server answers nothing (D-1430). `protocol/malformed_frame_ends_with_1` sends three such bodies after `initialize` and one before it, each to a fresh server, and waits for the end with the input still open.

The outline of `symbols/examples/*` is the parser's item list, since the harness cannot reach the checker's: each item, with a type's variants or fields, a named variant's fields and an interface's functions as children, by name, kind and nesting. Local functions and imports are not part of it. Every `selectionRange` must lie inside its `range`, and every child inside its parent. The request is sent as soon as the document is open, since a text request never waits for analysis (D-1367).

### Waiting for the server

The client waits for a `publishDiagnostics` of one URI and one version. The server sends one for each new version of an open document, and again after `didOpen` and `didClose`, even with an unchanged list. A run that changes neither the version nor the list sends nothing (D-1442). So no trial waits for a publish after `didSave`, a settings change or a sweep. A request does not wait for such a run either, since it waits only for the text it names (D-1367, D-1443). A trial that needs the server to have caught up sends an edit and waits for that version's publish, since a package's jobs run in order.

A trial that needs a save's jobs to have finished, the constants child included, waits for `cheby/idle`: the server sends it for a package when nothing is running or due for it (D-1415). Every client of the harness but `empty` asks for it with `experimental.chebyIdle`. The wait takes the first `cheby/idle` whose `root` is the package's, or the file's in single-file mode, and that comes after the last message the client read. Earlier ones, and every other notification not yet taken, are dropped, since they tell of a state before the edits and saves the client sent. So are the notifications read before it. Its payload must be `root` and a whole `generation`, 0 when the root has had no snapshot since the server started, as for a package whose manifest gives none (D-1492, D-1499), and that generation must be at least the one of every earlier `cheby/idle` of the same session, since it never goes back (D-1495). The server keeps the count of a root for its whole life, also across a session that ends and starts again (D-1499). No golden ends a session, so `single_file_tests.rs` checks that in process.

Parity opens only `src/main.cheby`, waits for its publish and then for `cheby/idle`, so the constants child's diagnostics are in: E0069 from evaluation, E0075 to E0078 and E0081, of the codes of `ui::BACK_END_CODES` (D-1349, D-1589). E0053 is in that list too, but `cheby check` never reports it (D-532). The other files are published as closed files. A diagnostic is compared by severity, code, the first line of its message, file, and start position. The lines after the first carry the rest of `cheby check`'s text (D-1509), which the goldens pin: `diagnostics/mismatched_types_shows_its_label` shows the primary label, and `diagnostics/division_by_zero_note`, which waits for `cheby/idle` and so is ignored on Windows, shows an E0075 from the child with the `note:` that gives the panic's reason. The harness converts the compiler's 1-based code-point columns (D-421) to the protocol's positions itself. A diagnostic with no location, such as E0037, is expected on `cheby.toml` at any position. When a file has a phase-A error, only the files with one and `cheby.toml` are compared, since the other files are checked against last good text (D-1347). Parity leaves out UI tests with `@flags`, run tests, and goldens with an error that has no code. It has no skip list.

## Golden tests

A test is one `.cheby` file, which the harness copies into a package named `lsp_test` as `src/main.cheby`. A test may also be a directory with its own `cheby.toml`, copied as it is. A file with `@package: none` is copied alone, under its own name, into a directory with no `cheby.toml` above it, and the server is started as Zed starts one for a file outside its worktree: rooted at that directory, with no workspace folders. The server then serves it in single-file mode (D-1371), as `single_file/type_error` checks. `single_file/names_no_package` checks that hover, the call hierarchy and `workspace/symbol` name no package for it (D-1477). Its expected answers are in `<name>.expected` beside the file or the directory.

The files here are test input, not examples. They need not be valid Cheby, need not be in `cheby fmt`'s form, and are outside `cargo xtask cross-check`.

### Header

The file, or a package's `src/main.cheby`, starts with `// @key: value` lines:

| Key           | Value                                                                           | Default             |
| ------------- | ------------------------------------------------------------------------------- | ------------------- |
| `@decisions`  | the decisions the test pins, `D-NNN, …`                                         | none                |
| `@milestone`  | the milestone in which the test must pass                                       | `M1`                |
| `@client`     | `empty`, `standard` or `full` capabilities                                      | `standard`          |
| `@encoding`   | the only position encoding the client offers                                    | none                |
| `@settings`   | the `cheby` settings object, as JSON (D-1376)                                   | none                |
| `@requests`   | document requests sent for every source file                                    | none                |
| `@package`    | `none`: the file is opened outside a package; `std-checkout`: in a std checkout | `lsp_test`          |
| `@probes`     | `open`, `disk` or `none`: how a std checkout places its probes                  | none                |
| `@open`       | the documents a std checkout opens, in order                                    | none                |
| `@clientInfo` | the `clientInfo.name` of `initialize`                                           | `cheby-lsp-harness` |
| `@steps`      | what runs after the opens, in order                                             | none                |
| `@rewrite`    | `bom`, `crlf` or both: the form of the copy                                     | none                |
| `@newErrors`  | the error codes an applied edit may add                                         | none                |

The `standard` client announces every capability the server reads but no position encodings, so it runs on UTF-16 (D-1368). It announces `insertTextModeSupport` with `asIs` and `adjustIndentation`, so a completion item whose text spans lines shows `insertTextMode: 2` (D-1506). `full` adds all three encodings and `textDocument.rename.honorsChangeAnnotations`. Both take change annotations, so a rename's note is a `window/showMessage` with `standard` and only an annotation with `full` (D-1391). `@clientInfo: Zed` makes the client name itself as Zed does, for the one answer that depends on the name, `filterText` after `xs.` (`features.md` §4.2). `@settings` is sent as `initializationOptions` and as the answer to `workspace/configuration`.

`@steps` is a list of steps, run after every source file is opened and published, before the markers' requests:

- `idle` waits for `cheby/idle` of the package, as "Waiting for the server" says.
- `started` waits for the `$/progress` begin of a child run, whose token starts with `cheby/child/`.
- `quiet` waits for `cheby/idle` as `idle` does, and fails the trial if a child run began since the last `cheby/idle` the client read.
- `status` prints a block of `cheby/status`: each package it lists, by its `root` as goldens show paths, its `kind` and, where the server sets it, `stdDiffers` (D-1705), and every `window/showMessage` the server has sent since it started. The other fields of `cheby/status` depend on the platform and on timing.
- `published` prints a block of the last published list of every file with a non-empty one at that point, as the `diagnostics` block shows them at the end.
- `settings NAME` pushes the settings object in `NAME.json`, at the package's root, with `workspace/didChangeConfiguration`, and makes it the client's answer to `workspace/configuration`. It waits for nothing.
- `edit DIR` makes each file under the test's `DIR/` the text of the open document at the same path below the package, `DIR/src/other.cheby` for `src/other.cheby`, unsaved, and waits for its publish.
- `save DIR` does what `edit` does, and also writes the file to disk and sends `didSave`.
- `zed-save DIR` does what `save` does, in the order Zed 1.27 sends a save: it writes the file, sends `workspace/didChangeWatchedFiles` for it, then `didSave` 5 ms later and `didSave` again.
- `disk DIR` writes each file under the test's `DIR/` to the same path below the package and tells the server nothing, so a closed file goes stale, or a module file appears that the server has not seen (D-1669).
- `close PATH` closes the open document at `PATH` below the package and waits for its publish as a closed file. Its markers are then not read.
- `execute COMMAND ARG …` sends `workspace/executeCommand` with the arguments as strings and prints its block: the `answer`, the params of each `window/showDocument` the server sent before it, its path shown as goldens show paths, an explanation the server wrote as `<cache>/lsp/explain/<code>.md` or `<tmp>/cheby-explain/<code>.md`, and each `window/showMessage` as `showMessage` lines. A document `cheby.explain` opened must hold the explanation that `cheby explain` prints for its code, which the block does not show (D-1693). So a client with no code actions, such as `@client: empty`, pins the `showMessage` form.
- `explain CODE` sends `cheby/explain` and prints the answer's `code` and `summary`. Its `markdown` must be the explanation `cheby explain CODE` prints, and is not shown, so no golden holds a `docs/diagnostics` text (X §8.3). An error or `null` answer is shown as it is.
- `willRename OLD NEW …` sends `workspace/willRenameFiles` for each pair of paths below the package, of a file or a folder, and prints its block. An edit in the answer is applied and checked with the moves, as "Edits" below says. Then, whatever the answer, the files move on disk, as Zed moves them: each open document below `OLD` is closed and opened again at its new path with its text, from version 0, and each moved module file gets a watched change, deleted at its old path and created at its new one. The step then waits for the server as step 3 of "Edits" does, also after a refusal.

A test with `edit`, `save`, `disk`, `close` or `willRename` is a package or a std checkout's directory, and its markers are read from the text of each document open after the steps, in path order, so the files under `DIR/` hold the markers of the documents they replace, and a moved document's markers are read at its new path. `@rewrite: bom` starts every source file of the copy with a BOM, and `@rewrite: crlf` ends its lines with `\r\n`, which no file here can hold (`.gitattributes`). Files under a `DIR/` take the same form on disk. The documents are opened and edited as Zed holds such files, with no BOM and `\n` line ends, so the open text differs from disk as it does in the editor. `@requests` takes `documentSymbol`, `formatting`, `foldingRange`, `documentLink`, `codeLens`, `semanticTokens` (`full`), `semanticTokensRange` (the whole text) and `inlayHint`.

### Std checkout tests

`@package: std-checkout` runs a test in a std checkout (D-1699). The harness copies this repository's `std/` into a scratch directory, beside an empty `crates/cheby_driver/src/std_lib.rs` and with no `cheby.toml` above it, and starts the server rooted there with the copy as its only workspace folder, as Zed opens the repository. The server checks the copy as package `std` (D-1700) in a session rooted at the copy, so its files show as `std/json/tree.cheby`, with `/` on every platform (D-450, D-1704). The test opens only what `@open` names, in its order, as paths below the copy, real modules and probes alike. The session starts at the first open document (D-1704), and a module not named stays closed.

The copied real modules have no markers, and a committed copy of one with markers would replace the live module and rot with every std change. So a checkout test keeps every marker and edit in probes: modules of its own at `std/probe_<name>.cheby`, which import real modules and are modules of the run. Markers are read from probes only, a step's `DIR/` may hold probes only, and a probe whose path is a module of std is refused. Real modules are only opened, and expected clean. `@probes` says how the probes are placed:

- `open`: never written to disk. Each is opened as an unsaved buffer, which routes (D-1707), so `@open` must name every probe. The disk then matches the binary's std, so D-1705's message is not sent.
- `disk`: written before the server starts, so a probe that `@open` does not name is a closed module. The disk then differs from the binary's module set, so D-1705's message is sent.
- `none`: no probe. The test's one file only carries the header, for a test that opens real modules only.

A one-file test is one probe, `std/probe_<file name>.cheby`, unless `@probes: none`. A test of several probes is a directory with no `cheby.toml` whose `std/` holds them, each placed at the same path, such as `std_checkout/dependent/std/probe_base.cheby`. Its header is in the probe whose path sorts first. Its other entries, such as a step's `DIR/`, are copied beside `std/`, so `edit v2` makes `v2/std/probe_base.cheby` the text of `std/probe_base.cheby`. `@rewrite` is refused, since it would rewrite the copied std.

In the marker blocks of a checkout test, a range in a real module, beside the `uri` or `targetUri` that names it, shows as the text it covers, cut at its first line end with ` …` after it, so a golden does not pin std's line numbers. The goldens under `std_checkout/` pin the merge plan's acceptance, `list_clean` and `json_clean`, and D-1700 to D-1705 and D-1707: a type error typed into an open-only probe that calls `list::map`, a closed probe broken by an edit of the probe it calls, a grammar error with hover still answering, a jump into `std/json/tree.cheby` that stays in the checkout, hover's "Defined in `std::list`" (D-1477), D-1705's message and `stdDiffers` from an on-disk probe, and test bodies checked only while their module is open (D-1701). Its `rename_*` and `move_*` goldens pin D-1706: a package-visible helper renamed across two probes and checked by `verify`, a name that `@std_hooks` gives renamed with its function, a `pub` item and a satisfying function refused, and a move of a file or a folder answered `null` with its warning. Its `fix_*` goldens pin D-1706 for fixes: a raise stops at package-visible, no stub is `pub`, and E0022's help, which writes `pub`, is no fix and keeps its line in the message (`fix_exposed`). `fix_not_a_module` holds a probe whose file name is no module, which gets phase-A diagnostics only and no fix, so its help keeps its line (D-1686). `import_elsewhere` pins E0042's std row read from the checkout's own modules (D-1694, D-1726).

`std_checkout_sweep` opens every module of a copy of `std/` in turn, waits for `cheby/idle`, and expects every module to have been published with an empty list, warnings included, and no `window/showMessage`. It then closes the module. It is stricter than `cargo xtask test-std`, which prints errors only, on purpose: the editor shows warnings. It takes about 40 s on the Apple M3 and prints its time on standard error.

### Markers

A marker is a comment line that points at the nearest line above it that is not a comment:

```cheby
fn main() {
  let total = add(1, 2)
  //          ^ hover
  //      ^~~~~ codeAction quickfix
}
```

- `^ name args` puts the position at the caret's column. `^~~~` makes a range from the caret to the end of the tildes.
- `//> L:C name args` names the compiler's 1-based line and code-point column instead, for a column a caret cannot reach, such as column 1. `//> L:C-L:C name args` names a range, its end exclusive, which may span lines.
- Ordinary comments between a marker and its line are skipped.

The names are `hover`, `definition`, `declaration`, `typeDefinition`, `implementation`, `references`, `documentHighlight`, `completion [LABEL…]`, `apply LABEL`, `signatureHelp`, `inlayHint`, `prepareRename`, `rename NEW_NAME`, `codeAction [KIND]`, `action TITLE`, `noAction TITLE`, `prepareCallHierarchy`, `incomingCalls`, `outgoingCalls`, `workspaceSymbol [QUERY]`, `selectionRange` and `rangeFormatting`. `references noDeclaration` leaves out the declaration. A code action gets the published diagnostics that touch its range. `incomingCalls` and `outgoingCalls` send `prepareCallHierarchy` at the marker, then the follow-up with each item it prepared: the block is a list of one answer per item, or the prepare answer itself when it prepared none. `workspaceSymbol` sends only its words, joined by spaces, as the query; its position means nothing.

### The `.expected` file

The file is a list of blocks. Each block is a line `== <label>` followed by pretty-printed JSON, with keys sorted:

- `== diagnostics`: the last published list of every file with a non-empty one.
- `== <file>:<line>:<col> <name>`: one block per marker, in file and line order. A request that fails shows `{"error": {"code", "message"}}`.
- `== <file> <name>`: one block per `@requests` entry.
- `== willRename OLD NEW …`, `== status`, `== published`, `== execute COMMAND ARG …` and `== explain CODE`: one block per such step, in step order, before the markers' blocks.

A `codeAction` answer shows the text hash in each action's `data` as `<hash>`, since any change of the test's text moves it (D-1683).

`foldingRange` answers are sorted by start, then end, since their order means nothing. Whatever the golden says, a `formatting` answer applied to the file must give `cheby fmt -`'s output byte for byte, `[]` when the file is already in its form, and `null` when `cheby fmt` refuses it. Every edit of a `rangeFormatting` answer must touch the line of its marker (D-1399), except one that only removes and inserts `import` lines: the formatter sorts imports, and the other half of a moved import is kept with the half the range touches.

### Edits

Every edit the goldens apply goes through the applied-edit check (plan §1.7, D-1676): a `rename` marker's answer, a `willRename` step's and an `action` marker's fix.
1. The client waits until the server has caught up with its inputs, so the published lists are those of the text the edit was made for.
2. It applies the edit as Zed does: one `didChange` with the new text for each file the edit names. A file that is not open is opened first, with its disk text, as Zed opens a buffer to edit it. The check opens it before step 1's lists are read, so its form before the edit is known and step 5 asks it as it asks an open file (D-1712). Every `TextDocumentEdit` must name the version of an open document, and `null` for one that was not open (D-1445). A resource operation fails the check, since no edit of rename or a file operation makes one. For a `willRename` step, the files then move, as the step says.

### Text features

The goldens under `format/`, `symbols/` and `folding/` are written by hand from `features.md` §5.1, §5.3 and §5.4. Where that text leaves the rendering open, they take the simplest JSON:

**The request.** `completion` and `apply` send `textDocument/completion` at the marker. When the character before the position is one of the trigger characters the server advertises, the context is `triggerKind` 2 with that character, as typing it would send. Otherwise it is `triggerKind` 1. `signatureHelp` sends no context. `inlayHint` sends the marker's range: a caret with tildes for a range on one line, `//> L:C-L:C` for one across lines, and a caret alone for an empty range. `@requests: inlayHint` asks over the whole file.

**Completion items.** A `CompletionList` and a bare list of items print alike, as `isIncomplete` and `items`. The list's `itemDefaults` are merged into each item first, as a client merges them. Items are in the client's order: by `sortText`, or the label where there is none, and then as the server sent them.

- `completion` with no words prints every item as one line. The parts are joined by ` | `: the label with `labelDetails.detail` after it, the kind's name (`-` for none), then, where present, `detail`, `labelDetails.description` in parentheses, the text the main edit writes in backticks when it differs from the label, `+N edits` for `additionalTextEdits`, and `deprecated`. So `` "length(xs) | Function | pub fn length<T>(xs: List<T>) -> Int | (list) | ` |> list::length`" ``.
- `completion` with words prints `count`, the number of items, and the whole JSON of each item a word names, in the client's order. A word names the items whose label it is, or one item as `label@description`, with `labelDetails.description` after the `@`. A label with a space is written in backticks: `` `let guard` ``. When the server advertises `resolveProvider`, each named item is sent to `completionItem/resolve` and the resolved item is printed. `data` is left out, since it is the server's own. A word that names no item is listed under `absent`, which is how a test says an item must not be offered.
- `apply LABEL` prints the item that `LABEL` names, resolved as above, and `text`: the file after its edits, one string per line. The main edit is the `textEdit`, or for an `InsertReplaceEdit` its `insert` range. A snippet is expanded as a client would expand it: `${1:f}` gives `f`, `${1|a,b|}` gives `a`, `$1` and `$0` give nothing, and `\$`, `\}` and `\\` give the character. Each later line of the main edit's text gets the indentation of the cursor's line, up to the cursor, as `insertTextMode` `adjustIndentation` and Zed do, unless the item says `asIs` (D-1506). Then `additionalTextEdits` apply to the same text. The result must parse with no syntax error, or the trial fails and names the errors. So a test of an item that completes its construct puts one broken construct in its file, and an item that does not complete one is tested with `completion LABEL`. A `LABEL` that names no item, or several, fails the trial. `cheby fmt`'s form is not required (plan W8, S-24).

Whatever the golden says, every item of every completion answer must have an edit on one line that holds the position (D-1394, and the protocol's rule for `textEdit`). For an `InsertReplaceEdit` both ranges must, and `insert` must be a prefix of `replace`. Its `additionalTextEdits` must not overlap the main edit.

**Signature help** prints the answer with each parameter's label as text: a label given as offsets prints as `"[start, end] text"`, the offsets in the negotiated encoding, and a label given as a string prints as it is. Offsets outside the signature's label fail the trial.

**Inlay hints** print as a list of lines, sorted by position: the compiler's 1-based line and code-point column, the kind (`type`, `parameter` or `-`), and the label in backticks. A label of parts prints each part in backticks, joined by `+`, with a part's location after it as `@path:L:C`. Then, where set, `padding-left`, `padding-right`, `tooltip` and each of `textEdits` as `edit L:C-L:C` with its text in backticks. So `` "3:8 type `: List<Int>` edit 3:8-3:8 `: List<Int>`" ``.

`CHEBY_BLESS=1 cargo xtask test -E 'binary_id(cheby_cli::lsp)'` writes the goldens, and so does `cargo xtask bless`. Review a blessed change like code (D-292). A test of a later milestone is never blessed, and trials without a golden are ignored under blessing. A missing golden fails with the whole answer in the message, so it can also be written by hand.

## Milestones and platforms

Protocol trials and golden tests use the header default, M1, so they fail CI from the day they land while `tests/milestone` names a later milestone (D-1352). Example trials use the example's milestone, and a `skip-run` example of a later milestone, such as 030, is tolerated. UI parity trials use the UI test's milestone. The strict runs of D-544 apply:

```sh
CHEBY_PENDING=require cargo xtask test -E 'binary_id(cheby_cli::lsp)'
```

On Windows, until M6, the `parity/examples/*` trials are ignored, since they run `cheby check`, which builds a JIT for a package that passes the front end, and so are the UI parity trials whose golden has no front-end error, as their check tests are (D-545, D-641). The server evaluates no constant there (D-1414), so a golden test whose `@steps` hold `idle`, `started` or `quiet` is ignored too, and so is every `rename_run/*` trial, which runs `cheby check` and `cheby run` (D-1677). A `@package: std-checkout` test is not: a checkout session never starts the constants child (D-1700), so its `cheby/idle` comes on every platform, and it runs there, as `std_checkout_sweep` does. The applied-edit check's own wait for `cheby/idle` is not such a step. The server never runs generated code (D-1349), so every other trial runs there.

Every `cheby` gets the harness's fresh `CHEBY_CACHE` (D-959). `CHEBY_HARNESS_SCALE` multiplies the timeout of each wait (D-722). `cargo xtask coverage` reads the `@decisions` of the tests here.
