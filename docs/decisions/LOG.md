## 2026-09-28: Cheby language foundations

Goal: settle the core design of the Cheby programming language before implementation.

- **D-001 Syntax base**: Core syntax is inspired by Rust. Why: familiar to the target audience and a good fit for expression-oriented code.
- **D-002 Control flow**: No loops and no `if`. Iteration is recursion with TCO, and branching is `case`, as in Gleam. Why: one way to do each thing, and it fits immutable data. → [ADR-0001](../adr/0001-no-loops-no-if.md)
- **D-003 Concurrency model**: Stackful fibers in the style of goroutines. No stackless coroutines, no async/await, no function coloring. Why: any function can block without changing its signature. → [ADR-0002](../adr/0002-stackful-fibers-no-function-coloring.md)
- **D-004 Mutability**: All data is immutable, and persistent data structures share structure. Why: Gleam/Erlang/Clojure-style reasoning, and it is safe to share across fibers. → [ADR-0003](../adr/0003-immutable-data-with-perceus-rc.md)
- **D-005 Memory management**: Perceus-style precise reference counting with reuse, not a tracing GC. Why: deterministic, no GC pauses, and in-place updates for uniquely owned values. → [ADR-0003](../adr/0003-immutable-data-with-perceus-rc.md)
- **D-006 Targets**: Native code via Cranelift, and JavaScript via transpilation. Why: fast native binaries plus browser/Node reach.
- **D-007 Compilation modes**: Both JIT and AOT compilation. Why: JIT for REPL and `run`, AOT for shipped binaries.
- **D-008 REPL**: A good REPL is a first-class goal. Why: fast exploratory workflow.
- **D-009 Project ambition**: Cheby should be usable by others in real projects, so ecosystem, tooling and stability matter. Why: the user's stated goal (not just a hobby or a research vehicle).
- **D-010 Name and implementation language**: The language is called Cheby, and the compiler, runtime and REPL are written in Rust. Why: Cranelift is a Rust library, and one language covers the whole toolchain.
- **D-011 Typing discipline**: Static typing. Top-level functions must have signatures, and types are inferred inside function bodies (Rust-style). Why: good error messages, readable APIs, and each REPL declaration can be checked on its own.
- **D-012 Parallelism**: An M:N fiber scheduler across OS threads from day one. Why: real parallelism is needed for real-world use, and it is costly to retrofit into the runtime and RC design. → [ADR-0004](../adr/0004-mn-parallel-scheduler-from-day-one.md)
- **D-013 Fiber communication**: Typed channels are the primitive, and actors/mailboxes are built as a library on top. Why: matches the Go inspiration, and actors are easy to layer on channels.
- **D-014 Fibers on the JS target**: A whole-program analysis compiles only the functions that can reach a suspension point to generators, and pure code stays plain JS. Why: keeps "no function coloring" for the user without slowing down all JS code. → [ADR-0005](../adr/0005-js-fibers-via-suspension-analysis.md)
- **D-015 Tail-call guarantee**: Every tail call is guaranteed, including mutual and indirect calls. Native uses Cranelift `return_call`. On JS, self-recursion becomes loops and other tail calls use trampolines. Why: recursion is the only looping construct. → [ADR-0006](../adr/0006-guaranteed-general-tail-calls.md)
- **D-016 Side effects**: Effects are untracked, so any function may do IO. Why: an effect system is a large project and brings back a form of coloring.
- **D-017 Mutation escape hatch**: None. State lives in fibers (recursive loops that carry state), and Perceus reuse makes updates to uniquely owned values in-place. Why: stays true to immutability, and it can be revisited if benchmarks demand. → [ADR-0007](../adr/0007-no-mutable-escape-hatch.md)
- **D-018 Error handling**: `Result`/`Option` types with Gleam-style `use` syntax. There is no Rust `?` operator. `panic` kills only the current fiber. Why: the user prefers `use` over `?`, and fiber-scoped panics fit "let it crash". → [ADR-0008](../adr/0008-gleam-use-instead-of-question-mark.md)
- **D-019 Execution architecture**: One mid-level IR feeds the Cranelift JIT (REPL, `run`) and Cranelift object output (AOT). There is no interpreter tier, and the JS emitter branches off the same IR. Why: only one native backend to maintain, and Cranelift compiles fast enough for a REPL. → [ADR-0009](../adr/0009-cranelift-only-no-interpreter.md)
- **D-020 Polymorphism**: Structural interfaces in the style of Go. A type satisfies an interface implicitly by having the required operations, without an `impl Trait for T` declaration. Why: the user prefers Go's implicit satisfaction over Rust traits. → [ADR-0010](../adr/0010-structural-interfaces.md)
- **D-021 Generics compilation**: A uniform boxed representation with small ints tagged unboxed, with monomorphization of hot paths added later as an optimization. Why: fast JIT/REPL compiles, small code, a natural mapping to JS, and a good fit for Perceus. → [ADR-0011](../adr/0011-uniform-representation-for-generics.md)
- **D-022 Data types**: Gleam-style algebraic data types. Every user-defined type is an enum whose variants have record (struct-like) fields, and a struct is just a single-variant type. There is no separate `struct` keyword. `case` matching is exhaustive. Why: one data-definition construct, and exhaustiveness matters because `case` is the only branch. → [ADR-0012](../adr/0012-gleam-style-adts-only.md)
- **D-023 `use` semantics**: General Gleam form. `use x <- f(args)` passes the rest of the block as a callback to any function. Why: one small feature covers `Result`, `Option`, resources and more, and `result.try` becomes a library function.
- ~~**D-024 Numeric types**: `Int` (64-bit) and `Float` (f64) are the defaults, and sized types (`i8`…`u64`, `f32`) exist for FFI and binary data. Why: simple everyday code, precise where it matters.~~ Superseded by D-105.
- **D-025 Integer overflow**: Overflow panics (checked arithmetic), and explicit `wrapping_*` style functions cover intentional wrapping. Why: overflow is almost always a bug, and a panic kills only the current fiber.
- ~~**D-026 Modules**: Each file is a module, nesting follows directories, items are private by default and exported with `pub`, and there are no `mod` declarations. Go-style `internal` directories restrict imports to the parent subtree. Why: the filesystem is the single source of truth, and `internal` lets packages hide implementation modules.~~ Superseded by D-147.
- ~~**D-027 Fiber stacks (native)**: Each fiber gets a large virtual-memory reservation that the OS commits lazily, with a guard page. Stacks are neither copied nor segmented. Why: simplest and fastest on 64-bit, needs no stack maps from Cranelift, and costs only a page or two per idle fiber. → [ADR-0013](../adr/0013-vm-reserved-fiber-stacks.md)~~ Superseded by D-124.
- **D-028 Preemption**: The compiler inserts a cheap yield check at every function entry. Why: without loops every iteration is a call, so this catches every long-running fiber, and CPU-bound fibers must not hog a thread under M:N.
- **D-029 Reference cycles through runtime objects**: v1 accepts leaks from cycles through channels and fibers, documents them, and reports them in debug mode. A cycle collector for runtime objects only may come later without language changes. Why: keeps v1 simple, as Koka does, and Go also leaks blocked goroutines. → [ADR-0014](../adr/0014-accept-rc-cycle-leaks-in-v1.md)
- **D-030 FFI**: Foreign functions are declared per target with Gleam-style attributes, such as `@external(native, "c_symbol")` and `@external(js, "./ffi.mjs", "fn")`. Native uses the C ABI and JS uses ES modules. Why: proven in Gleam, and the target split stays explicit and type-checked.
- **D-031 Toolchain**: One `cheby` binary. `build`, `run`, `repl`, `test`, `fmt`, `lsp` and the package manager are all available from v1. Why: real-world usability needs the whole toolchain at first release.
- ~~**D-032 Where operations live**: There are no methods and no `impl` blocks. Operations are module functions, called qualified (`list.len(xs)`) or with the pipe operator (`xs |> list.len`). A type satisfies an interface through same-named functions in the type's own module. Why: Gleam-style simplicity, with one kind of function. → [ADR-0015](../adr/0015-no-methods-module-functions-and-pipe.md)~~ Superseded by D-061.
- **D-033 Equality, hashing, printing**: `==`, hashing and debug printing are built in and structural for all data types except functions. Why: deep structural equality is natural for immutable data.
- **D-034 Operator overloading**: User types can overload operators via interfaces in v1. Why: the user wants it available from the first release.
- **D-035 Type definitions and visibility**: Types are declared with `type`. Variants can have named or positional fields (`Some(T)`), and records support update syntax (`Point { ..p, x: 1 }`). Types are opaque by default, and a new `exposed` keyword makes constructors usable outside the type's package. Why: hiding representation is the safe default for libraries. → [ADR-0016](../adr/0016-opaque-by-default-exposed-keyword.md)
- **D-036 Closure syntax**: Anonymous functions use the Gleam form `fn(x) { x + 1 }`. Why: the user's preference, and it reuses the `fn` keyword.
- **D-037 `Int` on JS**: `Int` is a JS number, and overflow checks trigger at ±2⁵³, so JS panics earlier than native. Why: both targets panic rather than give wrong results, and JS numeric performance matters. → [ADR-0017](../adr/0017-js-int-as-number.md)
- **D-038 Strings**: `String` is immutable Unicode text with no integer indexing, iterated by grapheme or code point, with explicit byte views. It is UTF-8 on native and a JS string on JS. Why: without O(1) indexing, each target can use its natural representation.
- **D-039 Core collections**: The built-in `List` is a persistent RRB-tree vector, not a linked list. `Map` and `Set` are HAMTs (Clojure-style). Why: indexing, concatenation and slicing are efficient, and all three share structure. → [ADR-0018](../adr/0018-list-is-rrb-tree.md)
- **D-040 Fiber lifetime and panic propagation**: Structured concurrency. Every fiber belongs to a scope (`use s <- fiber.scope()`), the scope waits for its children, and a child's panic cancels its siblings and surfaces as a `Result`. Detached spawn exists explicitly, and Erlang-style links/monitors are a library. Why: scopes prevent most fiber leaks (see D-029) and fit `use`. → [ADR-0019](../adr/0019-structured-concurrency.md)
- **D-041 Waiting on multiple channels**: A library selector combines several receives, each mapped to a common result type (Gleam's `process.selector`). There is no `select` syntax. Why: no new syntax and type-safe with generics.
- **D-042 Blocking IO and FFI (native)**: Networking and timers use a Go-style poller (kqueue/epoll/io_uring). File IO and FFI functions annotated as blocking run on a separate blocking thread pool. Unannotated FFI is assumed fast. Why: Go's proven model, and ordinary C calls stay cheap.
- **D-043 REPL redefinition**: Late binding. Redefining a function updates existing callers through a JIT indirection table, and a signature change re-checks dependents and reports breakage. Old values keep their old type when a type is redefined. Why: matches how people iterate in a REPL.
- **D-044 Package distribution**: Start with decentralized git/URL packages, a lockfile and checksums (Go modules), and add a central registry later. The manifest leaves room for a registry. Why: running a registry is ongoing work that isn't needed to start.
- **D-045 Several types in one module**: A module satisfies a given interface for one type only. To satisfy it for more types, split them into submodules. Why: the simplest rule, and functions stay non-overloaded. → [ADR-0020](../adr/0020-one-interface-implementation-per-module.md)
- **D-046 How interfaces are used**: Interfaces work both as generic bounds (resolved by dictionary passing) and as runtime values that carry their dictionary, which gives dynamic dispatch and mixed-type collections (Go's `io.Reader`). Why: the main strength of Go's model, and cheap with the uniform representation.
- **D-047 Operator overloading rules**: `+ - * /` map to `add`, `sub`, `mul`, `div` in the type's module. `< <= > >=` all come from one `compare` function returning `Order`. `==` stays built-in and structural and cannot be overloaded. There are no implicit Int↔Float conversions. Why: an overloadable `==` could disagree with hashing and break `Map`/`Set` keys.
- **D-048 `exposed` boundary**: The opaque boundary is the package, so other modules in the same package see constructors. Other packages cannot construct, match on or read fields of a non-`exposed` type. Why: readable fields leak the representation as much as constructors do.
- **D-049 Generics syntax**: Angle brackets, `List<T>`, with Rust's turbofish `::<T>` for explicit type arguments in expressions. Why: familiar from Rust, and type arguments are almost always inferred in bodies.
- **D-050 Pipe and function capture**: `x |> f(a)` becomes `f(x, a)`, and Gleam's capture shorthand `f(a, _)` creates a one-argument function. Why: keeps closure noise out of pipelines. The pipe part is superseded by D-244, and the capture shorthand stands.
- **D-051 Statements and shadowing**: Statements are newline-terminated with no semicolons. A `let` may not shadow an earlier binding with the same name. Why: the user's preference, and a name always means one value within its scope. → [ADR-0021](../adr/0021-no-semicolons-no-shadowing.md)
- **D-052 `case` syntax**: Arms use `=>`, guards use the `when` keyword, and `case a, b { ... }` matches several subjects at once. Why: `=>` matches the Rust syntax, and `when` avoids reintroducing `if`.
- **D-053 List patterns**: `[first, ..rest]` and `[.., last]` are patterns on the RRB `List`, and `rest` is an O(1) slice view into the shared tree. Why: keeps recursive list processing linear.
- **D-054 Channels**: Channels are bounded with a capacity, where 0 means a synchronous handoff. They come as separate `Sender<T>`/`Receiver<T>` handles, close automatically when the last sender is dropped, and `receive` returns `Result`. Why: Perceus knows exactly when the last `Sender` goes away, so closing is deterministic with no `close()` call.
- **D-055 Tests**: Built-in `test "name" { ... }` blocks live next to the code, can reach private functions, and are stripped from release builds. Why: tests stay close to what they test.
- **D-056 Target-specific code**: `@target(native)` and `@target(js)` mark functions and modules that exist on one target only, and the type checker flags uses that don't work on every target. Why: real libraries need target-only code, such as file IO.
- **D-057 Metaprogramming**: None in v1. No macros and no derive annotations. Why: macros hurt tooling, the LSP and compile speed, and equality, hashing and printing are already built in. → [ADR-0022](../adr/0022-no-metaprogramming-in-v1.md)
- **D-058 Standard library**: One stdlib bundled with the compiler and versioned with it (Go). Why: fibers, channels and collections are tied to the runtime, and one version means no compatibility matrix.
- **D-059 Naming conventions**: The compiler enforces `snake_case` for values and functions and `PascalCase` for types and constructors. Why: a pattern like `Foo` is always a constructor and `foo` always a binding.
- **D-060 Imports and module paths**: Imports use Rust-style paths with the `import` keyword (`import std::list`, `import std::list::{map}`), since `use` is taken by callback syntax. Module members are accessed with `::` (`list::map`), and `.` is only for record fields. Earlier examples written with `.` for module access (`fiber.scope()`, `result.try`) read as `::`. Why: the user's preference for Rust paths, and `.` then means one thing.
- **D-061 Where operations live**: There are no methods and no `impl` blocks. Operations are module functions, called qualified (`list::len(xs)`) or with the pipe operator (`xs |> list::len`). A type satisfies an interface through same-named functions in the type's own module. Why: Gleam-style simplicity, with one kind of function. Supersedes D-032. → [ADR-0023](../adr/0023-no-methods-module-functions-and-pipe.md)
- **D-062 Reach of the shadowing ban**: The ban applies in nested scopes (closures, `case` arms, `use` callbacks) and to module-level names, such as a local called `list` when `list` is imported. The error suggests a new name. Why: a name means one thing everywhere in a function.
- **D-063 Interface declaration**: `pub interface Show { fn show(Self) -> String }`, where `Self` is the implementing type. Bounds are written `fn f<T: Show>(x: T)`, and the runtime-value form is `dyn Show`. Why: `dyn` marks where dynamic dispatch and boxing happen and can't be confused with bounds.
- **D-064 Conditional conformance**: A generic type satisfies an interface when its module's function has matching bounds, e.g. `List<T>` is `Show` whenever `T` is. Why: generic containers must be printable, comparable and addable.
- **D-065 Unit and Bool**: The unit type and value are `Nil` (Gleam). `Bool` is an ordinary built-in ADT `True | False`, matched with `case`. Tuples are not settled yet. Why: the user's preference, and `Bool` as an ADT fits "case is the only branch".
- **D-066 Labelled arguments**: None in v1. Why: more syntax to design and teach, and they can be added later without breaking code.
- **D-067 String concatenation and interpolation**: Strings concatenate with `+` through `String`'s `add` (D-047), and `"hi {name}"` interpolation requires `Show`. Why: follows from operator overloading, and interpolation is expected in a practical language.
- **D-068 Partial code**: `panic("msg")`, a typed `todo` placeholder that warns at compile time, and a refutable `let assert Some(x) = expr` that panics on mismatch. Why: standard in Gleam, and `let assert` is the concise unwrap without `?`.
- **D-069 Numeric edge cases**: Integer division by zero panics, and `/` on `Int` truncates. Floats follow IEEE, but `==` on `Float` is reflexive (`NaN == NaN`), `-0.0 == 0.0`, and equal floats hash the same. Why: keeps structural `==` and hashing consistent, so NaN keys and records containing NaN work.
- **D-070 `==` on values containing functions**: Panics at runtime, with a compiler warning when the concrete type is known. Why: identity comparison differs between native and JS and breaks hashing, and a compile-time `Eq` bound would bring back ceremony.
- **D-071 Field access on multi-variant types**: `x.name` and record update are allowed only if every variant has that field with the same type. Why: safe without a `case`, and the checker enforces it.
- **D-072 Perceus across threads**: Values are marked "shared" when sent on a channel, captured by a spawned fiber or stored in a global, and only shared values use atomic RC. Borrowing is inferred, with no user annotations. Why: Koka's proven approach, and most values never leave their fiber. → [ADR-0024](../adr/0024-koka-style-shared-marking-for-rc.md)
- **D-073 Program entry and exit**: `pub fn main()` is the root fiber scope, and the program exits when `main` and its scoped children finish. Detached fibers are killed at exit. `main` returns `Nil` or `Result<Nil, E>`, and an `Error` prints and gives a non-zero exit code. Why: follows from structured concurrency (D-040).
- **D-074 Supported platforms**: Native targets are 64-bit macOS, Linux and Windows on x86_64 and aarch64. JS output is ES modules for Node, Deno, Bun and browsers. Debug info is DWARF on native and source maps on JS. Why: VM-reserved stacks rule out 32-bit, and Windows is essential for real-world use.
- **D-075 Stability policy**: Breaking changes are allowed before 1.0. After 1.0 there are no breaking changes, only additions (Go 1 promise), with no editions. Why: editions are expensive to maintain across compiler, LSP and formatter, and `cheby fmt` can handle rare migrations. → [ADR-0025](../adr/0025-go1-style-compatibility-promise.md)

- **D-076 Tuples**: Tuples exist, written `(a, b)`. Unit stays `Nil` (D-065). Why: a `List` holds one element type, so it can't replace heterogeneous groupings.
- **D-077 Panic cleanup (native)**: A panicking fiber unwinds its stack and releases each frame's RC references, using Cranelift `try_call` landing pads and its unwinder. Why: structured concurrency makes recovering from panics routine, and leaking on every panic would hurt long-running servers. → [ADR-0026](../adr/0026-unwind-on-panic.md)
- **D-078 Comments and docs**: `//` line comments, `///` item docs, `//!` module docs, and no block comments. `cheby doc` generates HTML in v1. Why: less for the formatter and LSP to handle, and the tooling ships in v1.
- **D-079 Formatter configuration**: `cheby fmt` has zero options. Why: one style and nothing to argue about.
- **D-080 Unused code**: Unused variables, imports and private functions are warnings, and `--deny-warnings` makes them errors for CI. Why: hard errors get in the way of REPL-driven experimenting.
- **D-081 Type aliases**: `type UserId = Int` is a transparent alias. A distinct type is a single-variant type. Why: easy to tell apart from `type X { ... }`.
- **D-082 Single-variant shorthand**: `type Point { x: Float, y: Float }` declares one variant whose constructor is named after the type. Why: records are the most common type and shouldn't repeat their name.
- **D-083 Function signatures**: Function types are written `fn(Int) -> Int`, and `-> Nil` may be omitted. Why: familiar Rust syntax.
- **D-084 Numeric literals**: Rust-style literals (`1_000`, `0xFF`, `0b1010`, `1.5e3`) take their type from context, default to `Int`/`Float`, and are a compile error when out of range. There are no suffixes. Why: simple syntax, and signatures supply most of the context.
- **D-085 Numeric conversions**: Narrowing conversions return `Result` (`u8::from_int(x)`), widening always succeeds, and `Float -> Int` uses explicit `truncate`/`round`. Why: consistent with checked overflow (D-025).
- **D-086 Interpolating types without `Show`**: `"{x}"` is a compile error unless `x` is `Show`, and `{x:?}` uses built-in debug printing. Why: user-facing text stays deliberate, and debug output is one `:?` away.
- **D-087 Sending on channels**: `send` blocks while the buffer is full and returns `Result` once every `Receiver` is gone. Why: mirrors `receive` (D-054), and Perceus detects dropped receivers exactly.
- **D-088 Linking native binaries**: Start by calling the system linker, and bundle a linker such as lld before 1.0. Why: bundling for three platforms is a big job, but requiring MSVC on Windows is real friction.
- **D-089 License**: MIT/Apache-2.0 dual license for the compiler, runtime and stdlib. Why: the Rust ecosystem norm, covering permissive use and a patent grant.
- **D-090 Constants and compile-time evaluation**: `const` initializers may call ordinary functions, which the JIT runs at build time and whose results are baked into the output. Types are not values and there are no comptime parameters, so D-057 stands. IO and fiber operations fail during compile-time evaluation. Why: most of Zig comptime's practical benefit without a second generics system or the tooling cost D-057 avoids. → [ADR-0027](../adr/0027-compile-time-evaluated-constants.md)
- **D-091 Result and Option constructors**: Rust names, `Ok`/`Err` and `Some`/`None`. Why: consistent with the Rust-inspired syntax.
- **D-092 Built-in operators**: `&&` and `||` short-circuit, `!` is logical not, `%` is remainder with the dividend's sign, and `& | ^ << >>` are bitwise on integer types, with shift overflow panicking. Why: binary and FFI work needs bitwise operators, and short-circuiting matters more without `if`.
- **D-093 Map and Set hashing**: The hash seed is random per process, so iteration order changes between runs, and `==` ignores order. Sorted conversions give deterministic output. Why: HashDoS resistance for servers, and code can't accidentally rely on order.
- **D-094 Deep non-tail recursion on JS**: Accepted limit. Stack overflow panics on both targets, earlier on JS, and all stdlib functions avoid growing the stack. Why: the same trade-off as D-037, and an explicit heap stack would slow everything.
- **D-095 Binary data**: An immutable `Bytes` type with a stdlib builder and parsing functions. Bit-array syntax may come later. Why: bit syntax is a lot of grammar and checking for v1.
- **D-096 Assertions**: An `assert expr` statement usable anywhere, which panics when false and prints both sides of a failing comparison. Why: tests need it, and `let assert` only covers patterns.
- **D-097 Package manifest**: `cheby.toml` holds the package name, semver version and dependencies (git URL plus tag or commit), with a `cheby.lock` beside it. Why: familiar to Rust and Gleam users, and dependency entries can later gain a registry form.
- **D-098 REPL scope**: `cheby repl` accepts expressions, `let`, `fn`, `type`, `interface`, `import` and `const`, loads the project's modules, and has `:type`, `:reload` and `:module path` (entering a module so its private items are visible). Why: entering a module is how people test private helpers.
- **D-099 Build order**: 1) parser, checker, IR, JIT and REPL for the single-fiber core, 2) Perceus and the runtime with the M:N scheduler and channels, 3) AOT output and linking, 4) the JS backend, 5) fmt, LSP, doc and package manager grown alongside, all shipping in v1. Why: the REPL gives the fastest feedback on the design itself, and JS is the least coupled backend.
- **D-100 Channel auto-close on JS**: The JS backend reference-counts channel handles only (`Sender`/`Receiver`), emitting increments and decrements where Perceus would, so channels close as deterministically as on native. Pure data stays GC-managed. Why: the same program must behave the same on both targets. → [ADR-0028](../adr/0028-deterministic-handle-rc-on-all-targets.md)
- **D-101 Resource cleanup**: FFI and runtime handle types (files, sockets, foreign handles) may register a drop function that runs deterministically when the last reference goes away, on JS through the same handle RC as D-100. Explicit scoped closing (`use f <- file::with_open(path)`) is also available. User-defined ADTs get no destructors. Why: deterministic RC is one of Perceus's strongest points, and limiting drops to handle types keeps it simple. → [ADR-0028](../adr/0028-deterministic-handle-rc-on-all-targets.md)
- **D-102 Cancellation semantics**: Cancellation is delivered at the next suspension point or function-entry yield check, and the fiber then unwinds like a panic, releasing references and running handle drops. It cannot be caught or ignored, and cancelled blocking operations never return. Why: reuses the yield-check and unwinding machinery, and a fiber can't refuse cancellation. → [ADR-0029](../adr/0029-uncatchable-cancellation-via-unwinding.md)
- **D-103 Timeouts and deadlines**: The stdlib provides `fiber::timeout(duration, fn() { ... }) -> Result<T, Timeout>` and a timer arm for selectors, built on the poller (D-042) and cancellation (D-102). Why: servers need them, and they need no new language features.

## 2026-09-28: Cheby language specification

Goal: settle the remaining details needed to write the language spec. Continues [Cheby language foundations](#2026-09-28-cheby-language-foundations).

- **D-104 Spec format**: The spec is a set of chapter files under `docs/spec/`, one per area. Why: easier to grow and review chapter by chapter than a single file.
- **D-105 Numeric types and names**: `Int` (64-bit) and `Float` (f64) are the defaults. Sized types for FFI and binary data are named `I8 I16 I32 I64 U8 U16 U32 U64 F32`, and their functions live in lowercase modules (`std::u8`, so `u8::from_int`). Why: keeps D-059 exceptionless, like Gleam's `Int` type beside its `int` module. Supersedes D-024.
- **D-106 `Int` vs `I64`**: `Int` and `I64` are distinct types, and there is no `F64` (`Float` is the only 64-bit float). Sized types behave identically on both targets, so `I64`/`U64` are exact `BigInt`s on JS while `Int` is a JS number (D-037). Why: sized types exist for exact FFI and binary work. → [ADR-0030](../adr/0030-int-distinct-from-i64.md)
- **D-107 Separators and line continuation**: Newlines separate statements and `case` arms. A statement continues inside an unclosed `(` or `[`, after a trailing binary operator, `,`, `=`, `=>` or `<-`, and when the next line starts with `|>`, `&&` or `||`. A leading `-` does not continue. Commas separate arguments, list items, fields and variants, trailing commas are allowed, and `case` arms never end with a comma. Why: multi-line pipelines work, and unary `-` stays unambiguous.
- **D-108 Operator precedence**: Highest first: call/`.field`/`.0`; unary `-` `!`; `* / %`; `+ -`; `<< >>`; `&`; `^`; `|`; `|>`; non-chaining comparisons `== != < <= > >=`; `&&`; `||`. Why: Rust's order with `|>` just above comparisons, so `xs |> list::len == 3` reads naturally.
- **D-109 `case` without a subject**: `case { cond => …, _ => … }` takes `Bool` conditions per arm, like Elixir's `cond`, and requires a final `_` arm. Why: avoids nested `case b { True => … False => case … }` chains while keeping `case` the only branch (D-002). → [ADR-0031](../adr/0031-subjectless-case.md)
- **D-110 Local named functions**: A function body may declare `fn name(…) { … }` that captures locals and may call itself, with inferred types. Only self-recursion is allowed. Why: recursion is the only loop, so loops shouldn't all need top-level helpers.
- **D-111 Import paths**: The first path segment is a package (`std::list`, `my_app::web::router`). There is no `super::` or `self::`, and `as` aliases are allowed. Types and values have separate namespaces, so importing `Point` brings the type and its same-named constructor. Why: aliases are needed because shadowing is banned (D-062).
- **D-112 Prelude**: Only types and constructors are auto-imported: `Int Float String Bool Nil List Result Option Order`, the sized numeric types, `True False Ok Err Some None Less Equal Greater`, and the `Show` interface. No functions. Why: a small prelude avoids name clashes, which matter more without shadowing.
- **D-113 Patterns**: Literals (Int, String, Bool), `_`, bindings, constructors (named with punning and `..`, or positional), tuples, lists, alternatives `A | B`, and `as` bindings. No Float literal patterns, ranges or string-prefix patterns in v1. Field punning also works in construction (`Point { x, y }`). Why: Float patterns clash with reflexive NaN equality (D-069).
- **D-114 String literals**: Escapes are `\n \t \r \\ \" \{ \u{…}`, `{` starts interpolation, strings may span lines, and raw strings `r"…"` have no escapes or interpolation. There is no `Char` type. Why: raw strings cover regexes and other brace-heavy text.
- **D-115 Interpolation contents**: `{…}` holds only a name or field path, optionally with `:?` (`{user.name}`, `{x:?}`). Why: no nested quotes, and a simpler lexer and formatter, as in Rust.
- ~~**D-116 `panic`, `todo` and `Never`**: `panic` and `todo` are keywords with an optional message (`panic("msg")`) and type as anything. `Never` is a writable return type for functions that never return. Why: helpers like `unreachable()` type-check at any use site.~~ Superseded by D-161.
- **D-117 Interface rules**: No default implementations. Bounds combine with `T: Show + Compare`. Interfaces may embed others (`interface Num: Add + Sub + Mul + Div`). `dyn I` is allowed only if `Self` appears solely as the first parameter of each function. Why: `dyn` values can't satisfy a second `Self` parameter or a `Self` return.
- **D-118 Operator signatures**: `add sub mul div` are `(Self, Self) -> Self`, `compare` is `(Self, Self) -> Order`, and unary `-` maps to `neg(Self) -> Self`. `%`, bitwise operators and `!` can't be overloaded. Why: same-type operands avoid multiple dispatch.
- ~~**D-119 Attributes**: A fixed set: `@external(…)`, `@target(…)`, `@blocking` and `@deprecated("msg")`. No user-defined attributes. Why: `@deprecated` is essential under the Go 1 promise (D-075), and D-057 rules out user metaprogramming.~~ Superseded by D-200.
- **D-120 Evaluation order and tail position**: Arguments and operands evaluate left to right. Tail positions are the last expression of a body or block, the arm bodies of a tail `case`, the right operand of `&&`/`||`, and the call a tail `|>` desugars to. Why: `a && recurse(b)` must not grow the stack.
- **D-121 Declaration forms**: `pub fn name<T: Show>(x: T) -> String { … }`, `pub exposed type … { … }`, `pub type Id = Int`, `pub const limit: Int = 100`, `pub interface … { … }`, `test "name" { … }`. `exposed` requires `pub`, and `const` requires a type annotation. Why: consistent with required top-level signatures (D-011).
- **D-122 Spec chapters**: Overview, lexical structure, types, declarations, expressions, patterns, modules and packages, interfaces, memory model, concurrency, errors and panics, targets and FFI, tooling, plus a full-grammar appendix. Chapters use prose, EBNF snippets and examples, and cite decisions as D-NNN. Why: every rule traces back to the log.
- **D-123 Local generalization**: `let`-bound closures and local named functions are monomorphic. Their type is fixed by inference within the body, and only top-level functions can be generic. Why: simple, local type errors (Rust's rule), and generic code already lives at top level with signatures (D-011).
- **D-124 Fiber stacks and overflow detection (native)**: Each fiber stack is a fixed, lazily committed virtual-memory reservation carved out of large shared regions, with no per-fiber guard page. Overflow is detected by a stack-limit check at function entry, merged with the yield check (D-028) into one compare, as in Go. Stacks are neither copied nor segmented. Why: a guard page per fiber costs about two kernel memory mappings, which hits Linux's default `vm.max_map_count` (65,530) at roughly 32k fibers, while the entry check is already there. Supersedes D-027. → [ADR-0032](../adr/0032-shared-region-fiber-stacks-with-entry-limit-check.md)
- **D-125 Default fiber stack size**: 8 MiB of address space per fiber by default, and more for the root fiber running `main` (for example 64 MiB), configurable at build time and per spawn. Physical memory is used only for touched pages. Why: the recursion depth C and Rust programmers expect from a main thread, while still leaving room for millions of fibers in the address space.

- **D-126 Source file extension**: Source files use `.cheby`. Why: unambiguous and easy to search for. Settles OQ-02-1.
- **D-127 Identifier character set**: Identifiers are ASCII only. Why: keeps D-059's case rules unambiguous and avoids confusable identifiers, and it can be relaxed later without breakage. Settles OQ-02-2.

- **D-130 Quotes in raw strings**: Raw strings use Rust-style hash delimiters (`r#"…"#`, `r##"…"##`), ending at `"` followed by the same number of `#`. Why: familiar and nests to any depth. Settles OQ-02-5.

- **D-132 Conversion errors**: Narrowing conversions return `Result<T, Nil>`, and `Float -> Int` rounding functions return `Result<Int, Nil>` with `Err(Nil)` for NaN, infinities and out-of-range values. - **D-136 Built-in `compare`**: `Bool` is comparable (`False < True`), tuples and `List` compare lexicographically when their elements are comparable, and `String` is ordered by Unicode scalar values on both targets. Why: common needs, and scalar-value order is identical on UTF-8 and (with code-point comparison) on JS. Settles OQ-03-6.
- **D-137 Entry points**: Any module's `main` can be run by module path (`cheby run my_app::tools::migrate`), and the root module's `main` is the default. Why: covers tools and scripts without a separate binaries concept. Settles OQ-04-2.
- **D-138 Named-field constructors**: Constructors with named fields are only called with braces, never positionally or as function values. Positional constructors such as `Some` remain usable as functions. Why: field order is never significant, so reordering fields never breaks callers. Settles OQ-04-3.
- **D-139 Constant types**: A constant's value must not contain function values (including top-level function references), channels, fibers or external/handle types in v1. Why: baking them into a binary is impossible or meaningless, and allowing function references later is additive. Settles OQ-04-4.
- **D-140 Test body type**: A `test` body may have type `Nil` or `Result<Nil, E>`, and `Err` fails the test. Why: `use x <- result::try(…)` works directly in tests. Settles OQ-04-5.
- **D-141 Module-level `@target`**: A whole module is marked with the inner attribute `@!target(…)` before its first item. Why: visible in the file itself and mirrors `//!`, with no file-naming conventions. Settles OQ-04-6.
- **D-142 Root module file**: The package's root module, whose path is just the package name, is `src/main.cheby`, and it cannot also be imported as `my_app::main`. Why: the user's preference, since that is where the default `main` lives. Settles OQ-07-1.
- **D-143 Import placement**: All imports come before all items. Why: one place to look, as in Go and Gleam, and simpler formatting and tooling. Settles OQ-07-2.
- **D-144 Item imports don't bind the module**: `import a::b::{x}` binds only the listed items, not `b`. Why: names are bound only when asked for, which matters with the shadowing ban (D-062). Settles OQ-07-3.
- **D-145 Import cycles**: Cyclic imports between modules are a compile error. Why: keeps constant evaluation order, REPL `:reload` and incremental builds simple, as in Go and Gleam. Settles OQ-07-4.
- **D-146 Hiding prelude names**: A local declaration or explicit import may hide a prelude type or constructor in that module, and doing so is a warning. Why: new prelude names must not break code after 1.0 (D-075), while the warning flags the confusion. Settles OQ-07-5.

## 2026-09-29: Language gaps found by the examples

- **D-202 Nested function capture**: A `_` belongs to the innermost call that has it as a whole argument, so `f(a, g(_))` passes the capture `fn(x) { g(x) }` to `f`. Only a `_` that is not a whole call argument, and more than one `_` in one argument list, are errors. ## 2026-09-29: Review fixes

Goal: fix spec bugs found in a review of the draft. Continues [Language gaps found by the examples](#2026-09-29-language-gaps-found-by-the-examples).

- **D-231 Newline continuation is decided by the parser**: The lexer turns every line break outside strings and comments into an `NL`, and the parser decides whether the line continues. It ignores an `NL` inside an unclosed `(`, `[` or type-argument or type-parameter `<`, after a token it has read as a binary operator or after `,`, `=`, `=>`, `->` or `<-`, and before a leading `|>`, `&&` or `||`. A `>` that closes type arguments is not an operator, so `type Cell = Option<Player>` ends its line. The parser always knows which `<` and `>` are brackets, because in expressions type arguments appear only after `::`. Why: the old rule already depended on parsing (binary position, unary `-`), and this is the only variant that ends lines at a closing `>` and also lets type arguments span lines. Tools such as highlighters and the formatter need the parser's view of `<` and `>`. Refines D-107.
- **D-232 Cross-target guarantee covers only timing-independent results**: A program whose result does not depend on timing or scheduling order computes the same result on every target, and every failure that happens only on JS is a panic (`Int` range, recursion depth), never a different value. Timing, scheduling and liveness may differ. On JS a CPU-bound fiber holds the thread until its next real suspension point, so timeouts, timers (including selector timer arms) and cancellation take effect only at that point, other fibers can be starved, and a fiber that never suspends can keep the program from finishing. A program that needs a timeout to bound CPU work on JS must put suspension points in that work, such as a channel operation or a timer. Why: the old wording claimed more than JS can deliver without preemption (D-185), and timeouts already depend on timing on native, so only time-independent results can be promised. Deadline checks at function entry on JS were considered and left for later; adding them would only bring JS closer to native and break no program. Refines D-037, D-094, D-185.
- **D-233 Functions and handles: placeholders in debug output, panics on `==` and hash**: Debug printing works for every value of every type. A function value (top-level function, closure, capture, constructor used as a function) prints as `<fn>`, a `Sender` as `<Sender>`, a `Receiver` as `<Receiver>`, a fiber as `<Fiber>` and a scope as `<Scope>` (names provisional, D-174), and a value of an external type as its unqualified type name in angle brackets, such as `<Db>`. A `dyn I` value prints as the value inside it. Placeholders never show identity, addresses or contents, so `(1, fn(x) { x })` prints `(1, <fn>)`. `==`, `!=` and hashing panic when they reach a function value or a handle (`Sender`, `Receiver`, fiber, scope, external type), so such values cannot be `Map` keys or `Set` elements. D-070's warning also covers types statically known to contain a handle type. `compare` is unchanged: these types have none. Why: one rule for everything that is not data, identity stays unobservable (§9.1), and failure messages from `let assert`, `assert` and `main`'s `Err` can always be printed. Identity comparison of channel handles was rejected because it makes identity observable and could not be undone after 1.0, and a compile error for `{x:?}` on such values because it would break panic messages. Allowing `==` on handles later would break no program. Refines D-033, D-070, D-086, D-134, D-189.
- **D-234 Order of inference: closures last, operators deferred**: Inference stays local to one top-level function. Statements are checked in order, and subexpressions left to right, except that in a call (including the call a `|>` or `use` desugars to, and constructor calls) the arguments that are not closures or function captures are checked first, then the closure and capture arguments, left to right, with parameter types from the callee's signature as instantiated so far. Field access, tuple index and record update need the type known at that point in this order (D-213). Operators whose meaning depends on the operand type (arithmetic, unary `-`, `< <= > >=`, bitwise operators), interface-qualified calls such as `Compare::compare(x, y)` and the `Show` requirement of `{x}` are recorded and resolved at the end of the enclosing top-level function or `test` body, not of a local function's own body, after literal defaulting (D-133). Their result types are known before that: arithmetic, unary `-` and bitwise results have the operand type (D-118), comparisons return `Bool`, and an interface call's type follows from its signature. A type such a constraint needs that is still unknown at the end is a compile error asking for an annotation, as for `let f = fn(a, b) { a + b }` with `f` never called. Evaluation order is unchanged (D-120). Why: the spec's own `go(acc + first, tail)` loops (§1.4, §5.8) and closures such as `list::fold(xs, 0, fn(acc, x) { acc + x.price })` compile without annotations, argument position does not matter for inference, and this follows Rust. Deferral is sound because interfaces have no type parameters and functions are not overloaded (D-045, D-165), so a deferred constraint never changes a result type. Strict left to right (forces data-first argument order) and eager operators (break §1.4 and §5.8, force annotations on local-function parameters) were rejected. Relaxing any of these rules later breaks no program. Refines D-011, D-123, D-133, D-213.
- **D-235 `Never` and `dyn` are one-level conversions at the point of use**: Type inference has no subtyping. The only implicit type changes are two conversions, and both happen only where an expression is checked against an expected type known at that point in the D-234 order, never inside another type. Expected types come from a `let` annotation, a function or closure parameter type from the callee's signature as instantiated so far, a declared function result type and a closure's annotated return type, a constructor's declared field types (with its type parameters as instantiated so far) and record-update fields, list literal elements when the list type is expected, and tuple elements when the tuple type is expected. An expected type passes into the result of a block and into every arm body of a `case`. An expression of type `Never` takes the expected type when there is one and is `Never` otherwise. Arms of type `Never` do not constrain the type of a `case`, and a `case` whose arms are all `Never` is `Never`. A value whose type satisfies `I` converts to `dyn I` only where `dyn I` is expected when the value is checked. A value whose type is still unknown is unified with `dyn I`, so `let shapes: List<dyn Shape> = []` is fine, and a `dyn I` value is not repackaged. `fn(String) -> Never` does not fit `fn(String) -> Int`, `List<Never>` does not fit `List<Int>`, and `List<Circle>`, `fn() -> Circle` or an already-built `Option<Circle>` never become `List<dyn Shape>`, `fn() -> dyn Shape` or `Option<dyn Shape>`. `Some(circle)` checked against `Option<dyn Shape>` works, because the field's expected type is `dyn Shape`. Whole lists are converted with `list::map(circles, fn(c) -> dyn Shape { c })` and functions with a closure such as `fn(s) { unreachable(s) }`. Without an expected type nothing converts, so `let shapes = [circle, square]` is a type mismatch whose diagnostic suggests an annotation such as `List<dyn Shape>`. Why: inference stays free of subtyping and variance, every conversion is visible and O(1), and this follows Rust. A real bottom type with variance for `Never`, and conversion of `dyn` inside other types (hidden O(n) rebuilds, impossible for functions and channels), were considered. Either could be added later without breaking any program. Refines D-161, D-168, with the order of D-234.
- **D-236 `dyn` values carry type descriptors**: Every `dyn` value carries a runtime type descriptor of its underlying value's full type, including all type arguments. Descriptors identify nominal types exactly: same-shaped declarations, or the same name in different modules or packages, differ, aliases have the descriptor of the aliased type, and a type redefined in the REPL gets a new one (D-043). Two `dyn I` values are equal under `==` when their descriptors are equal and their values are structurally equal, and hashing a `dyn` value hashes its descriptor with its value, so `dyn` values can be `Map` keys and `Set` elements. D-233's panics still apply inside. `[]: List<Int>` and `[]: List<String>` as `dyn Show` are not equal. A concrete type's descriptor is supplied statically. For a type parameter `T` of the enclosing top-level function, it comes from one of `T`'s bounds, because every function package passed for a bound carries the descriptor of its type. Converting to `dyn` a value whose type mentions a type parameter without a bound is a compile error that suggests adding one, and an empty interface such as `Any` (D-166) always works. Descriptors of generic types are built at runtime from their arguments' descriptors. Descriptors are observable only through `==` and hashing: no conversion back, downcasting or reflection (D-168), and debug printing is unchanged (D-233). Code without `dyn` conversions or bounds pays nothing, and generic code is still compiled once. Why: keeps the same-type-and-equal-values rule exactly, like Go's interface equality, lets `dyn` values be compared and used as keys, and the bound keeps the cost visible in signatures (D-011) and local. Panicking on `dyn` equality (then `List<dyn Shape>` could never be compared or be a key) and comparing only type names (`[]: List<Int>` would equal `[]: List<String>`, fixed forever after 1.0) were rejected, as were passing descriptors for every type parameter (every generic call pays) and inferring which parameters need one (non-local, and complicates REPL redefinition). Relaxing the bound requirement later breaks no program. Refines D-021, D-033, D-046, D-168, with D-233 and D-235. → [ADR-0040](../adr/0040-dyn-values-carry-type-descriptors.md)
- **D-237 Details of `dyn` type descriptors**: A `dyn` of an empty interface holds any value, except that a type parameter in the value's type needs a bound. Packaging a value as `dyn` is O(1) in the size of the value. Building the descriptor of a generic type such as `List<T>` takes time proportional to the size of the type, and implementations may cache it. A bound on a type parameter, even an empty interface, makes that parameter's type identity observable through `==` and hashing on `dyn` values, and this is intended. Type parameters without bounds stay fully parametric. The check that a value's type satisfies `I`, and the choice of its function package and descriptor, are constraints resolved at the end of the top-level body after numeric literal defaulting, like operators and interface calls, so `let x = 1`, `let d: dyn Show = x` and a later use of `x` as a `U8` package a `U8`. A value whose type is a still-unfixed numeric literal type counts as known to be numeric: it converts to `dyn I` rather than being unified with `dyn I` (an exception to D-235's rule for unknown types), and its concrete type is still fixed later or defaulted. A converted type still not fully known then, as in `let a: dyn Any = []`, is a compile error asking for an annotation. Only numeric literals are defaulted. A constant's value must not contain `dyn` values in v1, and the type checker rejects declared types containing `dyn`. Descriptors, and so `==` and hashing on `dyn` values, are the same on every target: `Int`, `I64`, `F32` and `Float` differ on JS too. The type parameters of a foreign function, including one that has both a body and an `@external` (D-207), must not have bounds in v1. Foreign code cannot build or inspect `dyn` values, which cross the boundary only as opaque values. Why: descriptors are exact only if every type is fully known when one is chosen, a constant cannot bake in a function table, the cross-target guarantee covers `==`, and dictionaries and descriptors have no foreign ABI. Allowing `dyn` in constants or bounds on foreign functions later breaks no program. Refines D-236, D-139, D-186, with D-232 and D-234.
- **D-238 Package identity**: A dependency package is identified by its normalized git URL together with its major version. The same repository written in different ways, such as with or without a trailing `.git` or `/` or with the host name in a different case, is one URL, and different repositories, including forks, are different packages. The package being built is identified by itself, and `std` is the standard library (D-058), not a URL. Different majors of one URL are different packages and can be in one build together under different dependency keys. Within one identity a build contains exactly one version, chosen by minimal version selection (D-192), so requirements within one major never conflict. The version of a dependency is the `version` in its `cheby.toml` at the fetched tag or commit, which is authoritative over the tag. Two required commits of one identity that claim the same version, or a chosen `rev` while another requirement pins a different commit, or a `rev` whose `version` is not in the requested major, are an error reported by `cheby update`. A package imports its own modules by its own manifest `name` (D-111, D-142) and a dependency by the dependency's key in its own manifest. Keys are local to each manifest, must be `LOWER` identifiers, must not be `std` and must differ from the package's own `name`, so a dependency's own `name` need not be unique in a build and renaming is just choosing a key. Types from different identities are different types, even with the same module path and name, and have different descriptors (D-236). Diagnostics mentioning such types should say which package and version they come from. The identity is the opacity boundary (D-048), so two majors of one URL cannot see each other's non-`exposed` constructors and fields. `cheby.lock` records each identity's URL, major, chosen version, exact commit and checksum. Why: there is no registry, so the URL is the only globally unique name, letting a new major sit beside the old one keeps builds resolvable when two dependencies need different majors, and key-based import names avoid Go's `/v2` import paths. URL alone (two dependencies needing different majors of one library could not be built together) and the manifest `name` (unrelated packages that share a name would break each other's builds, and no registry keeps names unique) were rejected. Refines D-044, D-097, D-111, and D-192, whose `package` field it removes.
- **D-239 Major versions below 1.0**: The major version in a package identity (D-238) is the first non-zero part of the version, as in Cargo. `0.1` and `0.2` of one URL are different packages, every `0.0.z` release is a package of its own, and `0.1.3` and `0.1.8` are one package, so version selection picks between them. Why: before 1.0 most libraries are on `0.x`, where minor releases may break compatibility by semver convention, and Go's rule (all `0.x` is one package) would silently give a dependency an incompatible `0.x` and break code nobody changed. Two copies with types that don't mix are reported by D-238's diagnostics instead. Refines D-238. Settles OQ-13-7.

## 2026-09-29: Tuple access

Goal: stop long positional chains such as `x.0.1.0` on nested tuples.

- **D-241 No positional tuple access**: Tuples are read only with tuple patterns, in `let`, `case`, `use` binders and closure or local-function parameters. `x.0` is not an expression and is a compile error that suggests a tuple pattern, and interpolation paths hold only field names (`{pair.0}` is gone). Why: chains of `.N` hide meaning, patterns name each part where it is used, positional variant fields already worked this way, and it removes the lexer ambiguity where `x.0.1` read `0.1` as a float. One-level `.N` and keeping `.N` with a lint were considered. Adding `.N` back later breaks no program. Refines D-076, D-115. → [ADR-0041](../adr/0041-no-positional-tuple-access.md)
- **D-242 Pattern parameters in closures and local functions**: A closure or local-function parameter is an irrefutable pattern with an optional type annotation for the whole pattern, as in `fn(acc, (_, quantity)) { … }`. It behaves like a `let` of the pattern at the start of the body. Refutable patterns are a compile error. Top-level function parameters stay plain names. Why: without `.N` (D-241), callbacks over pairs would otherwise need a `let` in every body, `use` binders already take patterns, and top-level signatures keep parameter names for documentation and hover. Allowing patterns in top-level parameters later breaks no program.
- **D-243 Tuple shape warning**: A written type (in any annotation, signature, alias or field) that contains a tuple with a tuple element, or a tuple with four or more elements, is a warning that suggests a named type. Why: such tuples are where positional meaning gets lost, and a warning steers toward records without banning anything. Refines D-080.

## 2026-09-30: Explicit pipe holes

Goal: make every pipe step show where the piped value goes.

- **D-244 Pipes need an explicit hole**: `x |> rhs` has exactly two forms. If `rhs` is a call with a `_` as a whole argument, `x` fills that `_`, in any position, including the first: `xs |> list::map(_, f)` means `list::map(xs, f)`. Any other `rhs` is an expression of function type that is called with `x` alone: `xs |> list::length` means `list::length(xs)`, so only one-parameter functions are piped bare. A call on the right side without a `_`, such as `xs |> list::take(3)`, is a compile error that suggests adding the `_`. To pipe into a function returned by a call, parenthesize the call: `x |> (make_handler(config))`. A `_` nested in another argument still belongs to that inner call (D-202), so `x |> f(a, g(_))` has no hole and is an error. The capture shorthand `f(a, _)` itself is unchanged (D-050). Why: the reader sees where the value goes at every step without knowing each function's argument order, and one rule covers data-first and data-last functions alike. Implicit first-argument insertion (Gleam, Elixir) was rejected as a hidden second rule. Supersedes the pipe part of D-050 and D-221. → [ADR-0042](../adr/0042-explicit-pipe-holes.md)
- **D-245 No sole-argument capture**: A call whose only argument is `_`, as in `f(_)`, is a compile error everywhere, not only after `|>`. The error suggests writing `f`. Why: `f(_)` means exactly `f`, so there is one way to write it, and in a pipe it keeps `x |> f` as the only form for one-parameter functions. Allowing `f(_)` again later breaks no program. Refines D-202. → [ADR-0042](../adr/0042-explicit-pipe-holes.md)

## 2026-10-02: Compilation speed

Goal: make Go-class compile speed a property of the language and the toolchain, and keep Rust's costs out.

- **D-246 Compile speed as a design principle**: Compile speed is a language design principle (spec §1.1). Its normative core is the locality rule: type-checking a module needs only the interfaces of the modules it depends on, never their function bodies, and every future feature must keep this. Why: the current design already meets it (required signatures, local inference, no macros, no cycles), and writing it down stops a later feature from quietly breaking it. → [ADR-0043](../adr/0043-compile-speed-and-the-locality-rule.md)
- **D-247 Compile-speed budgets**: The reference compiler has two budgets, tracked in CI from the first compiler milestone: a clean debug build checks and generates code for at least 100k lines per second per core and scales with cores, and after editing one function body in a 1M-line project, `cheby run` restarts in under 500 ms. Why: throughput covers CI and clean builds, latency is what developers feel and where Rust hurts most. → [ADR-0043](../adr/0043-compile-speed-and-the-locality-rule.md)
- **D-248 Unit of caching and parallelism**: The module (one file) is the unit of compilation, caching and parallelism, not the package. Why: modules already form an acyclic graph (D-145, D-162), and package units would serialize big packages and rebuild a whole package on any edit. → [ADR-0044](../adr/0044-module-interface-artifacts.md)
- **D-249 Recompilation through interface artifacts**: Each module produces an interface artifact holding its signatures, types, interfaces, constant types and small inlinable bodies. A dependent module is rebuilt only when the hash of an interface it uses changes. Fine-grained query-based incremental compilation (rustc, salsa) is not used for builds, though the language server may use queries internally. Why: Go's export data with early cutoff is simple and predictable, fits D-246, and query systems slow down clean batch builds. → [ADR-0044](../adr/0044-module-interface-artifacts.md)
- **D-250 Borrowing inference stays inside a module**: Borrowing (D-072) is inferred only for calls within one module. Calls across modules use a fixed owned calling convention, as in Perceus. Why: a body edit never changes how other modules call a function, so it never ripples outward, and REPL redefinition (D-043) stays simple. The extra reference-count operations at module boundaries are recovered by release builds (D-251). Refines D-072. → [ADR-0045](../adr/0045-borrowing-inferred-only-within-a-module.md)
- **D-251 Optimization across modules**: Debug builds do no specialization and no inlining across modules. Release builds may specialize generic functions and inline across modules within a size budget, as Go does. Whole-program, LTO-style optimization is not part of the plan. Why: debug builds stay purely local and fast, and release builds get good code without Rust's monomorphization blowup. Refines D-021, replacing ADR-0011's open-ended "monomorphization may be added later". → [ADR-0046](../adr/0046-cross-module-optimization-only-in-release-builds.md)
- **D-252 Implementing equality, hashing and debug printing**: Debug builds implement built-in equality, hashing and debug printing (D-033) with one runtime routine driven by per-type layout tables. Release builds may generate code per type. Why: generating code per type is an implicit `derive` on every type, which debug builds should not pay for.
- **D-253 Unused imports stay warnings**: Unused imports remain warnings (D-080), with `--deny-warnings` for CI, not errors as in Go. Why: the speed gain is one edge in the dependency graph, and errors make REPL and LSP editing more annoying. Confirms D-080.
- **D-254 How `cheby run` meets the latency budget**: `cheby run` loads machine code cached per module for every unchanged module, and JIT-compiles changed modules lazily, each function on its first call, through the indirection table of D-043. Why: cached code makes start-up independent of project size, lazy compilation means an edit costs only the functions that actually run, and the cached code is shared with AOT builds. Needs a small loader of our own, since Cranelift's JIT does not reload compiled code. Refines D-019, D-043. → [ADR-0047](../adr/0047-cached-module-code-and-lazy-jit-for-run.md)
- **D-255 Build cache location**: Build artifacts live in one global cache per machine, shared by all projects and addressed by content hash of their inputs, the compiler version and the flags, like Go's `GOCACHE`. Why: a dependency used by many projects is compiled once per machine, and switching branches hits the cache.
- **D-256 Precompiled standard library**: The toolchain ships `std` precompiled: its interface artifacts, native code for every supported native platform and its JS output. Why: `std` is versioned with the compiler (D-058), so it never needs rebuilding, and first builds stay fast.
- **D-257 Constant values and interfaces**: In debug builds, only a constant's declared type is part of its module's interface, and its value is linked in as data, so changing the value rebuilds only its own module. In release builds, the values of small scalar constants may also be exported, so dependents can fold them. Why: the same split between local debug builds and budgeted release optimization as D-251. Refines D-090.
- **D-258 Where the JS suspension analysis runs**: Each module exports a small summary of which of its functions suspend directly and its call edges. A link-time step computes which functions suspend transitively, and JS code is generated and cached per function, keyed on its IR hash and whether it suspends. Whether a function suspends is not part of the interface artifact. Why: keeps D-249 intact, since a body edit never changes an interface, and an edit regenerates only the functions whose suspension status actually changed. Refines D-014. → [ADR-0048](../adr/0048-js-suspension-analysis-at-link-time.md)
- **D-259 Debug profile backend settings**: The debug profile runs Cranelift with optimization off and emits line-table-only DWARF by default. Full debug info is opt-in. Why: the optimizer and full debug info are the largest backend costs, and line tables still give panic backtraces. Refines D-184.
- **D-260 Interface satisfaction across modules**: When a module needs a fact about a type from a module it does not import, such as whether `geometry::Point` satisfies `Show`, it loads that module's interface directly, and the compiler records it as a hidden dependency for rebuilds. Interface artifacts do not copy facts about other modules' types. Why: every fact has one source, so cache invalidation is exact, and a module is not rebuilt because a module it re-exports types from changed.
- **D-261 Linker for AOT builds**: D-088 stands: call the system linker first, and bundle lld before 1.0. Faster linkers such as mold or wild are not planned. Why: lld covers all three platforms, and `cheby run` skips linking (D-254), so link time is not on the edit-run loop. Confirms D-088.
- **D-262 Where reference counting and cleanup are lowered**: Perceus reference counting and unwind cleanup are inserted and optimized on Cheby's mid-level IR, before Cranelift. Calls in a function share cleanup blocks, one landing pad per set of live values rather than one per call. Why: debug builds run Cranelift without optimization (D-259), so nothing would clean up naive lowering, and the code Cranelift sees could otherwise grow 1.5 to 3 times. Refines D-005, D-077.
- **D-263 Parallelism inside a module**: Type-checking and code generation run per function, in parallel, apart from the per-module steps of D-250 and D-252. Why: inference is local to one body (D-011), and otherwise one large module or a module on the critical path serializes the build.
- **D-264 Deterministic builds**: The toolchain is deterministic: the same inputs, compiler version and flags produce bit-identical artifacts, including interface artifacts and object code, and CI checks this. Why: early cutoff (D-249) and the shared cache (D-255) silently degrade otherwise, and it leaves room for a remote or CI cache later.
- **D-265 Tests outside the artifacts**: Test blocks (D-055) and doc examples (D-197) are not part of a module's interface artifact or its normal cached code. `cheby test` compiles them as separate units per module. Why: nothing depends on tests, so editing one never rebuilds dependents or changes what `cheby run` loads.
- **D-266 Whole-package warnings**: Warnings that need the whole package, such as unused package-visible items (D-152), run in a separate pass after type-checking, in parallel with code generation. They never block `cheby run`, and the pass is skipped when the package's interface hashes are unchanged. Why: keeps the edit-run path purely local.
- **D-267 Release build budget**: A clean release build of a project takes at most three times as long as a clean debug build of the same project, tracked in CI. Why: without a ceiling, the budgeted optimization of D-251 drifts toward Rust's release times. Extends D-247.
- **D-268 Build process model**: Every `cheby` command runs as its own process, with the disk cache (D-255) as the only shared state, and the language server keeps its own state in memory. A persistent build server may be added later only as a pure accelerator: its results must be bit-identical to a fresh process (D-264), and correctness never depends on it. Why: Go meets its speed without a daemon, per-command processes fit the latency budget (D-247) by estimate, and the rule keeps a later server from ever becoming a source of truth or a source of stale-state bugs. → [ADR-0049](../adr/0049-per-command-processes-server-only-as-accelerator.md)
- **D-269 Hash seed for constant evaluation**: During compile-time evaluation of a constant, the hash seed is derived from the constant's identity (package, module path, name) and the content hash of what it depends on, not chosen at random per process. Why: D-264 requires deterministic builds, but a constant that depends on iteration order, such as `map::keys(table)`, would otherwise bake a different value on every compile and poison the shared cache (D-255). Seeding from the inputs keeps builds deterministic, while the order still changes when relevant code changes, so programs cannot come to rely on it. A fixed seed (order stable until a toolchain upgrade silently changes it) and exempting constants from D-264 were rejected. Refines D-093, D-196.

## 2026-10-04: Implementation plan

Goal: settle how the reference implementation is organized and built, as recorded in [`../plan/`](../plan/README.md).

- **D-270 Implementation lives in this repository**: The reference implementation is a Cargo workspace in this repository, next to `docs/`, with crates under `crates/`. Why: spec and code change together in one change, and the examples can serve as conformance tests directly. A separate compiler repository was rejected because spec and code would drift.
- **D-271 Plan layout**: The implementation plan lives in `docs/plan/`, with a README, cross-cutting files and one file per milestone. It covers the whole road to v1, with the first compiler milestone in task-level detail and later milestones refined when they start. Why: early representation and IR choices must account for Perceus, fibers and JS, but detailed tasks for far-off milestones would go stale.
- **D-272 Hand-written parser**: The compiler uses a hand-written lexer and recursive-descent parser over a lossless concrete syntax tree, shared by the compiler, the formatter and the language server. `tree-sitter-cheby` stays the editor grammar, and CI checks that both parsers accept and reject the same files. Why: speed (D-247), diagnostics and error recovery under full control, and one tree for all tools. Reusing the tree-sitter grammar in the compiler was rejected for weaker diagnostics and a C dependency.
- **D-273 Explicit reference counting in MIR from the start**: The MIR has explicit `dup` and `drop` from the first compiler milestone, placed naively but already following the last-use rule (D-205). Perceus in the second milestone only optimizes these instructions, with borrowing (D-250) and reuse. Why: this is the design of D-262 anyway, handle drops and channel closing can be tested early, and adding reference counting later would mean rewriting the lowering. Leaking in the first milestone was rejected for that reason. Refines D-099.
- **D-274 Collection and string kernels in the runtime**: The data-structure and text kernels of `List`, `Map`, `Set`, `String` and `Bytes` are implemented in the runtime, in Rust for native and in hand-written ES modules for JS, and exposed to `std` through `@external`. Combinators such as `map`, `fold` and `filter` are written in Cheby. Kernels are reviewed once Perceus reuse and release-mode specialization are measured, and moved to Cheby where the cost is acceptable. Why: unblocks the examples soonest without depending on optimizer quality, and the API does not change when a kernel moves.
- **D-275 Conformance tests**: Each example in `docs/examples/` gets golden files next to its sources (expected output and exit code, optional input, arguments and environment), and `tests/ui/` holds small files that pin compile-time rules, diagnostics and focused runtime behavior. Why: the examples stay the single source for end-to-end behavior, so documentation and tests cannot drift, and UI tests cover the many rules the examples do not exercise. A separate copy of the examples was rejected because copies drift.
- **D-276 Standard-library spec as a workstream**: The standard-library spec in `docs/stdlib/` (D-204, D-220) is written in tiers, each before the milestone that needs it: core data and text modules before the first compiler milestone, fibers, channels and selectors before the runtime milestone, and IO modules before AOT and JS. Why: the stdlib is the known bottleneck for running the examples (D-204). Refines D-204.
- **D-277 Rust toolchain and CI**: The workspace pins a stable Rust release in `rust-toolchain.toml`, starting at 1.99, uses edition 2024, and bumps the pin deliberately. CI runs on GitHub Actions with the full matrix of D-074, macOS, Linux and Windows on x86_64 and aarch64, on every pull request. Why: a pinned compiler is needed for deterministic builds (D-264), and platform bugs are cheapest to fix in the change that causes them. A two-tier CI with a reduced pull-request matrix and tracking the latest stable without a pin were rejected. Settles OQ-P1.
- **D-278 Tagged integers**: In the uniform representation (D-021), a word with low bit 1 is a 63-bit tagged integer and a word with low bit 0 is a pointer to a heap or static object, as in OCaml, Koka and Lean. An `Int` outside the 63-bit range is boxed when it enters the uniform representation. Monomorphic code keeps `Int`, `Float` and sized numbers unboxed and boxes them only at generic boundaries, and a boxed `Float` is a heap object. Why: pointers are dereferenced directly, reference-count operations skip integers with one bit test, and it is the representation Perceus implementations use. Tagging integers with low bit 0 (V8) and boxing every `Int` in generic code were rejected. Settles part of OQ-P2.
- **D-279 Object header**: Every heap object starts with an 8-byte header: a 32-bit reference count, an 8-bit scan count and a 24-bit layout id. A positive count is local, a negative count is shared and updated atomically (D-072), and one reserved value marks static objects, whose count operations are no-ops (§9.7). The scan count is the number of leading pointer fields that freeing visits, with an escape value for objects that have more than the field allows. The layout id indexes a global layout table that gives the type, constructor tag and field layout, used by `case`, equality, hashing and debug printing (D-252). Why: small allocations, and freeing needs no table lookup. 16M layouts are enough even with REPL redefinitions (D-043). A header with only a 32-bit layout id and a 16-byte header with a layout pointer were rejected. Settles the rest of OQ-P2.
- **D-280 Flat concrete syntax tree**: The parser emits events (start node, token, finish node), and a builder turns them into a flat, arena-allocated lossless syntax tree written for Cheby, not `rowan`. Later phases see the tree only through typed AST views, and the cursors and incremental reparsing the language server needs are part of `cheby_syntax`. Why: parsing must be a small fraction of the 100k lines per second per core budget (D-247), and a flat arena is compact, cache-friendly and easy to keep deterministic. `rowan`, with or without a later swap decided by benchmarks, was rejected. Settles OQ-P3. Refines D-272.
- **D-281 Hash functions**: The hash used by `Map`, `Set` and hashing (D-093) is chosen per target behind one runtime routine that walks layout tables. Native starts with keyed SipHash-1-3. JS uses a keyed 32-bit hash suited to JS numbers, chosen with the JS runtime in M4. The seed is random per process, and derived from the constant's inputs during compile-time evaluation (D-269). Why: hash values are not observable, so each target can use its natural function, and either can be replaced for speed later without changing any program. Settles OQ-P4.
- **D-282 `cheby check`**: A new command, `cheby check`, parses and type-checks the package, including `test` blocks and the cross-target checks of D-056 for the selected or declared targets, reports diagnostics and writes no artifacts other than the build cache. It is a permanent v1 command. Until native AOT output exists, `cheby build --target native` is an error that points to `cheby check` and `cheby run`, and the same holds for `--target js` until the JS backend exists. Why: CI and editors need a fast check that produces no output, like `cargo check`, and adding a command is free before 1.0 (D-075). Making `cheby build` check without output, and an interim `check` removed later, were rejected. Settles OQ-P5. Extends D-031.
- **D-283 Panics in the REPL before unwinding**: Until unwinding exists, each REPL entry runs on its own stack. A panic prints its message, switches back to the REPL's stack and abandons the entry, whose live objects leak, and the session continues. The debug leak counter is not checked in the REPL. Once unwinding lands (D-077), the entry's fiber unwinds instead. Why: the user sees the final behavior of §13.5.4 from the start, and the leak is temporary. Ending the session on a panic and restarting it by replaying earlier inputs were rejected, the latter because it repeats their side effects. Settles OQ-P6.

## 2026-10-04: Standard library, tier 1

Goal: settle the conventions and the tier-1 module APIs of the standard-library spec in [`../stdlib/`](../stdlib/) before M1 (D-276).

- **D-294 Scope of the first standard-library session**: This session specifies tier 1 only, the modules M1 needs, with `std::json` last. Tier 2 is specified in its own session before M2. Why: D-276 writes each tier right before the milestone that needs it, and example 011 moves to the M2 exit list if `std::json` runs late, rather than holding up M1. Refines D-276.
- **D-295 Standard-library spec format**: `docs/stdlib/README.md` holds the conventions shared by every module, and each module file (D-220) documents each function as a Markdown entry: signature, behavior, failure cases, cost, and an example written as a `test` block. Why: easier to review than declarations with doc comments, and the check against `cheby doc` output (D-220) works with either. Writing the files as Cheby declarations with `///` comments was rejected. Refines D-220.
- **D-296 Subject-first argument order**: Every standard-library function takes the value it works on, such as the list, map, string or number, as its first argument. Why: the examples already do this everywhere, and with explicit pipe holes (D-244) one fixed order means nobody has to remember each function's argument positions.
- **D-297 How standard-library functions fail**: A function returns `Option` when the answer may simply be absent (`list::get`, `map::get`), `Result<T, Nil>` when there is only one way to fail (`int::parse`, as in D-132), and `Result<T, E>` with the module's own error type when callers need the reason (`io::Error`, `json::Error`). The standard library panics only where a language rule already does, such as overflow (D-025) or `==` on functions (D-233), never because of a bad argument. Why: the examples already follow this, and failures stay visible in signatures.
- **D-298 Counts and widths out of range**: A count, width or length argument outside its useful range is clamped, so `list::take(xs, -1)` is `[]`, `list::take(xs, 100)` on a shorter list is the whole list, and `string::pad_start(s, -3, " ")` is `s`. A negative count that the compiler can see is a warning. Why: the functions stay total, as in Gleam, and the warning still catches the obvious mistakes. Panicking was rejected because it makes ordinary arithmetic on counts a crash risk. Refines D-297.
- **D-299 Stable sorting**: `list::sort` and every other sorting function in the standard library is stable. Why: the cross-target guarantee (D-232) needs equal elements in the same order on every target, and unstable sorts differ between implementations.
- **D-300 Costs are normative**: The costs a module spec states for collection and text kernels, such as O(log n) for `list::get`, are upper bounds every implementation must meet. Costs of other functions are informative. Why: programs rely on the persistent `List`, `Map` and `Set` (D-039) for fast indexing, update and concatenation, so a slower implementation would break real programs.
- **D-301 `length` and `size`**: Sequences (`List`, `String`, `Bytes`) have `length`, and unordered collections (`Map`, `Set`) have `size`. Why: the examples already use these names, and Gleam makes the same split. One name for both was rejected because it would rename calls in the examples for no gain.

- **D-302 Strings count code points**: `string::length`, `pad_start`, `pad_end` and every other position or count in `std::string` are in code points (Unicode scalar values, §3.5), and `to_code_points` splits a string into one-code-point strings. Grapheme clusters are available only through separate functions, `string::to_graphemes` and `string::grapheme_length`. Why: code-point counts need no tables, are the same on every target and never change with a Unicode version, which fits D-075 and D-232. Counting grapheme clusters by default (Gleam, Swift) was rejected because every program would pay for the tables and its results would change when Unicode is updated. Neither choice gives terminal column width. → [ADR-0050](../adr/0050-strings-count-code-points.md)
- **D-303 Marking count parameters**: A standard-library-only attribute marks the parameters that D-298 clamps, and the compiler warns when the argument written for such a parameter is a negative integer literal. It does not look through constants or other expressions. User code cannot write the attribute, so user attributes stay the fixed set of D-200. Why: the knowledge sits next to the function it describes, and a constant's value is not part of its module's interface (D-257). A list of functions built into the compiler, and no warning at all, were rejected. Refines D-298.
- **D-304 Standard-library error types**: An error type whose cases are fixed by an outside specification, such as `json::Error`, is an `exposed` ADT that callers may match on. An error type whose cases follow the operating system or the host, such as `io::Error`, is opaque: callers inspect it with predicate functions and print it with `show`. Why: after 1.0 a new variant breaks every exhaustive `case` (D-075), and operating systems keep adding kinds of IO error, while JSON's failure cases do not change. Making every error type `exposed` (frozen at 1.0) or every one opaque (example 011 matches `json::Syntax(_)`) was rejected. → [ADR-0051](../adr/0051-exposed-and-opaque-standard-library-errors.md)
- **D-305 Line endings from `io::read_line`**: `io::read_line` returns the line without its ending, removing a final `\n` or `\r\n`. The last line may have no ending, and `Ok(None)` means end of input. Why: input reads the same on every platform, and the examples already parse the returned text directly.
- **D-306 Failing to write to standard output**: When `io::println` or another function that writes to standard output or standard error without returning a `Result` cannot write, for example because the reader of a pipe has gone, the program ends at once with exit code 1 and prints nothing. `io::write_stdout` and `io::write_stderr` return `Result<Nil, io::Error>` for programs that handle the failure themselves. Why: `cheby run | head -1` must neither run forever (ignoring the error) nor print a panic message (panicking, which D-297 rules out for problems in the environment). This is Go's behavior.
- **D-307 One name for text conversion**: A type's text is produced only by its `show` function (§8.8), so `int::show` exists and `int::to_string` does not. `json::to_string` keeps its name, because it encodes a JSON value rather than showing a Cheby value. Why: one way to do each thing, and `show` is the name the `Show` interface needs anyway.
- **D-308 Numeric conversion names**: Every pair of numeric types has a conversion named `target::from_source`, such as `int::from_u32`, `u32::from_u8` and `u8::from_int`. A widening conversion returns the target type, and a narrowing one returns `Result<T, Nil>` (D-132). Why: the names follow one rule and every pair exists, so nobody has to guess which ones do. Refines D-085.
- **D-309 Checked arithmetic returns `Result`**: `int::checked_add`, `checked_sub`, `checked_mul`, `checked_div` and the checked functions of the sized types return `Result<T, Nil>`, and example 015 is updated. Why: overflow is a failure, not an absent answer, so D-297 calls for `Result`, as `float::truncate` already does (D-132). Rust's `Option` was rejected as an exception to D-297.
- **D-310 Case mapping**: `string::lowercase` and `uppercase` apply full Unicode case mapping, including mappings that change the length such as `ß` to `SS`, the same in every locale (no Turkish dotted `i`), from tables shipped with the runtime. The toolchain fixes one Unicode version for all standard-library tables, and updating it is a normal change. Why: users expect `"É"` to become `"é"`, the tables are small, and Unicode's stability policy means an update only adds mappings for new characters. ASCII-only mapping, and the host's mapping (breaks D-232 because JS hosts differ in Unicode version), were rejected. Extends D-302.
- **D-311 Invalid UTF-8 from the operating system**: A function that reads text from the operating system and returns a `Result`, such as `io::read_file` and `io::read_line`, returns an `io::Error` for which `io::is_invalid_data` holds when the bytes are not valid UTF-8. A function that cannot fail, such as `env::args` and `env::get`, replaces each invalid sequence with U+FFFD. `io::read_file_bytes` returns the raw `Bytes`. Why: corrupt input is never silently changed where an error can be reported, and reading arguments stays simple. Always replacing, and always returning an error (`env::args` would return a `Result`), were rejected. Refines D-183, D-304.
- **D-312 Integer parsing**: `int::parse` and the `parse` of each sized integer type accept an optional `-` followed by one or more ASCII decimal digits, and nothing else: no `+`, `_`, whitespace or base prefix. A value out of range is `Err(Nil)`. `int::parse_base(text, base)` reads other bases. Why: a strict format is easy to describe and identical on every target, and the examples already trim input before parsing.
- **D-313 Float parsing**: `float::parse` and `f32::parse` accept an optional `-`, ASCII decimal digits, an optional fraction of `.` followed by digits, and an optional exponent, so `"42"`, `"1e3"` and `"-1.5e-3"` parse, as do the spellings `NaN`, `inf` and `-inf` (D-219). `_`, `.5`, `1.`, a leading `+` and whitespace are rejected. Every text that `show` prints parses back to the same value. Why: numbers read from files and arguments are often written without a fraction. Accepting only Cheby float-literal syntax was rejected. Example 008's comment about adding `.0` is reworded. Refines D-203.
- **D-314 Rounding ties**: `float::round` rounds halfway cases away from zero, so 2.5 becomes 3 and -2.5 becomes -3, on every target. Why: the rule of Rust and C, and the one most users expect. JS's `Math.round` rounds -2.5 to -2, so the JS runtime implements the rule itself. Rounding to even can be added as a separate function later. Refines D-085.
- **D-315 Splitting on an empty separator**: `string::split(s, "")` returns the code points of `s`, the same as `string::to_code_points(s)`. Why: the only useful result, as in Gleam, and consistent with D-302. Returning `[s]` and Rust's `["", "a", "b", ""]` were rejected.
- **D-316 Building `Bytes`**: There is no separate builder type. `bytes::append` and the `bytes::push_*` functions update their first argument in place when it is unique, so a sequence of them runs in amortized O(1) per byte, and copy otherwise, as `List` does. Why: one type and one way to build bytes, and a separate builder would copy just the same when shared. Refines D-095.
- **D-317 `std::result` and `std::option`**: The two modules start from Gleam's: `try`, `map`, `map_error` (for `Result`), `unwrap_or`, `lazy_unwrap_or`, `or`, `flatten`, `is_ok` and `is_error` (`is_some` and `is_none` for `Option`), `all`, `values` and `partition`, with `option::to_result` and `result::to_option`. There are no functions that panic, such as Rust's `unwrap` and `expect`. Why: covers every call in the examples, and `let assert` (D-068, D-159) already unwraps with a message.
- **D-318 Negative list indexes**: `list::get(xs, i)` returns `None` for every `i` outside `0` to `length - 1`, including negative ones, and the other index functions of `std::list` treat them the same way. Indexes are not counts, so D-298's clamping does not apply. Why: counting from the end hides off-by-one bugs, and `[.., last]` patterns already reach the end of a list.
- **D-319 `list::range`**: `list::range(start, end)` returns the integers from `start` up to but not including `end`, and `[]` when `end <= start`. Why: `range(0, n)` has `n` elements and matches the indexes of an `n`-element list, as Rust's `start..end` does. Including `end`, and leaving ranges to user code, were rejected.
- **D-320 JSON decoding API**: `std::json` decodes with decoder values of type `json::decode::Decoder<T>`, built from primitive decoders such as `decode::string()`, `decode::int()` and `decode::list(d)`, and combined with `use` through `decode::field`, `optional_field`, `then`, `success` and `failure`, as in Gleam's `gleam/dynamic/decode`. `json::parse(text, decoder)` parses and decodes in one step, and the interface `json::ToJson` lets `json::list` encode any list whose elements satisfy it. Why: it works with `use`, needs no return-only `Self` (D-209), and examples 011 and 030 are written against it. Refines D-210.
- **D-321 `json::Value` is an exposed ADT**: `json::Value` is an `exposed` type with the variants `Null`, `Bool`, `Int`, `Float`, `String`, `Array` (a list of values) and `Object` (a list of key and value pairs in written order, D-218). Values are built with these constructors, so there are no builder functions such as `json::int` or `json::object`. `json::array(items, encode)`, `json::nullable(option, encode)` and `json::list(items)` stay as helpers that apply an encoding function. An `Int` outside the JS safe-integer range is written as is and reads back as a `Float` (D-222). Why: JSON's shapes are fixed by its specification, so D-304 allows an exposed type, and generic tools such as pretty printers, diffs and path lookups can walk any document with `case`. Keeping the type opaque, as example 011 assumed, was rejected. Refines D-210, D-217, D-218. → [ADR-0052](../adr/0052-json-value-is-an-exposed-adt.md)
- **D-322 Decoding reports every error**: A failing decoder records its error and decoding continues with a placeholder value, which is why `decode::failure` takes one. `json::Decode` holds every value that did not fit, in the order the decoder visited them. Why: an HTTP API reports every bad field in one response (example 030), as Gleam's decoders allow. Stopping at the first error was rejected.
- **D-323 Kind names in decode errors**: The `found` field of `decode::Error` names the JSON kind as `Null`, `Bool`, `Int`, `Float`, `String`, `Array` or `Object`, and the primitive decoders use the same names in `expected`. A missing field gives `expected: "Field"` and `found: "Nothing"`, with a path that ends at the field's name. Fields a decoder does not ask for are ignored. Why: the names match the variants of `json::Value` (D-321), and `Array` makes clear the value is JSON's array rather than a Cheby `List`. Example 011's `"List"` becomes `"Array"`.
- **D-324 Position of JSON syntax errors**: `json::Syntax` carries a `json::Position` with a line and a column, both starting at 1. A line ends at `\n`, so `\r\n` also ends one line, and the column counts code points (D-302). Why: users read errors as line and column, and the type is frozen at 1.0 (D-304), so it should hold what people need. A single offset, as example 011 assumed, was rejected.
- **D-325 Non-finite floats in JSON**: `json::to_string` writes a `NaN` or infinite `Float` as `null`, so encoding never fails. Finite floats are written as `show` prints them (D-203), so `2.0` keeps its `.0` and reads back as a `Float` (D-217). Why: this matches `JSON.stringify` on the JS host, and a `Result` on every encode would burden every caller.
- **D-326 JSON parsing and escaping**: An unpaired surrogate escape such as `\ud800` is a syntax error on every target, although JS's `JSON.parse` accepts it, because a `String` holds only scalar values (§3.5). Nesting depth is limited only by memory, because the parser keeps its stack on the heap (D-094). Encoding escapes only `"`, `\` and control characters and writes all other text unchanged. Why: the same document gives the same result on every target (D-232), and minimal escaping keeps output readable.
- **D-327 Pretty-printed JSON**: `json::to_pretty_string` writes a value with two-space indentation and `": "` after keys. Why: it is the most common need after compact output, and users would otherwise each write their own. Example 008 keeps its own printer, because the printer is part of what it shows (D-230).
- **D-328 Writing files in tier 1**: Tier-1 `std::io` has `write_file` and `write_file_bytes`, which replace a file's contents and return `Result<Nil, io::Error>`. File handles and `file::with_open` (D-101) stay in tier 3. Why: reading without writing would be an odd gap, and both are single kernels.
- **D-329 Duplicate keys in `map::from_list`**: When the list repeats a key, the last value wins, as if each pair were inserted in turn. Why: it matches `map::insert` and JSON's rule for duplicate keys (D-223).
- **D-330 More kinds of map**: Besides `Map` and `Set`, the standard library has a multimap, an ordered map and an ordered multimap. Why: they are common needs that users would otherwise build on `Map` themselves, and an ordered map iterates in a deterministic order, which `Map` cannot (D-093). What "ordered" means, the representation, the names and the tier are settled separately. Extends D-039.
- **D-331 Sorted and insertion-ordered maps**: "Ordered" covers two kinds of map, each in its own module. A sorted map iterates in key order by `compare`, so its keys must satisfy `Compare`, and it is a persistent balanced tree with O(log n) lookup and update. An insertion-ordered map iterates in the order keys were first inserted, accepts any key type, and is hashed like `Map`. Why: sorted order gives output that depends only on the contents, plus range and minimum and maximum queries, while insertion order preserves the order of the input, and Java ships both (`TreeMap`, `LinkedHashMap`). Choosing only one of them was rejected. Refines D-330.
- **D-332 Multimap values**: A multimap holds a `List<V>` under each key, in insertion order, with duplicates kept, so inserting `("a", 1)` twice gives `[1, 1]`. Why: a `Set` of values would bring `Set`'s random iteration order (D-093) into every lookup, and a caller who wants no duplicates can check before inserting. Guava's `SetMultimap` form was rejected. Refines D-330.
- **D-333 Sorted set**: The standard library has a sorted set, the sorted map's tree without values, whose elements must satisfy `Compare`. Why: it is the deterministic counterpart of `Set`, as the sorted map is of `Map`. Refines D-331.
- **D-334 Binary reads and writes on `Bytes`**: `std::bytes` has `get(b, i) -> Option<U8>`, `slice(b, start, end)` clamped like D-298, and fixed-order integer reads such as `read_u16_be`, `read_u32_le`, `read_u64_be` and their signed versions, each taking an offset and returning `None` past the end, with matching `push_*` functions that append them. Why: binary formats are why `Bytes` exists, and naming the byte order at every call keeps the format visible. Refines D-095, D-316.
- **D-335 `list::sort` and `list::sort_with`**: `list::sort(xs)` sorts a list whose element type satisfies `Compare`, and `list::sort_with(xs, compare)` takes a comparison function. Both are stable (D-299). There is no `sort_by_key`. The examples' comparator calls become `sort_with`, and those that pass `int::compare` or `string::compare` become plain `sort`. Why: the most common sort, of numbers or strings, needs no comparator, as in Rust and Gleam's `list.sort` with `int.compare` made implicit. Keeping a single comparator-taking `sort` was rejected. Refines D-299.
- **D-336 Sorted collections are written in Cheby first**: The sorted map and set are persistent balanced trees written in Cheby, in tier 1, with no runtime kernel. A benchmark compares them with a Rust tree in M2 and again in M6, and they move to runtime kernels if they are slower by more than an agreed factor, possibly only for keys whose `compare` is built in. Why: for user-defined keys every comparison is a call into Cheby either way, a kernel that calls back into Cheby would need panics and cancellation to unwind through Rust frames and a generator version on JS (D-014), and Koka's functional red-black tree runs at about the speed of C++ `std::map` once Perceus reuse applies. Kernels from the start (tier 2) and a permanent split by key type were rejected for now. The API does not change if a tree moves. Refines D-274, D-331.
- **D-337 Names of the extra collections**: The modules are `std::sorted_map` and `std::sorted_set` for key order, and `std::ordered_map` and `std::ordered_set` for insertion order. Why: next to `sorted_`, "ordered" can only mean the other order, as in Python's `OrderedDict`. `indexed_` (which promises access by position) and `linked_` (which names a representation) were rejected. Refines D-331.
- **D-338 Three multimaps**: `std::multimap` (hashed), `std::sorted_multimap` and `std::ordered_multimap` each wrap their map with `List<V>` values (D-332). Why: each is a thin wrapper, so the cost is mostly spec text, and every map kind gets the same counterpart. Refines D-330.
- **D-339 Insertion-ordered set**: `std::ordered_set` is `ordered_map` without values. Why: it mirrors D-333. Refines D-331.
- **D-340 Order after updates in insertion-ordered collections**: Inserting a key that is already present keeps its position and replaces its value, and removing a key and inserting it again moves it to the end. Why: this is how JS `Map` and Python's `dict` behave, so users expect it. Refines D-331.
- **D-341 Equal keys in sorted collections**: Sorted collections treat two keys as the same when `compare` returns `Equal`. Inserting such a key keeps the stored key and replaces only the value. Why: Rust's `BTreeMap` does the same, and a `compare` that disagrees with `==` is already a program bug (§8.7), so the choice only affects buggy code. Refines D-331.
- **D-342 Equality, hashing and debug printing hooks for standard-library types**: A standard-library-only attribute lets a type name Cheby functions that implement its `==`, hashing and debug printing, and the runtime routine of D-252 calls them instead of walking the representation. User code cannot write the attribute, so D-047 stands for user types. The named functions must not suspend. A panic inside them, such as `==` reaching a function value (D-233), unwinds through the runtime routine like any other panic. Why: collections written in Cheby (D-336) have several internal shapes for the same contents, and must compare, hash and print like `Map`, by contents. Representations with only one shape per content (O(n) removal from `ordered_map`, internal nodes still printed) and runtime kernels (superseding D-336) were rejected. Refines D-252, D-336.
- **D-343 Equality of insertion-ordered collections**: Two `ordered_map`, `ordered_set` or `ordered_multimap` values are `==` only when they hold the same entries in the same order, and their hash covers the order. Sorted collections compare by contents, which also fixes their order. Why: insertion order is observable, so values that are `==` should behave the same everywhere, as with Python's `OrderedDict`. Refines D-342.
- **D-344 Printing hashed collections**: Debug printing of `Map`, `Set` and `multimap` lists their entries sorted by each entry's printed text, so the output is the same on every run. These types do not satisfy `Show`, so a program chooses an order itself, for example with `map::to_sorted_list`. The sorted and insertion-ordered collections satisfy `Show` when their elements do, and print in their own order. Why: goldens and test failure messages must not change between runs despite D-093, and sorting costs O(n log n) only when printing. Refines D-093, D-134.
- **D-345 Text of `io::Error`**: `io::Error`'s `show` prints a fixed message for each kind the standard library knows, such as `not found`, `permission denied` or `invalid UTF-8`, and the operating system's own message only for other kinds. Debug printing uses the same text, not the internal fields. The examples print IO errors with `{reason}`. Why: example output must be the same on every platform, which operating-system messages and fields are not. Refines D-134, D-304.
- **D-346 Buffering of standard output**: Standard output is line-buffered, and is also flushed before the program reads standard input, so a prompt written with `io::print` appears in time. All buffered output is flushed when the program ends, including with exit code 1 or 101. Standard error is not buffered. Why: large outputs stay fast, prompts still appear, and no output is lost when a program fails. D-306 still applies when a flush cannot write.
- **D-347 `std::env` details**: `env::args()` excludes the program name, and `env::program_name()` returns it. `env::get(name)` returns `Option<String>`, with `Some("")` for a variable that is set but empty. Why: every example already assumes the first, and an empty variable is not an absent one. Refines D-183.
- **D-348 Drafting the tier-1 modules**: The full function list of each tier-1 module is drafted from the conventions of this session (D-294 to D-347) and the examples' calls, and reviewed by the user in `docs/stdlib/`. New decisions are logged only where a draft meets a trade-off these entries do not settle. Why: the remaining functions follow from the conventions, so more rounds would confirm recommendations one function at a time.
- **D-349 Signatures in the standard-library spec**: Each entry starts with its signature as a declaration without a body in a `cheby` code block, such as `pub fn get<T>(xs: List<T>, index: Int) -> Option<T>`. Why: it is the form `cheby doc` prints, so the check of D-220 compares like with like. Bodies written as `{ … }`, and signatures in the heading, were rejected. Refines D-295.
- **D-350 Sized numeric modules share one definition**: The standard-library README defines each family of numeric functions once (conversions, `checked_*`, `wrapping_*`, `parse`, `show`, `compare` and the others), and the files for `std::i8` to `std::u64` and `std::f32` give their type's range and a table of their functions with one example per family. `int.md` and `float.md` are written in full. Why: the nine modules differ only in range, so one definition leaves one place to review and fix. Nine full files were rejected. Refines D-295, D-308.
- **D-351 Files for submodules**: A submodule's file sits in a directory named after its parent, following the import path, so `std::json::decode` is `docs/stdlib/json/decode.md` next to `json.md`. Why: D-220 matches files to imports, and later tiers may add more submodules. A flat `json-decode.md` was rejected. Refines D-220.
- **D-352 Gaps in standard-library drafts**: A gap found while drafting is marked in the module file as `> **Open (OQ-<module>-<n>):** … _Proposed:_ …`, the draft is written as if the proposal were accepted, and the markers are settled together in a review round. Why: it is the spec's convention, the drafts read complete, and the user reviews every gap at once. Stopping to ask at each gap was rejected. Refines D-348.
- **D-353 Modules of `Bool`, `Nil` and `Order`**: `std::bool` declares `Bool` with `compare` and `show`, `std::nil` declares `Nil` with `show`, and `std::order` declares `Order` with `reverse`, `then`, `compare` and `show`. Why: every built-in type is declared in its standard-library module (§8.2), `Bool` and `Nil` satisfy `Show` (§8.8), and `order::reverse` and `order::then` keep descending and multi-key sorts short. A built-in `Show` rule like the one for tuples was rejected. Settles OQ-readme-1.
- **D-354 Order of callback calls**: A standard-library function that visits elements calls its callback exactly once per element, front to back in the collection's order, unless its entry says it stops early, as `any`, `all` and `find` do. A function that calls a comparison function, such as `list::sort_with`, uses one algorithm fixed by the toolchain on every target, and the number of its calls is not specified. Hashed collections visit entries in their per-process order (D-093). Why: a callback can print or panic, so the order is observable, and D-232 requires the same result on every target. Leaving the order unspecified was rejected. Settles OQ-readme-2.
- **D-355 `show` text of containers**: `show` of `List`, `Option`, `Result`, tuples and the sorted and insertion-ordered collections uses the punctuation of debug printing (D-134) with each element written by its own `show`, so `["a", "b"]` shows as `[a, b]` and `Err("not found")` as `Err(not found)`. Why: `show` is user-facing text, so interpolating an error should not print quotes, and `{x:?}` still gives the exact form. Showing the debug text unchanged was rejected. Settles OQ-readme-3. Refines D-064.
- **D-356 Checked division by zero**: `checked_div` and `checked_rem` return `Err(Nil)` for a zero divisor as well as for overflow, so no `checked_*` function panics. Why: as in Rust, a checked function is the one to call when no panic is wanted. Settles OQ-readme-5. Refines D-309.
- **D-357 `Int` results on JS**: A standard-library function that returns `Result<Int, Nil>`, such as `checked_add`, `parse`, `from_i64` or `float::truncate`, returns `Err(Nil)` only for a value outside the 64-bit range, on every target. A value inside that range but outside ±(2⁵³−1) panics on JS like any other `Int` result (D-037). Why: each function returns the same value wherever it returns (D-232), and native keeps all of `Int`'s range. `Err` outside the safe range on every target (native loses most of its range) and on JS only (a different value per target) were rejected. Settles OQ-readme-6 and OQ-int-3. Refines D-037, D-309.
- **D-358 `int::min_value` and `int::max_value` are native-only**: Both constants are declared `@target(native)`, so code that uses them is restricted to native and the compiler checks it (D-056). `int::min_safe` and `int::max_safe`, ±(2⁵³−1), are the portable limits. Why: an `Int` literal outside the safe range is a compile error on JS (§3.3.4), and native code still needs to name the full range. Dropping the constants was rejected. Settles OQ-readme-7.
- **D-359 Inexact numeric conversions**: A conversion from an integer type to a float type, and `f32::from_float`, returns the target type rounded to nearest with ties to even, and `f32::from_float` gives an infinity beyond `F32`'s range. Integer modules have no conversion from a float type. A float becomes an integer through `truncate`, `round`, `floor` or `ceil`, which return `Result<Int, Nil>` (D-132), followed by a narrowing conversion if needed. Why: Rust and JS convert this way, and a `Result` on every inexact conversion would burden nearly every integer-to-float conversion. Settles OQ-readme-4. Refines D-085, D-308.
- **D-360 Standard-library kernels in constants**: Compile-time evaluation runs the effect-free kernels of `std::list`, `std::map`, `std::set`, `std::string` and `std::bytes`, as an exception to the rule that reaching an `@external` function while computing a constant is a compile error. Why: D-196 already allows `Map` and `Set` in constants, lookup tables are a main use of constants, and the kernels give the same value on every target. Forbidding them would change examples 006 and 030. Settles OQ-list-1. Refines D-090, D-274.
- **D-361 Decoders do not name `json::Value`**: `json::Value` stays in `std::json`, which imports `std::json::decode`. Decoders run over a raw tree in an internal standard-library module that both import, and `json::decode_value(value, decoder)` decodes an already-built `Value` in O(n). No decoder can return part of a document as a raw `Value`. Why: `json::Error` holds `decode::Error` and `json::parse` takes a `Decoder`, so `decode` cannot import `json` (D-145), and this keeps every name of D-320, D-321 and the examples. Moving the decoders into `std::json` was rejected because it renames the API and rewrites examples 011 and 030. Settles OQ-json-5. Refines D-320, D-321. → [ADR-0053](../adr/0053-json-decoders-do-not-name-json-value.md)
- **D-362 `json::Value` does not satisfy `Show`**: Only `json::Error` satisfies `Show` in `std::json`. A program prints a `Value` with `json::to_string` or `{v:?}`. Why: a module satisfies `Show` for one type only (D-045), example 011 interpolates a `json::Error`, and `to_string` already is a `Value`'s user-facing text. Moving `Value` to a submodule was rejected because it renames every constructor. Settles OQ-json-1.
- **D-363 Multimap `size` and `count`**: In every multimap, `size` counts keys and `count` counts values. Why: `size` then means the same in every map-like module. Guava's `size`, which counts values, was rejected. Settles OQ-multimap-1, OQ-sorted_multimap-1 and OQ-ordered_multimap-1. Refines D-301, D-332.
- **D-364 Multimap keys never go empty**: Every key of a multimap holds at least one value, so removing a key's last value removes the key, and `get` returns `List<V>`, `[]` for a missing key. Why: a missing key and a key without values would mean the same, so `Option<List<V>>` would only add `unwrap_or(…, [])` at every call, and `has_key` tells the two apart where needed. Allowing empty keys was rejected. Settles OQ-multimap-2 and -3 and their sorted and ordered copies. Refines D-297, D-332.
- **D-365 `io::write_stdout` flushes**: `io::write_stdout` writes through the same buffer as `io::print` and then flushes it, so its `Result` covers everything written to standard output so far. Why: with line buffering (D-346) a write that only fills the buffer cannot fail, so without a flush the `Result` would almost never report anything. Settles OQ-io-1.
- **D-366 Byte-order marks are kept**: `io::read_file` and `string::from_bytes` keep a leading U+FEFF. Why: Rust, Go and Node.js keep it, and `read_file` stays equal to decoding `read_file_bytes`. Stripping it was rejected. Settles OQ-io-2.

## 2026-10-06: Diagnostics

Goal: fix how diagnostics look before the first `.stderr` golden is written (M1 task A1), and settle how compiler code is exempted from the strict lints before the lexer is written.

- **D-418 Diagnostic layout**: The compiler renders a diagnostic as plain text: a header `error[E0012]: message` or `warning[W0003]: message`, a location line ` --> src/main.cheby:4:7`, a snippet of the affected source lines with line numbers, `^` under the primary span and `-` under secondary spans, each with an optional label, and then `= note: …` and `= help: …` lines. A suggested fix is a `help` line. Why: the layout of rustc is familiar, shows the code it talks about, and leaves room for the suggestions §13.8 asks for. A compact one-line format in the style of GCC and Go was rejected because suggestions and secondary spans read poorly in it.
- **D-419 Diagnostic codes**: Every diagnostic has a code: `E` and four digits for errors and `W` and four digits for warnings, assigned in order as checks are implemented, starting at `E0001` and `W0001`. A code is never reused or renumbered. When a check is removed, its code stays reserved and its explanation says so. Codes are stable from 1.0 (D-075). Why: a code names a diagnostic independently of its wording, so the wording can improve without breaking tools, searches or tests, and it is the key `cheby explain` (D-420) looks up. Warnings named by identifiers, and codes grouped by compiler phase, were rejected: names would compete with codes as a second key, and phase blocks fill unevenly and break when a check moves between phases.
- **D-420 `cheby explain`**: A new command, `cheby explain <code>`, prints the long explanation of a diagnostic code. The explanations live in `docs/diagnostics/`, one Markdown file per code (`E0001.md`), and are embedded in the `cheby` binary at build time. A test checks that the codes the compiler can emit and the files in `docs/diagnostics/` are the same set. Why: a diagnostic has room for one line of explanation, and the longer text with examples and fixes belongs next to the spec, where it is reviewed like the spec. Explanations written as strings in the compiler, and a spec appendix that lists every code, were rejected: the first hides them from review, and the second makes every new check a spec change. Extends D-031.
- **D-421 Positions and paths in diagnostics**: A location is `path:line:column`, with lines and columns counted from 1 and columns counted in Unicode code points. Spans inside the compiler stay byte offsets, and the language server converts them to the positions its protocol needs. The path of a file in the package is relative to the package root and uses `/` on every platform. Why: output is deterministic across machines and platforms (D-264), the goldens need no rewriting, and code points match rustc and most editors for the text Cheby source contains. Grapheme-cluster columns were rejected as needing segmentation tables in the compiler for a rare gain, and byte columns as wrong for any non-ASCII line.
- **D-422 Lint exemptions in code**: Code that needs raw arithmetic, `as` casts or indexing, such as the lexer's offsets, the runtime's tagged integers and object headers (D-278, D-279) and code generation, uses a local `#[expect(clippy::…, reason = "…")]` on the smallest function or module that needs it, in any crate. The reason states the invariant that makes the code safe. The workspace lints are never weakened, and no crate relaxes them in its own `[lints]`. Why: every exemption is visible and reviewed where it applies, and `expect` fails once the exemption is no longer needed. Crate-level relaxations were rejected because they leave whole crates unaudited, and keeping the front end free of exemptions was rejected because checked arithmetic in the lexer's inner loop works against the speed budget (D-247).
- **D-423 Strict Clippy lints without `nursery`**: The workspace denies Clippy's `pedantic` group and the lints that allow panics or silent overflow: `unwrap_used`, `expect_used`, `indexing_slicing`, `arithmetic_side_effects`, `unreachable`, `unimplemented`, `unchecked_time_subtraction`, `todo`, `string_slice`, `panic_in_result_fn`, `panic`, `exit` and `as_conversions`, following [namtao.com/rust](https://www.namtao.com/rust/). `clippy.toml` allows `unwrap`, `expect`, `panic` and indexing in tests. Violations are fixed in code or exempted locally (D-422). The `nursery` group is not enabled. Why: the compiler must report errors, never panic, on any input, and adopting the lints costs least while the code base is small. `nursery` lints are still in development and can report false positives, so denying them would push code into workarounds. Supersedes D-293.

Open:

- Whether diagnostics printed to a terminal use color, and how it is turned off (D-418). The goldens have none.
- How the path of a file outside the package, in `std` or a dependency, is shown in a location (D-421).
- The spec's examples of compile errors, such as those in §3.12 and §5.2.3, are written as comments without codes. They stay informal until the compiler assigns the codes.

## 2026-10-07: M1 syntax layer

Goal: settle the spec gaps that the lexer, parser and syntax validation of M1 found (phase A), and fix the diagnostic codes of the syntax layer.

- **D-424 Grammar errors versus validation errors**: The compiler parser reports a grammar error only for a shape that both the spec and `tree-sitter-cheby` reject. Where tree-sitter accepts a shape that the spec rejects, the parser builds a tree without an error, and a separate validation pass reports it. Examples are camelCase or reserved-word names, patterns as top-level parameters, `exposed` without `pub`, `f(_)`, pipes without a hole, chained comparisons, float patterns and type arguments on an interface function (`Show::show::<T>(x)`, which App. A.5 and D-165 rule out). A shape that both reject stays a grammar error, so a named rest in a field pattern, `P { x, ..rest }`, is reported by the parser. Line-break significance (§2.8, D-231), lexical errors (§2.1, §2.5) and keyword reservation (§2.4) are grammar errors even where tree-sitter accepts the input. Such disagreements are grammar mismatches, fixed in tree-sitter. The parser cross-check compares grammar errors only, so a `parse-fail` UI test must contain a grammar error, and a `check-fail` test covers the rest. Why: otherwise every spec rule that tree-sitter does not enforce would fail the cross-check on its own UI test, and a check over a whole tree gives better messages than parser recovery. A parser that accepts everything tree-sitter accepts was rejected, because line breaks, lexing and keywords cannot be left that loose. Extends D-272.
- **D-425 Validation of files with grammar errors**: On a file with grammar errors, `cheby check` runs only the token-level checks: lone carriage returns (E0002), naming (E0006), reserved words (E0007), malformed numbers (E0008), escapes (E0011), and whitespace in an interpolation that has no grammar error of its own (E0012). The checks of tree shapes run only on files without grammar errors. The other files of the package are checked in full. Why: shape checks on a broken tree report misleading errors, such as "a tuple has at least two elements" for an unclosed `(1 +`. Token checks do not depend on the tree. Skipping them too was rejected, because it hid real errors, and the help "Cheby has no `if`, use `case`" exactly when `if` caused the grammar error.
- **D-426 Newlines at the start and end of a file**: Newlines before the first token and before the end of the file are ignored, and a file need not end with a newline. Why: App. A.1's `module` asked for an `NL` after every item, so a file without a final newline would have been rejected, which no reader expects.
- **D-427 Newlines in interface bodies**: The functions of an interface body are separated by newlines, with none needed after the last: `"{" [ NL ] [ interface_fn { NL interface_fn } ] [ NL ] "}"`. Why: §2.8 drops the `NL` before `}`, so the old rule `{ interface_fn NL }` could never be met by the last function.
- **D-428 Kinds of `////` and `//!!`**: A comment that starts with four or more slashes, `////…`, is an ordinary comment. `///` followed by the end of the line or by any character other than `/` is a doc comment. Every comment that starts with `//!`, including `//!!`, is a module doc comment. Why: §2.2 did not say. This is Rust's rule, rows of slashes are a common separator that should document nothing, and `tree-sitter-cheby` already follows it under this number. Refines D-078.
- **D-429 Module-qualified record update**: A record update starts with a `ctor_path`, so its type name may be qualified: `supervisor::Policy { ..policy, backoff_ms: 1 }`. Why: §5.11.2 (D-156) already allows a qualified name and example 019 writes one, but Appendix A's `record_update` started with `UPPER` only. Refines D-156.
- **D-430 Splitting `>=` after type arguments**: In type contexts the parser splits `>=` into `>` and `=`, as it splits `>>` into two `>`, so `const empty: List<Int>= []` parses. Why: by longest match the closing `>` and the `=` would form one token, and tree-sitter's context-aware lexer already splits it. A valid program never changes meaning, since `>=` is never an operator in a type.
- **D-431 Line breaks in raw strings**: A raw string's value normalizes each CRLF line break to LF, as other string literals do. Every other character is taken literally. Why: otherwise a raw string's value would depend on how the file was checked out, such as with CRLF on Windows, which breaks deterministic output (D-264). Refines D-114.
- **D-432 Identifiers starting with a non-ASCII letter**: A token that starts with a non-ASCII letter is read as an identifier over the letters and digits that follow, an `UPPER` one if the first letter is upper-case and a `LOWER` one otherwise, and is reported once as a non-ASCII identifier (E0005). Any other non-ASCII character outside strings and comments is an unexpected character (E0003), one error per character. Why: `été` is an attempt at a name, not stray punctuation, and one error for the word reads better than one per character. Refines D-127.
- **D-433 A base prefix followed by underscores**: A base prefix followed by `_`, such as `0x_`, `0b__` or `0x_1`, is a malformed number (E0008) reported by validation. A prefix followed by nothing of its base, such as `0x` or `0b2`, is a grammar error with the same code. Why: §2.5.1 needs a digit right after the prefix, but tree-sitter's integer token accepts underscores there, so by D-424 it is a validation error. Refines D-084.
- **D-434 A doc comment between attributes**: A `///` comment comes before all attributes of the item it documents. A `///` after an attribute is a misplaced doc comment (E0017), with a help to move it above the attributes. Why: §2.2's "possibly after more `///` lines and attributes" did not say whether a `///` may stand between two attributes, Appendix A.2 forbids it, and one place for docs keeps them easy to find.
- **D-435 Attribute names are not checked as names**: The name after `@` or `@!` is not checked against the reserved words or the naming convention. A name outside the fixed set is an unknown attribute (§4.8). Keywords stay keywords, so `@test` is a syntax error. Why: `@async` is an attribute (D-200) although `async` is a reserved word, and an attribute name binds nothing. Refines D-128.
- **D-436 `(T)` as a type is a one-element tuple**: There is no parenthesized type. In a type, `(T)` is a tuple type with one element and so an error (E0030), like `()` and `(T,)` (D-076). In patterns and expressions, `(p)` and `(e)` stay parenthesized forms. Why: Appendix A.3 has no parenthesized type, types have no operators that need grouping, and tree-sitter reads `(T)` as a tuple type. Adding parenthesized types was rejected as a second way to write `T`.
- **D-437 Empty field and pattern lists**: A positional variant has at least one type, a named-field variant at least one field, and a positional constructor pattern at least one sub-pattern. `Foo()` and `Foo {}` as variants and `Some()` as a pattern are syntax errors (E0013) reported by validation. Why: Appendix A already requires one element, and an empty list would be a second way to write the unit variant `Foo`. tree-sitter accepts them, so by D-424 validation reports them.
- **D-438 `as` and `|` after an `as` pattern**: `as` binds a whole list of alternatives and comes at most once at that level, so `A as x | B` and `p as a as b` are syntax errors (E0013) reported by validation. A parenthesized `as` pattern may stand anywhere a pattern may. Why: Appendix A.6 allows `as` only after the whole list of alternatives, which keeps `A | B as x` meaning one thing. tree-sitter accepts both shapes, so by D-424 validation reports them.
- **D-439 A `_` arm that is not last in a subjectless `case`**: In a subjectless `case`, a `_` arm anywhere but last is an error (E0035), like a missing final `_`. A subjectless `case` without arms is only a syntax error (E0013). Why: every arm but the last has a `Bool` condition (D-109), and `_` is not an expression, so an earlier `_` breaks the same rule. Refines D-109.
- **D-440 Tuple-shape warning once per written type**: The warning of D-243 (W0001) is reported on the outermost tuple type that has a tuple element or four or more elements. A tuple inside one already reported is not reported again. Why: one warning per written type is enough, and `(((A, B), C), D)` would otherwise give two. Refines D-243.
- **D-441 Nesting depth limit**: The parser counts the nesting of expressions, patterns, types and blocks with one counter, and nesting deeper than 256 levels is an error (E0016). A block used as an expression counts once, through its expression. A block reached otherwise, as the body of a function, closure, local function or test, counts itself. The limit belongs to the implementation, not to the language. Why: a recursive-descent parser must never overflow its stack, on any input. One counter bounds every cycle of the recursion, including nested local functions, and 256 levels fit in 512 KiB of stack in debug builds, far beyond real code. Separate counters per construct were rejected, because mixing constructs would multiply the depth.
- **D-442 Diagnostic codes of the syntax layer**: The syntax layer uses these codes: E0001 invalid UTF-8, E0002 lone carriage return, E0003 unexpected character, E0004 block comment, E0005 non-ASCII identifier, E0006 naming convention, E0007 reserved word, E0008 malformed number, E0009 number suffix, E0010 unterminated string, E0011 invalid escape, E0012 invalid interpolation, E0013 syntax error, E0014 unexpected line break, E0015 unclosed delimiter, E0016 nesting too deep, E0017 misplaced doc comment, E0018 module order, E0019 dangling attribute, E0020 missing type annotation, E0021 pattern as a top-level parameter, E0022 invalid `exposed`, E0023 bound or type argument where none is allowed, E0024 tuple index, E0025 misplaced `_`, E0026 several `_` in one argument list, E0027 `_` as the only argument, E0028 pipe without `_`, E0029 chained comparison, E0030 tuple with fewer than two elements, E0031 invalid record update, E0032 misplaced rest, E0033 float pattern, E0034 interpolated pattern, E0035 subjectless `case` without a final `_`, E0036 invalid manifest, E0037 invalid module name, and W0001 tuple shape. A rule with a decision behind it gets its own code, and other syntax errors share E0013. Errors that are not about the program, such as an unreadable file or directory, a missing `cheby.toml`, a misused command line or an unknown code given to `cheby explain`, have no code and print as plain `error: …` lines. Why: D-419 needs a code for every diagnostic, assigned in order as checks arrive, each with its explanation (D-420). Tool errors have nothing for `cheby explain` to say, and coding them would use up numbers. Extends D-419.
- **D-443 Rendering details**: Diagnostics are rendered as rustc does in the cases D-418 leaves open. Line numbers are left-aligned. Several labels on one line share one marker row: the label that ends last is written inline, and the others hang below it. A multi-line span is drawn with a rail to the left of the text, from `_…^` on its first line to `|_…^` on its last. A gap of one line between shown lines is printed, and a longer gap becomes `...`. A tab shows as four spaces and other control characters as their Unicode control pictures, and markers use display width. Labels in another file get their own `::: path:line:col` section. Notes come before helps. A byte-order mark is not counted in columns, and an empty span at the end of a file that ends with a newline points at the empty last line. Diagnostics are separated by an empty line, and no summary line such as "2 errors" follows them. Why: goldens need one fixed form. A summary line was left out to keep goldens minimal and stable, and it can be added later in one change. Refines D-418.
- **D-444 Unknown keys in `cheby.toml`**: `cheby.toml` accepts only the top-level keys `name`, `version`, `description` (a string), `licences` (a list of strings), `targets`, `[dependencies]` and `[const-eval]`. Any other key is an error (E0036) whose help lists the keys. A dependency accepts only `git`, `tag` and `rev`. `targets` must not be empty or repeat a target. The contents of `[const-eval]` are not checked until §13.9 settles its spelling. Why: §13.3 listed the keys without saying what happens to others, and a typo such as `verison` or `target` would otherwise be ignored silently.
- **D-445 Check-only examples and the bless guard**: In the conformance harness, an example marked `skip-run` is only ever checked with `cheby check`. Its milestone names when its fixture arrives, so a passing check before that milestone is pending, not an unexpected pass. Separately, `cargo xtask bless` refuses to rewrite an example's goldens when the run's exit code differs from `expected.exit` (0 by default). Why: M1 checks every example, but 020 and 031 are M3 examples because of their fixtures, so they would fail as unexpected passes from M1 on. The bless guard stops toolchain errors such as "not implemented" from replacing good goldens, which happened once in M1. Extends D-288.
- **D-446 Example 030 moves to M5**: Example 030's milestone is M5, and examples with dependencies are exempt from the M1 exit criterion that every other example passes `cheby check` until M5. Why: 030 imports its git dependency `sql`, which cannot resolve before fetching exists, and `cheby check` rejects dependencies until M5 (m1-core.md B1). Keeping 030 in M3 would contradict both the M1 exit criteria and the M3 plan. Refines D-288.

## 2026-10-07: M1 vertical slice

Goal: settle the spec gaps and plan-level choices that the M1 vertical slice found (name resolution, interfaces, type checking, MIR, runtime, the Cranelift JIT and the driver, enough to run example 001), and fix the diagnostic codes it added.

- **D-447 Prelude types live in a builtin module with home modules**: The prelude's types, constructors and `Show` (D-112) are compiler-known declarations of a builtin module, which has no source and cannot be imported. Each type except `Never` records its home module in `std`, such as `std::int` or `std::option`, and `Show` has none yet. A qualified name or item import into a home module finds the builtin item, so `option::Option` and `option::Some` are the prelude's `Option` and `Some`, and the home module's source does not declare them again. Interface satisfaction for a builtin type looks for its functions, such as `show` and `compare`, in its home module (§8.2). Every module of the local package depends implicitly on each home module that the toolchain ships, while std modules depend only on what they import. Why: the prelude must exist before any module is checked, including the std modules that use `Option`, and implicit imports between std modules could form cycles (D-145). The implicit edges keep the home module among the module's dependencies, as the locality rule requires (D-246), although user code does not import it. Observable behavior is that of D-112, D-353 and §8.2.
- **D-448 Every top-level `main` has an entry-point signature**: Every top-level function named `main`, in any module, must take no parameters and return `Nil` or `Result<Nil, E>`, or it is an error (E0050). Its visibility stays free (D-163). This check comes before the support gate of D-451, so `fn main() -> Int` is E0050, not E0038. Why: any module's `main` can be run by its path (D-137), so a `main` with another signature is a mistake, not a function that merely is not an entry point. Treating it as an ordinary function was rejected, because `cheby run` on its module would then fail far from the cause. A real error must not be reported as "not supported yet", because the report would stay wrong once the feature lands. Refines D-137, D-163.
- **D-449 Panic report format**: A panic flushes standard output, then writes `panicked at <path>:<line>:<column>:` and the message on the next line to standard error, as rustc does. The location uses the paths of diagnostics (D-421, D-450), or `<unknown location>` when none is known. The default messages, used when the program gives none, are `explicit panic`, `not implemented`, `integer overflow`, `division by zero`, `assertion failed`, `` `let assert` pattern did not match ``, `stack overflow`, `equality or hashing reached a function value or a handle` and `shift amount out of range`. A message given with `panic as` replaces the default, `todo as m` prints `not implemented: m`, and failed assertions add what §11.4 and §11.5 require to their message. `cheby run` then exits with status 101 (D-182), and constant evaluation captures the report instead of printing it. Why: §11.6 requires a location in every panic message but fixes no text, and run-fail goldens need one. Flushing first keeps the program's earlier output ahead of the report when both streams go to one terminal or file (D-346), and diagnostics already follow rustc (D-443).
- **D-450 Standard-library sources in M1**: Until M3 ships `std` precompiled (D-256), the sources in `std/` are embedded in the `cheby` binary, and a build parses and checks only the std modules its imports reach. In diagnostics and panic locations, a std file is shown as `std/` followed by its module path with `/` and `.cheby`, such as `std/io.cheby:12:8`. Std modules may declare `@external(js, …)` bindings to `.mjs` files that do not exist yet, and nothing checks JS module files before M4. Why: the binary is then self-contained and deterministic from any directory, including the temporary packages of UI tests. D-421 covers only package files, and std locations must not contain absolute paths (D-264). Declaring the JS bindings now lets std pass the cross-target checks of packages that target both platforms, without editing std again in M4. Extends D-421.
- **D-451 A temporary code for what M1 does not support yet**: While M1 is in progress, a valid construct that the compiler cannot check or run yet is reported as E0038 ("… is not supported yet"), once for the outermost construct, so the compiler never panics on it or accepts it silently. The same code covers an import of a std module that the stdlib spec or plan defines but `std/` does not ship yet (otherwise E0039), and a name missing from a shipped std module that is still partial, such as `io::read_line` while `std/io.cheby` has only the printing functions (otherwise E0042). It covers an inference variable still unbound at the end of a top-level body after numeric literals are defaulted, such as the element type of `let xs = []` when nothing fixes it. That is a compile error asking for a type annotation, and it gets its own code when C3 lands. It also covers a bodiless function whose `@external` attributes do not cover every target its module is built for (the package's targets, narrowed by `@!target`), until the cross-target check (C12) lands. An E0038 inside a function body skips only the body: the signature is still checked, published in the interface and hashed, and callers are checked against it. An E0038 in a declaration, such as its kind, type parameters, attributes or signature types, skips the whole item. E0038 is retired at M1 exit: the compiler stops emitting it, and its explanation stays and says so (D-419). Why: while M1 grows, valid examples must report only E0038, never a false "no such module" or "no such name". Interfaces must not depend on bodies (D-246, §13.12.3), and gating whole items for body constructs hid real errors in their callers. A function that exists only on some targets needs the cross-target check of §12.6 before its uses can be accepted. Defaulting an unconstrained variable to `Nil` was rejected as surprising, and a per-name catalog of planned std items was rejected because it would duplicate `docs/stdlib/`. The cost is that a typo in a partial std module is E0038 instead of E0042 until the module is complete.
- **D-452 Phase-A errors stop later phases**: If reading the manifest, discovering modules, lexing, parsing or syntax validation reports an error, name resolution and type checking do not run. Warnings do not stop them. Why: later phases never see a broken tree, so none of their diagnostics come from one, as with D-425 inside the syntax layer, and every syntax UI golden stays as it is.
- **D-453 Native calling convention**: Every Cheby-ABI function takes a hidden first parameter, `ctx`, a pointer to the execution context of the running entry (from M2, the running fiber's), and passes it on in every call and tail call. The function-entry check compares the stack pointer with the stack limit at offset 0 of the context, and setting the limit to the highest address forces the next function entry into the runtime's slow path, so the yield check (D-028), the deadline of constant evaluation (D-195) and stack-overflow detection (D-124) share one compare. Every Cheby-ABI function returns one uniform word, whatever its declared type, while parameters keep the representation of their declared types, with `Int`, `Float`, `Bool` and the sized numbers unboxed. Every call whose callee is not known statically, of a closure, local function, function value, dictionary entry or `dyn` value, uses one convention: `ctx`, the owned closure object `self`, then uniform words, returning a uniform word. A closure object holds its code address as `addr | 1` at offset 8, so freeing skips it like a tagged integer, and every function is aligned to 16. Inside a local function, its own name refers to `self` and is never a capture. A function value of a top-level function is a closure whose code calls the function through its indirection slot, and a dictionary is an object holding a type descriptor and one closure per interface function. The runtime never calls `tail`-convention code: entry thunks and one trampoline per arity use the platform C convention, with `ctx` first. Foreign functions take no `ctx`. The vertical slice compiles only direct calls of top-level functions and rejects closures, local functions, function values and dictionaries with E0038 (D-451), so their part of this convention applies from the tasks that add them. Why: `cranelift-jit` has no thread-local storage, and the limit differs per fiber (D-124), per REPL entry (D-283) and per constant evaluation (D-195, D-269), so it travels with the code. Adding the parameter later would change every signature. A uniform result keeps every tail call a `return_call` (D-015): a function returning `Int` that tail-calls a generic function returning `T` could not convert the result after the call. One convention for unknown callees means indirect and `dyn` tail calls need no adapters. A local function that captured itself would be a reference-count cycle that leaks on every local loop, and calling through the slot keeps REPL redefinitions visible to function values (D-043). The cost is that an `Int` result is tagged and a `Float` result is boxed, and release builds may add unboxed-result entry points for calls that are not tail calls. → [ADR-0055](../adr/0055-native-calling-convention.md)
- **D-454 Object representation details**: In the header of D-279, a count of 0 marks a static object. A local count `n > 0` and a shared count `-n` both mean `n` references, so 0 is reached only by freeing, and an object is unique when its count is 1. Only the 32-bit count is written after allocation, and count operations never write a static object. A count that would overflow makes the object static, and it leaves the leak count (D-458). The nullary constructors `Nil`, `True`, `False`, `None`, `Less`, `Equal`, `Greater` and user unit variants are static objects with their constructor's layout id in the uniform representation, and the runtime provides the builtin ones. `Bool` is unboxed, one byte, in monomorphic code. A `String` is the header, `len: u64`, `cap: u64`, then the UTF-8 bytes, with `cap` equal to `len` in literals, and `Bytes` has the same shape. Layout ids 1 to 63 are fixed: 1 `String`, 2 `Bytes`, 3 boxed `Int`, 4 boxed `Float`, 5 boxed `F32`, 6 closure, 7 tuple, 8 boxed `U64`, 9 to 15 reserved for runtime objects, 16 `Nil`, 17 and 18 `False` and `True`, 19 to 21 `Less`, `Equal` and `Greater`, 22 and 23 `Some` and `None`, 24 and 25 `Ok` and `Err`, and 26 to 63 reserved for collection nodes. Constructor tags follow declaration order. User layouts get ids from 64 on, registered in build order before the code that uses them. Generated code never embeds a user layout id: it loads the header word from a per-layout data symbol, `cb$layout$<module path>$<Ctor>`, which the JIT or the loader fills in when it registers the layout, and the static object of a user nullary constructor, `cb$ctor$…`, gets its header filled in the same way. The vertical slice rejects user constructors with E0038 (D-451), so no generated code uses these symbols yet. Why: D-279 reserves one count value for static objects without naming it. With 0, static objects are never unique and never written, so they can live in read-only memory, and M2's 32-bit atomic count updates never race a wider store. Static nullary constructors keep every uniform value self-describing for the layout-driven equality, hashing and debug printing of D-252, while a tagged-integer encoding would print `Some(True)` wrongly in generic code. Freeing needs the allocation size, and in-place updates at count one (D-274) need the capacity. Static objects emitted by code generation need constant ids. User ids come from a process-wide table, so baking them into code would make the code depend on what the process registered before, which breaks D-264 and cached code (D-254). Refines D-279.
- **D-455 Native externals**: A function with `@external(native, "s")` compiles to a Cheby-ABI wrapper in its own module, which calls `s` through the C ABI with the mapping of §12.5.1 and returns the result as a uniform word. Callers in every module call the wrapper through its slot like any other function, so being external is not part of the module interface, only the targets the function exists on. Before a program runs, every native symbol must be defined by the runtime or the process. Otherwise `cheby run` reports E0053 at the `@external` that names it, before the program starts, and `cheby check` does not report it. All `@external(native, …)` attributes that name one symbol in a program, std included, must give it the same C signature, or the later one in build order is E0054, which `cheby check` reports. Outside the standard library, a native symbol must not start with `cheby_rt_`, the runtime's internals, or `cb$`, generated code (E0055). Other names starting with `cheby_` stay free. Why: call sites and function values stay uniform, the interface holds no body-level detail (D-246, D-249), and the wrapper's entry check leaves stack headroom for the foreign call. Cranelift's JIT panics on an unresolved symbol, and which symbols exist depends on the process or the link, not on the source, so `cheby check` cannot know. A missing symbol is about the program, so it is a coded diagnostic, not a tool error (D-419, D-442). Two C signatures for one symbol cannot be generated or linked consistently. The reserved symbols have signatures that only the compiler knows, and the spec's own example binds `cheby_sqlite_open`, so the whole `cheby_` prefix cannot be reserved. Refines D-030.
- **D-456 Symbol names and slot identity**: Generated symbols are `cb$<kind>$<module path>$<item>…`, with the module path joined by `$`. The kinds are `fn`, `slot`, `shim`, `fnval`, `clo`, `cinit`, `const`, `test`, `entry`, `tramp`, `str`, `ctor`, `desc` and `layout` (D-454). Closures append their number within the owner, tests and test entries use the test's ordinal in its module, and strings are `cb$str$` followed by the owner's symbol without `cb$`, then `$<n>`. Entry thunks are `cb$entry$main$<module path>`, `cb$entry$test$<module path>$<n>`, `cb$entry$const$<module path>$<item>` and `cb$entry$repl$<n>`, and trampolines are `cb$tramp$<arity>`. Names are built from module paths and item names only, never from internal ids. An indirection slot (D-043) is identified by the item's path and its ABI signature. A REPL redefinition with the same ABI signature repoints the existing slot. One with another signature gets a new slot, whose symbol ends in `$r<generation>`, and old callers keep the old code until they are checked and compiled again. The vertical slice has no REPL, so generations and the `layout` kind are not emitted yet. Why: names must not depend on per-build ids (D-264), and cached code (M3) and AOT objects need stable symbols. Putting the kind first rules out collisions with a package or module named `slot`, `str` or `fn`. §13.5.2 allows signature changes, and repointing a slot that callers compiled for another signature read would be undefined behavior. Refines D-043.
- **D-457 Entry stacks**: Each entry, `main`, a test, a constant's initializer or a REPL input, runs on its own stack with a fresh execution context. In M1 that stack is a dedicated thread with the requested size, at least 512 KiB, and its limit lies 256 KiB above the bottom of the stack, which covers the distance from the top to the first frame and the runtime and foreign calls below the last checked frame. `main` runs on 64 MiB, and other entries default to 8 MiB (D-125). A panic hands its report to the waiting host and parks the entry's thread forever, abandoning its stack and live objects. The host applies its own policy: `cheby run` exits with 101, `cheby test` fails the test and runs the next, the REPL continues, and constant evaluation reports a compile error. OQ-P7 replaces the thread with a stack owned by the runtime, behind the same interface. Why: D-283 needs a stack per entry and abandonment without unwinding, and the policy after a panic differs between running, testing, the REPL and constant evaluation (§4.5, §13.6). A thread gives both without a stack-switching library. D-125 asks for more than 8 MiB for the root fiber without fixing a number, and ADR-0032 requires headroom for foreign calls. Refines D-283.
- **D-458 Debug leak check at exit**: A toolchain built with debug assertions checks the live-object counter when `main` returns with status 0 or 1. If objects remain, it prints `error: leak check failed: N objects are still live at exit`, or `1 object is`, to standard error and exits with status 102. There is no check after a panic, whose entry abandons its objects until unwinding exists (D-283), nor in the REPL. Objects that became static because their count overflowed (D-454) are not counted. Why: M1's exit criteria require zero live objects for every passing example, and the conformance harness must fail on leaks. A distinct status makes `cargo xtask bless` refuse to record the message as a golden (D-445). Refines D-029.
- **D-459 `cheby check` evaluates constants**: `cheby check` evaluates constant initializers with the JIT, as `cheby build` does, and reports their panics and exceeded limits, while still writing no artifacts. The vertical slice rejects constants with E0038 (D-451), so this applies from E6. Why: a panicking or over-limit constant is a compile error (§4.5, §13.9), and §13.1 says `cheby check` reports diagnostics like `cheby build`, while D-282 said only that it type-checks. Refines D-282.
- **D-460 Interface hashes refer to definitions by name**: The canonical encoding of a module interface, with the format tag `CHBI` and version 1, holds the module's items that are not `priv`, are not tests and have not been replaced by a REPL redefinition, sorted by namespace and name bytes. Constructors and interface functions are encoded inside their parent. Other definitions are referenced by module path, namespace or parent, and name, never by internal indexes, module ids, spans or interning numbers. The hash is SipHash-1-3 with a 128-bit result and zero keys. Why: an internal index counts private items and tests, so encoding it would change dependents' hashes when a private helper or a test is added, which defeats early cutoff (D-249, D-265).
- **D-461 Attribute placement**: `@external` is allowed only on functions and on types without a body, at most once per target, as `@external(native, "s")` or `@external(js, "m", "f")` with non-empty strings. `@target` takes exactly one target and is allowed on functions, types, aliases, constants, interfaces and tests. `@blocking` and `@async` take no arguments: `@blocking` needs an `@external` on the same function, and `@async` an `@external(js, …)`. `@deprecated` takes one message string and is allowed only on `pub` items. No attribute is allowed on a variant, a record field or an interface function. Every attribute other than `@external` appears at most once on an item. The only inner attribute is `@!target(…)`, at most once per module. A violation of any of these rules is E0045. A function without a body exists only on the targets of its `@external` attributes, further narrowed by `@target`. Why: §4.8 makes an attribute in a place where it is not allowed an error but does not list the places. These rules follow its table, §12.5 and §12.6.
- **D-462 Front-end diagnostics without a decision of their own**: Two tests with the same name in one module are E0041, the code of other duplicate names (§4.7). `Self` written as a type outside an interface declaration is E0042 (§8.1). A written type must give exactly one type argument per type parameter, and none to a type without parameters or to a type parameter, or it is E0051. An interface where a type is expected, or something other than an interface after `dyn` or in a bound, is E0052, with a help that suggests `dyn I` or a bounded type parameter. Type arguments on an interface, `dyn I<T>`, stay E0023 of the syntax layer. Why: the spec states these rules (§3.1, §3.12.1, §4.7, §8.1, §8.4, §8.6, D-045) without naming their diagnostics, and D-419 needs a code for each.
- **D-463 How types print in diagnostics**: Prelude types and the current module's own types print by their bare names, as in `Option<Int>` and `fn(String) -> Nil`. Other named types print as `<last module segment>::<Name>`, as in `map::Map<String, Int>`, type parameters by their names, and a type that could not be determined as `_`. Why: these are the forms users write at that place in the code, and goldens need one fixed form (D-418).
- **D-464 Internal errors and misuse of `cheby run`**: A broken compiler invariant, from any phase including MIR validation and code generation, prints `error: internal compiler error: <message>` without a code and exits with status 1. `cheby run <path>` where the path is malformed, names no module of the local package, or names a module without `main` is a tool error without a code and exits with status 1, with the messages "`x` is not a module path", "there is no module `x` in this package" and "module `x` has no `main` function". Compile errors are printed first and stop the run with status 1, and warnings are printed to standard error before the program starts. Why: neither is about the program's source. The no-panic lints make broken invariants come back as values (D-423), and a bad path is a misused command line. Printing warnings first keeps them apart from the program's output. Extends D-442.
- **D-465 Crate edges of the middle and back end**: `cheby_iface` depends on `cheby_diag` and `cheby_package`, and `cheby_resolve` depends on `cheby_iface`, which reverses the `cheby_iface` → `cheby_resolve` edge of D-284. `cheby_mir` gains `cheby_iface`. `cheby_codegen_clif` gains `cheby_iface`, `cheby_diag` and `cheby_runtime`, of which it uses only the `abi` module, which has no state and no dependencies. `cheby_jit` gains `cheby_mir` and `cheby_iface`, and `cheby_driver` gains `cheby_runtime`. Why: name resolution must read the interfaces of dependencies (D-246), so the interface model sits below it and is the shared vocabulary of every later phase. Code generation needs one source of truth for header bits, layout ids, context offsets and runtime symbol names, without touching the runtime's state. Refines D-284.
- **D-466 Diagnostic codes of the vertical slice**: The slice adds E0038 not supported yet (D-451), E0039 unresolved import, E0040 import cycle, E0041 duplicate name, E0042 unresolved name, E0043 private item, E0044 shadowed name, E0045 invalid attribute (D-461), E0046 function without a body or an `@external`, E0047 mismatched types, E0048 wrong number of arguments, E0049 call of a value that is not a function, E0050 invalid `main` (D-448), E0051 wrong number of type arguments and E0052 an interface where a type is expected or a type where an interface is expected (D-462), E0053 unresolved native symbol, E0054 conflicting native symbol and E0055 reserved native symbol (D-455). Why: D-419 assigns codes in order as checks arrive, each with its explanation in `docs/diagnostics/` (D-420). Extends D-419.

Open:

- Standard output that is closed before the program starts, as in `cheby run >&-`, cannot be detected: Rust's startup code reopens closed descriptors 0 to 2 on `/dev/null`, so writes succeed. Detecting it needs a process entry that runs before Rust's, or the AOT runtime entry of M3.
- The JIT reserves a 1 GiB arena per instance, so that relocations between code and data stay in range on aarch64. Its size and commit behavior on Windows and x86_64 are untested, and parallel tests there might commit the whole arena each.
- A REPL retry that changes the signature of a foreign symbol is rejected by Cranelift as an incompatible redeclaration. Functions get new generations (D-456), but foreign imports need their own answer before G5.
- E0038 must be retired at M1 exit (D-451): every construct of the M1 examples supported, the gates removed, and `docs/diagnostics/E0038.md` saying that the code is no longer emitted.
