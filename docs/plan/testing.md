# Testing and measurement

Correctness is checked at three levels: the examples run end to end, UI tests pin every compile-time rule, and unit tests cover each crate. Performance and determinism are measured in CI from M1 (D-247, D-264).

## 1. Example goldens

Every example in [`../examples/`](../examples/) gets golden files next to its sources (D-275):

```
docs/examples/003_fizzbuzz/
  cheby.toml
  src/main.cheby
  expected.stdout       required unless the example is compile-only
  expected.stderr       optional
  expected.exit         optional, defaults to 0
  stdin                 optional input fed to the program
  args                  optional, one argument per line; may hold {http_fixture} (D-1027)
  env                   optional, KEY=VALUE per line; may hold {http_fixture} (D-1027)
  data files            optional, read by the program and named in args (D-415)
  site/                 optional, the files the HTTP fixture serves (D-1027)
  test.toml             optional: skip-run, targets, milestone, reason, timing
```

- The harness in `tests/conformance/` runs each example with `cheby run`, compares outputs and exit code, and from M3 and M4 also builds and runs it with `--target native` and `--target js`. The same goldens apply to every target (spec §1.1 principle 5).
- From M3 every example that runs gets one more trial, `<name>@aot`. It builds the example once with `cheby build -o` into a temporary directory and runs the executable at every thread variant with the same goldens, comparing standard output and standard error each as the build's followed by the executable's (D-1140). Its milestone is M3 for examples of M3 or earlier. It runs in the serial group for `timing` examples, is never blessed and is ignored on Windows. `@rc=naive` and `::test` trials stay on the JIT (D-1025). No trial and no test skips when the runtime archive is missing: every CI job that runs `cheby build` builds `libcheby_rt_exe.a` first (D-929).
- From M3 each harness process sets `CHEBY_CACHE` to one fresh temporary directory, shared by all its runs and deleted at the end, so a run never reads or fills the user's cache and parallel runs never share one (D-959). Every other `cheby` that a test or a tool starts gets a fresh owner-only cache too: per command or per test in `cheby_cli`'s tests, one per process in `cargo xtask`, one per build in `check-determinism`, and one shared by the program differential and the fuzz target of a process (D-1128). `CHEBY_TEST_KEEP_CACHE=<absolute directory>` makes the harnesses and `xtask` use that directory as their cache and keep it, so two runs can share one cache (D-1144).
- The harness also runs `cheby test` in each example's directory as a trial of its own, which passes when it exits with status 0 and has no goldens. It is pending until the example's milestone has ended and must pass after it. A `skip-run` example's trial stays pending until the harness gives `cheby test` the example's fixture, which its tests need as much as its run does (D-472).
- From M2 the harness runs every run trial and `::test` trial three times, as `<name>`, `<name>@threads=1` and `<name>@threads=2`, with `CHEBY_THREADS` unset, 1 and 2 and the same goldens. The variants land before the scheduler, so every later change is tested at several thread counts from its first commit. While they run, the harness caps its own parallelism, and `CHEBY_HARNESS_SCALE`, 1 by default, multiplies its timeouts (D-722). A further variant, `<name>@rc=naive`, runs every example under M1's naive reference counting with the same goldens (D-718). It runs each run and `::test` trial once more with `CHEBY_RC=naive`, the base trial's goldens and milestone, at the default thread count, and every other trial removes `CHEBY_RC` from the child's environment. A CI job `rc-naive` runs the UI tests and `cargo xtask test-std` with `CHEBY_RC=naive`. The UI harness removes `CHEBY_RC` only for a test whose flags include `--reuse-report`, and `cargo xtask bless` ignores the variants (D-853).
- An example whose `test.toml` sets `timing = true` runs its variant trials serially after the parallel batch. 009, 013 and 019 set it, because they wait 250 ms to 1 s and flake under load. An example is never changed to make a timing test pass (D-725). `timing` is an optional boolean, false by default. Another type, or `timing = true` with `skip-run = true`, is a harness error that names the file, with exit status 2 (D-886). The serial group is a second libtest run on one thread, made only when some example sets `timing`, and filters, `--exact`, `--skip`, `--ignored` and `--list` apply to each batch. It holds every run and `::test` trial of such an example at every variant, the base trial included: 24 trials, or 30 under `CHEBY_THREADS=4`, listed last. The tests inside one `cheby test` still run in parallel (D-723). The harness ends with one combined line, `conformance harness: <p> passed; <f> failed; <i> ignored; <x> filtered out (serial after the parallel batch: <n>)`, and judges pending trials once (D-887, D-888).
- From M2 a program in which every fiber is blocked ends at once, in every build, with `fatal error: all fibers are blocked`, the blocked fibers and exit status 103, so a deadlock fails its trial instead of waiting for the harness's timeout (D-724). The runtime finds a deadlock at once when the last worker parks, and a deadlocked test among running ones within about 200 ms, well inside the harness's timeouts (D-860).
- Examples that need the network (030, 031) run against local fixtures. Until their fixture lands they are marked `skip-run` and only checked with `cheby check` (D-282). From M3's ninth wave 031 runs against the conformance harness's HTTP fixture, with `{http_fixture}` as its `args` (D-1027, D-1248, D-1273). 030 also has a git dependency, so it waits for M5 (D-446).
- 020 needs no fixture of the harness: its own C code, `src/store_ffi.c`, is named by its manifest's `[native]` table, as D-940 lets any package do, and its run, thread variants, `::test` and `@aot` trials are M3 trials (D-952).
- The HTTP fixture is `cheby_test_support::http_fixture`, a small static HTTP/1.1 server in Rust. `http_fixture::url_for(site)` starts a server for a site directory the first time a process asks, on `127.0.0.1` with a port the operating system chooses, and returns `http://127.0.0.1:<port>`. Later calls in the process share it, so every trial of a harness run uses one server. It serves the files under the example's `site/` directory: a path maps to the file of the same name, `/` to `index.html`, and anything else is `404`. An `args` or `env` golden may hold `{http_fixture}`, which stands for the server's URL, and any other `{…}` word in them is an error. The substitution lives in `Example::run_args`, which the conformance harness and `check-determinism` call. An example's output prints paths, never the port (D-1027). The fixture answers `GET` and `HEAD` only, takes a target's segments literally, answers anything that is not a readable file of the site with `404`, and closes each connection after one response with `content-type`, `content-length` and `connection: close` (D-1248). A placeholder is a `{`, characters other than white space and braces, and a `}`; a brace that starts none, as in JSON text, is kept as it is (D-1249).
- A `skip-run` example's milestone names when its fixture arrives, not when `cheby check` can handle it. Before that milestone a passing check is pending, not an unexpected pass (D-445).
- Examples whose output depends on randomness or `Map` iteration order (D-093) must make their output deterministic, for example by sorting or by a fixed seed passed through `args`. Where an example cannot, the decision log gets an entry and the example is changed, never the harness.
- `test.toml` records the milestone in which an example is expected to pass. Before that it is expected-fail, and an unexpected pass fails the run, so the table in [README.md](README.md#milestones) stays accurate. `tests/milestone` names the milestone in progress: examples of earlier milestones must pass, examples of the milestone in progress are pending and only reported, and examples of later milestones must fail. Bumping the file at a milestone's exit makes its examples binding (D-288). An example that imports standard-library modules of a later tier is checked as well as run from the milestone that ships those modules, which its `test.toml` names, and until then it reports only E0038 for those imports (D-477).
- The UI and conformance harnesses read three environment variables, and CI sets none of them (D-544). `CHEBY_MILESTONE=<Mn>` overrides `tests/milestone` for one run, so with `M2` every M1 test is required, which is how M1's exit is checked before `tests/milestone` is bumped. `CHEBY_PENDING=require` turns a failing pending test into a failure, except tests whose name matches a line of the file that `CHEBY_PENDING_ALLOW` names, one glob per line with `#` comments. At the end the harness lists the pending tests that passed and the failures it allowed.
- A strict run requires a failing pending test only when its milestone is the run's milestone in progress, that milestone is not later than the one `tests/milestone` names, and the allow list does not name the test. These stay report-only even in strict runs: a `skip-run` example's `cheby check` before its milestone (D-445), an example's `::test` trial before its milestone or without its fixture (D-472), and a test of a milestone later than `tests/milestone` that the `CHEBY_MILESTONE` override made pending. So `CHEBY_MILESTONE=M2` requires every M1 test, while M2 tests, such as the checks of examples 005, 009, 013, 018, 019, 022 and 028, which must still report E0038 at M1's exit (D-477), may fail (D-566).
- `CHEBY_PENDING` accepts `require`, and `report`, empty or unset keep the behavior of D-288. Any other value, such as a typo, is a harness error with exit status 2, so a strict gate never turns lenient by accident. An empty `CHEBY_MILESTONE` is no override, and a value that names no milestone is a harness error. The allow file is read only in strict runs, and a file that cannot be read is then a harness error. Without `CHEBY_PENDING_ALLOW`, or with it empty, the allow list is empty (D-567).
- In the allow file, `#` starts a comment that runs to the end of the line, and blank lines are ignored. The pattern is the first whitespace-separated word of a line, and the rest of the line is a free note, such as the reason and the gate. In a pattern, `*` matches any run of characters, `/` and `:` included, `?` matches one character, and every other character matches itself. The summary groups the pending tests as passed, allowed failures with the matching pattern, required failures, and still failing (D-567).
- On Windows, CI builds every test but runs only the tests that execute no generated code, until M6, which brings Windows support. M1 is judged on Linux and macOS (D-545). The test modules of `cheby_jit` are not built on Windows. Every other test that builds or runs a JIT carries `#[cfg_attr(windows, ignore = "runs JIT-compiled code; Windows support is M6 (D-545)")]`, including every test that runs `cheby check` on a package without front-end errors, since `check` then evaluates constants with the JIT. `UiTest::builds_a_jit` in `tests/support/src/ui.rs` picks the UI tests that are ignored: every run test, and every check test whose `.stderr` golden has no front-end error code. The conformance harness ignores every trial, and the REPL suite stays ignored. `TODO(M6)` notes mark the Windows-only test code left unbuilt, and the header of `.github/workflows/ci.yml` states the rule (D-641). From M2 the rule also covers the runtime's unit tests that switch stacks or run a scheduler, a poller or the blocking pool, though they run no generated code (D-714), the tests that run the pool alone included (D-873). The tests Windows does not build also include `cheby_cli`'s `blocking_io`, `closed_streams`, `repl_runtime` and `test_parallel` test files and `cheby_driver`'s runner and stuck-test modules and its FIFO test, which need Unix pipes, a shell or FIFOs; `cheby_jit`'s `start_root_tests` is built and its test ignored. The header of `ci.yml` lists them (D-874). From M3 the rule covers every test that builds or runs an executable, the `@aot` trials and `@command: build` UI tests included, since `cheby build --target native` is a "not available yet (M6)" error on Windows (D-935).
- _Note:_ CI runs only on pull requests and pushes to `main`, and nothing is pushed before M1's exit. So Linux is checked locally instead: the gates of waves 3, 5 and 6 of M1's back end and its exit gate run the build, the tests and the conformance suite in a local Linux container, as the user decided on 2026-10-10.
- `cargo xtask bless` rewrites goldens (D-292). A blessed change is reviewed like code. It refuses to bless an example whose exit code differs from `expected.exit` (0 by default), so a toolchain error never replaces good goldens. An intended change of exit code is edited by hand (D-445).

## 2. UI tests

`tests/ui/` holds small Cheby files, one rule each, grouped by spec chapter. A rule that needs several modules or its own manifest gets a package directory instead (D-471):

```
tests/ui/05-expressions/shadowing/let_shadows_import.cheby
tests/ui/05-expressions/shadowing/let_shadows_import.stderr
tests/ui/05-expressions/pipe/call_without_hole.cheby       // D-244
tests/ui/05-expressions/pipe/call_without_hole.stderr
tests/ui/06-patterns/exhaustiveness/missing_variant.cheby
```

- A file starts with a header comment that says whether it must compile, fail with the expected diagnostics, or run with expected output (D-289). The format is described in [`tests/ui/README.md`](../../tests/ui/README.md).
- A run test may have input and arguments beside it, like an example's: `<name>.stdin` is fed to `cheby run` as standard input, which is null without it, and `<name>.args` holds one argument per line, passed after `--`. In the header, `// @command: test` makes a `run-pass` or `run-fail` test run `cheby test` instead, and its goldens hold that output, and `// @flags: …` adds command-line flags after the subcommand, such as `// @flags: --deny-warnings` or `// @flags: --target js`. `tests/ui/README.md` documents every directive (D-543). The value of `@flags` is split at whitespace into words, which go after the subcommand and before `--` and the program's arguments. The directive may appear more than once, and its words are appended in order. There is no quoting, so a word cannot contain whitespace. A `.args` file beside a test with `@command: test` is a harness error, "`cheby test` takes no program arguments" (D-600). `.stdin` is fed byte for byte, with line endings unchanged, so a test can send `\r\n` and invalid UTF-8, and an empty one gives a standard input that ends at once. `.args` is read as text, with invalid UTF-8 replaced and `\r\n` turned into `\n`. An empty line is an empty argument, and a final line ending adds none. An input file beside a test whose mode is not `run-pass` or `run-fail` is a harness error (D-576).
- From M3, `// @command: build` makes a `run-pass` or `run-fail` test build the test's package with `cheby build` and run the executable, and compares the same goldens as a run test, the build's standard error followed by the executable's. E0053 at build time, E0055's reserved names and the errors of the `[native]` table get UI tests of this kind (D-1026). The build writes with `-o` into a fresh temporary directory, never into the package copy's `build/` (D-1143). When the build fails, its exit status and outputs are the test's result and nothing runs, so a `run-fail` test pins a build error (D-1142). These tests are never blessed: `CHEBY_BLESS=1` ignores them, and their goldens are written by hand (D-1141). Such a test is ignored on Windows (D-935).
- From M3 a run test may have `<name>.env` beside it, `KEY=VALUE` lines in the format of an example's `env` file, which the harness applies to the child's environment. Every other UI test, every example trial and the REPL harness remove `CHEBY_BACKTRACE` from the child's environment, as they do `CHEBY_THREADS`. The panic backtrace's tests in `tests/ui/11-errors-and-panics/backtrace/` set it this way (D-1043). The harness applies the file after its own settings (`NO_COLOR`, `CHEBY_RT_POISON` and the cache), to `cheby` and to a build test's executable, so it may override them, but it may not set `CHEBY_CACHE`, a `--reuse-report` test still runs without `CHEBY_RC` (D-718), and a line that is not `KEY=VALUE` with a non-empty key is an error of the test (D-1237).
- A package test is a directory `tests/ui/<chapter>/<name>/` with `cheby.toml` and `src/**`. Its header is in `src/main.cheby`, its goldens sit beside the directory as `<name>.stderr` and `<name>.stdout`, and it cannot be `parse-fail` (D-471).
- Each example of a compile error in the spec gets a UI test once its check exists, and the golden pins the code (D-476).
- From M2, `--reuse-report` makes `cheby run` and `cheby test` write one line per reuse candidate to standard error, before anything runs, sorted by file, line, column and text (D-852). UI tests with `// @flags: --reuse-report` in `tests/ui/09-memory-model/reuse_report/`, built from 012's record update, 019's update of a constant and 013's `set::insert`, pin its format, and a driver test checks that the flag leaves every example's MIR and CLIF unchanged (D-717).
- Every "must" and every warning of [§13.8](../spec/13-tooling.md#138-diagnostics-and-warnings) gets at least one test. A coverage script, `cargo xtask coverage` (D-292), lists D-numbers cited in the spec that no UI test or REPL transcript names in its header (D-638), and the list shrinks every milestone.
- Diagnostics are rendered in a stable plain-text form for comparison, without colors or absolute paths (D-418, D-421). The harnesses run `cheby --color=never` and set `NO_COLOR=1`, so no environment can color a golden (D-467).

## 3. Unit and property tests

- Each crate has Rust unit tests.
- Runtime kernels (RRB, HAMT, strings) are property-tested against simple reference models (`Vec`, `BTreeMap`), including reuse paths with a count of one.
- The parser is property-tested for losslessness: printing the CST reproduces the input exactly, for any input, including invalid input.
- The formatter is tested for idempotence and for meaning preservation: every example and std source formats to a fixed point in one pass, formatting keeps the token stream without trivia unchanged, apart from the import order and the trailing comma of a laid-out list, keeps the comments' texts in order and re-parses to the same node kinds (D-1153), and each example's output is unchanged after formatting a copy. Its core lands beside M3, not in M5, and from M3's ninth wave CI runs `cheby fmt --check` on the examples and std (D-1029, D-1031, D-1252).
- From M3, driver tests check what the cache reuses through the hidden `CHEBY_CACHE_LOG=<file>`, which lists every lookup as a hit or a miss and every package module the command parsed (D-1135). They cover a body edit that changes no mask, a mask-changing edit, an edit to a body a constant reaches, an interface edit, a second run with no edit, an interface edit that only a reader's lowering reads, a constant near the memory limit across `cheby check` and `cheby run` in both orders, and a cached note into a module whose item moved. They test what is recompiled, never how long it takes (D-973).
- The standard library's `test` blocks sit in `std/`, next to the code they test. User builds skip them, and testing std itself checks and runs them (D-479).
- `cargo xtask test-std [FILTER]`, which CI runs, tests std (D-542). It checks every shipped std module with its tests, then builds and runs the tests one module at a time. When a module's tests do not build together, each test is built alone to find the ones that do. A module or test that does not build is reported as `module <path> did not build: <codes>` or `test <module path> "<name>" did not build: <codes>`, is counted, and does not stop the other modules. The report ends with counts per module and in total, and the command fails if any test failed or did not build.
- The self-test checks std through an in-memory package `std_self_test`, version `0.0.0`, whose root module imports every shipped std module, in a front-end mode that only it uses, which checks the `test` blocks of std modules and keeps them. A module with front-end errors in its own file does not build, and while the tests run `env::program_name()` returns `std_self_test` (D-599).
- Every test of the stdlib spec is in `std/`, which the driver test `stdlib_spec_tests_are_in_std` checks by name. A test that needs a module importing its own lives in that module, under its own name or with its module's name in front when two would clash (D-630). A helper item of a std test is named by a written path in a test, so user builds, which resolve those paths, never warn about it (D-631). From M2 a list of pending spec tests, each with its module, its name and a milestone, lets the check accept a test of a shipped module as absent while that milestone is in progress. Once the milestone has passed, a remaining entry fails the check, and so does an entry whose test is present, so the list shrinks as tests land (D-728).
- The self-test prints its report after every test has run: a line per test or per module or test that did not build, then the failure blocks, an empty line, `counts per module:` with one line `  <module path>: P passed; F failed; D did not build` per module, a line `  total: P passed; F failed; D did not build; N filtered out`, an empty line and the summary. The summary adds `D did not build; ` before the filtered count when D is not 0. `<codes>` are the distinct error codes, sorted and joined by `, `, or `internal compiler error: <message>`, and a module that the front end did not check without an error of its own says `not checked` (D-598).

## 4. REPL tests

`tests/repl/` holds scripted sessions: inputs and expected outputs, covering redefinition (D-043), stale types (D-626), `let` rebinding (D-193, D-608), satisfaction across entries (D-610, D-627), the commands `:type`, `:module`, `:reload`, `:help` and `:quit` (D-098, D-624, D-625), and a package for `js` only (D-628).

A session is a transcript `tests/repl/<name>.repl`. Lines that start with `> ` or `. ` are input, and every other line is expected output. A directory `tests/repl/<name>/` with a `cheby.toml` runs its session inside that package (D-546). A line that starts with `< ` is a line of standard input that an entry reads, for example with `io::read_line`. It is fed right after the input line before it and is not echoed, so it is not expected output, and blessing keeps it after the same input lines (D-614). The harness gives `cheby repl` one pipe for standard output and standard error, so the expected output is both streams merged in the order of writes (D-548).

A transcript may start with a header: every leading line that starts with `// @`, up to the first line that does not. Each header line is a directive `// @key: value`, as in a UI test's header (D-289). The key `decisions` lists the decisions the session pins as `D-NNN`, with exactly three digits, separated by commas. From M2 the key `milestone`, with a value `M<n>`, names the milestone in which the session must pass, M1 by default, so a session of a later milestone is pending like an example (D-288, D-726). A line without `:`, an unknown key, a malformed number or a milestone that does not exist fails the transcript in the harness and fails `cargo xtask coverage`. The header is not part of the session. The harness neither feeds it to `cheby repl` nor expects it as output, and `CHEBY_BLESS=1` writes it back unchanged before the new output. A session's output always starts with the echo of its first input line, so a `// @` line cannot be output. `cargo xtask coverage` counts the header's decisions as covered, and `cargo xtask cross-check` reads only input lines, so it ignores the header. The harness and `cargo xtask coverage` share the parser `cheby_test_support::repl` (D-638).

## 5. Parser cross-check

CI parses every example and every source file of every UI test, including each module of a package test (D-471), with both the compiler parser and `tree-sitter-cheby`, and fails if one accepts a file the other rejects (D-272). Only grammar errors count. A rule that the spec enforces and tree-sitter does not is checked by a validation pass after parsing, so the compiler parser accepts the file too (D-424). Files that test syntax errors on purpose must be rejected by both, so a `parse-fail` UI test must contain a grammar error, and the other syntax rules are `check-fail` tests. Where the compiler reports a grammar error that tree-sitter does not, the decision log lists a grammar mismatch to fix in tree-sitter. The tree-sitter grammar is pulled in at the commit pinned in `tests/tree-sitter-cheby.rev`, and bumping it is a normal change (D-290).

The cross-check also parses each input of a REPL transcript, a `> ` line with its `. ` lines, in two forms: as it is, as the items of a module, and inside `fn repl_entry() { … }`, as statements, which covers expressions. Of the commands, only the expression of `:type` is parsed. The two parsers must agree on whether at least one form parses, so an input that both reject is a syntax error on purpose, not a mismatch. The `.cheby` files of a transcript's package directory must parse (D-615).

From M2 the cross-check also collects every ` ```cheby ` block of `docs/stdlib/**/*.md` and parses it as module items with both parsers, which must both accept it. Validation errors, such as a signature without a body, are not consulted (D-424, D-662).

## 6. Determinism

CI builds the examples and the synthetic benchmark project twice, with different thread counts and from different absolute paths, and compares all artifacts bit for bit (D-264). In M1 the artifacts are the serialized interfaces and the Cranelift IR dumps. `cargo xtask check-determinism` builds every example and the benchmark projects with `--jobs 1` and with the default, from two different absolute paths, and compares their interface encodings, MIR dumps, CLIF dumps and evaluated constant values byte for byte (D-551). MIR lowering and code generation run in parallel but take their results in a fixed order, which this check confirms (D-632). From M3 they are also the cache's blobs and records and the executables, and from M4 the JS output. Objects are never cached, so the executables stand for them (D-915). From M2 the MIR dumps hold the results of the Perceus passes and the unwind edges and pads, so the check covers those passes too. It stays a check of build outputs: the output of a run across thread counts is compared by the thread variants of §1 (D-727).

In M1 the dumps come from `CHEBY_DUMP_DIR`. When it names a directory, every build writes there, overwriting earlier files: `iface/<module path>.iface`, with the segments joined by `.`, for each checked module's canonical interface encoding; `mir/<module path>.mir`, `mir/<module path>.tests.mir` and `mir/entries.mir` as `cheby_mir::dump` prints them; `clif.txt`, the CLIF of every compiled function in compile order, unless the caller captures it; and `consts.txt`, one line `<module path>::<name> = <debug text>` per evaluated constant, sorted. From M3 every constant evaluation module's MIR and CLIF go under `consteval/`, `cheby check`'s included, and `consts.txt` stays at the top (D-1187). The command first generates each benchmark shape into two directories and compares the trees. Then it copies every example and a generated project of each shape, 20,000 lines by default and at least 40,000 for `large`, under two absolute paths, and builds each copy with `--jobs 1` and with the default, through `cheby check`, which evaluates the constants, and `xtask bench-build`, which compiles every function. The dump trees must be identical, and so must each command's exit status and standard error and the standard output of `cheby check`. The standard output of `bench-build` holds timings and is not compared (D-620).

From M3 the command also builds every example and benchmark shape into two fresh caches from two absolute paths and compares `blob/` and `rec/` byte for byte. `hint/` holds indexes keyed by paths and is left out. C objects are included without exception, since their keys hold no path and their records hold normalized header paths; this holds for one C compiler on one machine. Each cache is written by `cheby check` under `CHEBY_DUMP_DIR`, so the dump comparison stays, and for a runnable example by `cheby build` and `cheby run`, and for an example with tests by `cheby test`. Then each example is checked again, and each runnable one run again, warm on the first cache without `CHEBY_DUMP_DIR`: exit status and outputs must equal the cold build's, every constant lookup must hit, so the values used are entries that the two caches compared, and the first cache must still equal the second afterwards (D-972, D-1283). It also builds each runnable example twice with `cheby build`, from two paths and two caches under one output basename, and compares the executables byte for byte, with the runtime archive built first. It accepts a refused build only for one of the "not available yet" errors or a compile error with status 1, and never for 001, 003 or 024 (D-1114). For executables the C compiler, the linker and the output's basename are inputs too, since ld64 derives `LC_UUID` and the signature's identifier from the output's name (D-934). Its runs take an example's arguments from `Example::run_args`, so 031 runs against the HTTP fixture (D-1027).

## 7. Performance

- `bench/gen` generates synthetic Cheby projects of a given size and shape: many small modules, few large modules, deep and wide import graphs, generic-heavy code. It is the input for the compile-speed budgets, and its output depends only on size, shape and seed (D-291).
- CI reports, from M1 on, lines per second per core for a clean debug build, scaling with cores, the time from a one-function edit to `main` running, and from M6 the release-to-debug ratio (D-247, D-267). Until M6 they are reported, not enforced, so that OQ-P10 (throughput), OQ-P11 (latency) and OQ-P12 (release ratio) can revise them with real numbers. D-644 settles OQ-P10: D-247's throughput budget stays as written, since M1 measures 104k to 107k lines per second per core on projects of 100k lines or more, and M3's exit measures it again on CI's Linux runner.
- `cargo xtask bench-compile [--quick]` generates `bench/gen` projects of 10k, 100k and 1M lines and reports, as a Markdown table, the checking throughput, the throughput of checking with code generation, both with `--jobs 1` and the default, and the edit-to-run latency, which is a full rebuild until M3. `--quick` runs the 10k project only.
- From M3 the edit-to-run latency is read as D-974 says, for OQ-P11. It uses a release `cheby`, a fresh `CHEBY_CACHE` per shape and `bench/gen` projects of 1M lines with seed 1, in two shapes: `wide`, whose `main` reaches about ten modules, and `deep`, whose `main` reaches all 4,000 modules. One cold run is timed and reported, not budgeted. Then come five rounds of an edit to one function body in a module `main` imports, each followed by `cheby run`, and five rounds of an edit to `main`'s own body; each reading is the median of its five whole-command times. The hidden `CHEBY_PHASES=<file>` gives each phase's time, and the breakdown decides at M3's third checkpoint whether lazy compilation, our own loader or a stat cache is built (D-974, D-1277). `cargo xtask bench-compile --oqp11` runs these rounds, with an unused `let` first in `main` as the `main` edit, and `--restarts` times the three causes that start a warm command again (D-1256, D-1278, D-1279). D-247's throughput is still read in memory with `cargo xtask bench-build`, without the cache, and `bench-compile` adds two reported columns, a cold `cheby check` and a cold `cheby build`, both writing to an empty cache, and the same two on a cache that std's records fill (D-975, D-1280).
- M3's readings run on GitHub's `ubuntu-24.04` x86-64 runner, the reference machine of M3's exit, with the Apple M3 reported beside it. A `workflow_dispatch` workflow, `.github/workflows/bench.yml`, builds both `cheby` binaries release with `--locked`, runs three rounds of `cargo xtask bench-run --against` a base ref, M2's exit by default, then, when dispatched with `-f compile=true`, the OQ-P11 rounds with the restart causes and D-247's throughput, in steps that never fail the job (D-1281). The user pushes and triggers it at M3's first and third checkpoints and at the exit; agents never push (D-1035).
- Runtime benchmarks cover RC overhead, reuse hit rate (with the reuse report flag of D-170), fiber spawn and switch cost, channel throughput and collection kernels, and from M2 the sorted collections against a Rust tree (D-664, D-855).
- From M2, `bench/runtime/` holds Cheby packages that print a checksum, in four groups. The RC group covers list, record, map and string work and persistent trees. The fiber group covers spawning and joining, a capacity-0 ping-pong, 005's sieve, buffered channels and a mix of selects. The collection group runs the Cheby collections against Rust baselines. The JSON group times `std::json` parsing, decoding and writing on documents the programs write themselves; it is reported, never gated (D-899). `cargo xtask bench-run [--quick] [--threads N] [--baseline FILE]` runs a release `cheby`, takes the median of 5 runs and reports the change against a baseline. The M1 baseline of the RC group is recorded at commit 587f8a9, before any Perceus or unwinding change, and `bench-compile` gains columns for code size and RC operations (D-718).
- The collection group's first reading is the checkpoint-4b tree under `CHEBY_RC=naive`, not M1's binary, which cannot run the new modules. It is committed as `bench/runtime/baseline-collections.json`, the reference for M6's second reading (D-336, D-854). `cargo xtask bench-run --group collections --rust` also runs four Rust variants of each program, a persistent `Rc` tree with the same algorithm and three mutable ones, and fails when a checksum or size differs. `--rust-bin` names a prebuilt binary of the variants. D-855's factor is read against the persistent tree under Perceus.
- The two unwinding backends of M2 are each measured against a baseline without unwinding: the throughput of `bench-compile` on the 100k and 1M shapes against the last commit before the unwind pass, and the geometric mean of the RC group's run times against the same build run with `CHEBY_UNWIND_EDGES=off`, a hidden measurement switch that ignores the unwind edges and that release builds honor too. The numbers go to the user at M2's slice checkpoint, who chooses the backend, with a cost of 3% on either measure as the reference (D-696, D-702).
- In M1, `CHEBY_RT_STATS=1` makes `cheby run` print the runtime's counters after `main`: allocations, the in-place, grown and copied paths of list, string, `Bytes`, map and set updates, the time spent in `main` and in other entries, and the peak of live bytes. It is the evidence that the examples hit the in-place paths of D-525, and its output is not a stable interface (D-635).

## 8. Fuzzing

From M1, `cargo fuzz` targets the lexer and parser (no panics, losslessness) and the whole front end (no panics on any input). The targets are `fuzz/fuzz_targets/lex.rs`, `parse.rs` and `check.rs`. `cargo-fuzz` needs a nightly toolchain, so the jobs of D-277's stable pin do not run them, and in M1 `check` had only short local runs. From M2, a program generator produces well-typed, terminating programs, and a `cargo fuzz` target runs each one under naive reference counting and under Perceus, compares the outputs and requires the leak counter to be zero in both (D-718). It runs for a bounded time in the scheduled nightly workflow of §9, `.github/workflows/nightly.yml`, on a pinned dated nightly, with the lexer, parser and front-end targets (D-721, D-781).

The generator lives in `cheby_test_support` (`tests/support/src/progen/`) and builds on stable Rust, so the same programs are also checked in every CI run, not only on the schedule. The test `rc_differential` of `cheby_cli` generates 40 programs from fixed seeds, of which at least 30 must have a borrowed parameter and at least 25 a `drop_reuse`, and requires each to check and to give the same standard output, standard error and exit status under naive reference counting, under Perceus and under Perceus with `CHEBY_RT_POISON=0`, with no leak. A 5-seed stats run must count reuse hits above 0. A program below a floor extends the generator, never lowers the floor (D-844). It also checks the generator on 200 seeds: each program must check without a diagnostic and finish in time. The nightly target `fuzz/fuzz_targets/rc_differential.rs` uses the same generator (D-809). From M3 the generated programs are also compared with expected values computed by a reference evaluator for the generator's subset, which lives in `cheby_test_support` beside the generator. `rc_differential` compares naive counting, Perceus and the evaluator on its 40 seeds in every CI run, and the nightly target does the same on random seeds (D-719, D-1028). The evaluator's exit status and standard output are always compared, and its standard error only where the spec fixes it, which leaves out a panic inside a standard-library kernel. A program outside its subset is an error, never a pass (D-1145). From M4 native output is compared with JS output.

## 9. Sanitizers and leak checks

- Debug builds of the runtime count live objects, and the harness fails any example that ends with live objects that are not documented runtime-object cycles (D-029). After D-458's line, debug builds add one line naming the leaked runtime kinds, such as `<Sender>` and `<Fiber>`. No M2 example has a runtime-object cycle, so no allowance list exists (D-711).
- From M2 the check also runs after a panic, and a leak turns status 101 into 102, so `cargo xtask bless` still refuses to record a leak line. Debug builds tear detached fibers down before the check, and skip it, counting the skip, when a fiber is stuck on the blocking pool (D-710).
- The harnesses start every `cheby` with `CHEBY_RT_POISON=1`. A toolchain with debug assertions then poisons freed objects, keeps them in a bounded quarantine and stops with a fatal "use after free" error when one is used again (D-544). Poisoning changes only running code, never a CLIF dump, so goldens and the determinism check see the same dumps with or without it (D-565). The runtime's own unit tests poison by default, and `CHEBY_RT_POISON=0` turns that off, so they can run on the block cache (D-635).
- `cheby test` in a toolchain with debug assertions counts live objects before and after each passing test, and a difference fails that test (D-541). From M2 the tests run in parallel, each in its own accounting domain, and a test's detached fibers are torn down when it ends, before its domain is checked as an absolute count (D-723). Only a test whose teardown skipped a fiber, or whose domain a system refusal marked, has its check skipped and counted; later tests are checked (D-833).
- Live objects are counted per accounting domain, one per JIT, so parallel tests and several JITs in one process never count each other's objects. The check at exit reads the domain's count as an absolute number, after constants frozen before `main` have left it (D-564). From M2 there is one domain per root, test, REPL session and constant evaluation, which spawned fibers inherit (D-691).
- From M2 a scheduled workflow, on a dated nightly toolchain, runs ThreadSanitizer and AddressSanitizer on Linux x86-64 over the runtime's tests and the conformance suite, at `CHEBY_THREADS` 2 and 4, with migration stress and `CHEBY_HARNESS_SCALE=10`, one trial at a time, and the REPL's `:reload` transcript with a detached fiber under AddressSanitizer (D-831). It also runs a Miri subset over the runtime's pure-Rust logic and the fuzz targets of §8 for a bounded time. The runtime annotates its fiber switches for both sanitizers. JIT code is not instrumented, so a clean run covers the runtime's accesses and the synchronization it creates, and M2's exit report says so. A scheduled run never blocks a pull request, and every other job keeps D-277's stable pin (D-721). Until the `runtime` branch is pushed, the evidence is a local run of the workflow's job script on its pinned nightly: both sanitizers in a `linux/arm64` container and the Miri subset on macOS arm64. An emulated x86-64 AddressSanitizer run is informative, and x86-64 ThreadSanitizer is first checked by the scheduled run after the push (D-862). A report whose accesses lie only in a dependency gets one line, with its reason, in a suppression file next to the workflow; a report in Cheby's own crates is fixed, never suppressed. The `loom` models are skipped under the sanitizers and Miri, and an example that fails under ThreadSanitizer only because its own timeouts expire under the slowdown runs under AddressSanitizer only, and the workflow's header says so, since an example is never changed to make a timing test pass (D-725, D-863).
- `cargo xtask sanitize <address|thread|miri>` is the one driver, for the workflow and for local runs (D-882). Its sanitizer steps are `runtime`, `runtime-stress`, `jit`, `ui-deadlock`, `conformance`, `examples-poison-off` (AddressSanitizer only) and `repl`. Each builds with the workflow's dated nightly, `-Zbuild-std` and `-Zsanitizer=<s>` with `--cfg cheby_sanitize="<s>"` (D-875), and runs with `CHEBY_RT_TEST_EMULATED=1` and `CHEBY_HARNESS_SCALE=10`. A sanitizer report fails a step even when its command exits 0, and each step prints one summary line. A `ci.yml` step runs clippy on the runtime with each `cheby_sanitize` value on the stable pin, so the hooks never rot between scheduled runs (D-883).
- The runtime's unit tests scale every bound on how long something may take by `CHEBY_HARNESS_SCALE`, through a test helper: a wait after which an outcome counts as missing, a deadline after which a test gives up, and an asserted upper bound on an elapsed time. The hang bound is 60 s scaled. A wait that asserts that nothing arrives keeps its literal, and a test scans the crate for unscaled forms (D-872). CI's macOS test job sets `CHEBY_HARNESS_SCALE=5`, because the hosted macOS VMs stretch 10 ms waits to 30 to 90 ms (D-892).
- LeakSanitizer runs on the `jit` and `ui-deadlock` steps on Linux. It is off for `runtime` and `runtime-stress`, whose unit tests leak on purpose, and for `conformance`, `examples-poison-off` and `repl`, whose programs keep objects for good: a constant's static objects are held only by its slot in the JIT's data memory, which LeakSanitizer does not scan (D-539), and the REPL never frees its session values (D-547). The workflow's header names these causes, and a test checks it. The runtime's own leak check stays on in every step. Under the AddressSanitizer cfg, fiber stack slots are root regions, so objects held by fibers a halt freezes are not reported, and the compiler's interners mark the entries they leak on purpose (D-881).
- The Miri subset runs the runtime's pure modules in 14 groups, hamt, num, alloc, list, generic, text, bytes, locate, rc, layout, string, abi, values and timer, with permissive provenance, isolation disabled, leaks ignored and `PROPTEST_CASES=4`. Tests too large for Miri are skipped with their reasons or take a smaller size under `cfg(miri)`, the out-of-memory tests are skipped, and D-552's Unicode version test is ignored under the sanitizer and Miri cfgs. Fibers, the scheduler and JIT code cannot run under Miri (D-884). The static descriptors expose their strings' provenance, since a pointer read back from a word must have been exposed (D-885).
- From M2, `loom` model tests cover the waiter's compare-and-swap, the idle counters and the race between a scope's close and an outer cancellation (D-730).
