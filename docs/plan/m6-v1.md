# M6: v1 readiness

Goal: the release profile, the bundled linker, every platform of D-074 and D-892 and the compile-speed budgets enforced, so that v1 can ship.

Prerequisites: M4 and M5 done.

Detail level: workstreams with outcomes. This file is refined into tasks when M6 starts.

## Workstreams

### 6.1 Release profile

- Cranelift optimization on, specialization and inlining across modules within a size budget, using small inlinable bodies in interface artifacts (D-251, ADR-0046).
- Values of small scalar constants exported for folding (D-257).
- Equality, hashing and debug printing may be generated per type (D-252).
- The release-to-debug build-time ratio held at three or below (D-267).
- `cheby build`'s release profile and full debug info, which M3 leaves out (D-1037). Direct calls between Cheby functions in executables are reconsidered with it, since M3 calls through slots everywhere (D-916).

### 6.2 Linking and platforms

- lld bundled in the `cheby` binary (D-088, D-261), and CodeView/PDB on Windows once it lands (D-184). With it, `cheby build` builds for platforms other than the host (D-936), and macOS executables get a debug map, through `dsymutil` or the bundled linker, with deterministic output (D-938). The bundled linker must resolve an x86-64 `R_X86_64_PLT32` to colocated data straight to the definition, as GNU ld does (D-913).
- The runtime archive embedded in `cheby` and written to the cache on first use, keyed by the runtime ID, so the one binary of D-031 holds it; M3 links it from next to the binary (D-929, D-931).
- Precompiled `std` for every native platform and for JS (D-256): a pre-filled std cache and std code for other platforms, since M3 compiles std into the cache on first use (D-980).
- Executables on Windows: `cheby build --target native` there, which M3 refuses, a COFF writer for code records, symbol names that Windows linkers accept, `ring` for TLS, whose gate M3 keeps, and the backtrace's walk start on Win64 (D-914, D-935, D-939, D-1011).
- The conformance suite on all five native platforms of D-074 and D-892.
- Windows support: the JIT's memory path, native symbol lookup and a Windows path for example 010, which calls `arc4random_uniform`. The harnesses then stop skipping the UI run tests, the conformance runs and `::test` trials and the REPL suite on Windows (D-545), and every test that D-641 ignores or leaves unbuilt on Windows runs there, as its `TODO(M6)` notes and the header of `ci.yml` record.
- Fibers on Windows: the Win64 and Windows aarch64 context switches, Windows's commit charge for stack regions and the stack fields of the thread environment block. They replace M2's thread backend and the fatal error for programs that start fibers, and the runtime's tests that D-714 ignores run on Windows. Hosts with strict overcommit may be revisited with the commit charge (D-676, D-677, D-714).

### 6.3 Kernel review

- Each runtime kernel is benchmarked against a Cheby version written over private intrinsics, and moved to Cheby where the cost is acceptable (D-274, [stdlib.md](stdlib.md#1-how-modules-are-implemented)).

### 6.4 Budgets and hardening

- D-247 and D-267 budgets, as confirmed by D-644 (OQ-P10), OQ-P11 and OQ-P12, enforced in CI, with OQ-P12 settled from the first release-build measurements.
- Fuzzing and sanitizer jobs run without open findings.
- Every D-number in the spec is covered by a UI test or an example, or listed as untestable with a reason.

### 6.5 Release

- Installers or archives per platform, the licence files (D-089) and the documentation of the leak behavior of D-029.
- The spec moves from draft to the version that v1 implements. After 1.0 the compatibility promise applies (D-075).

## Exit criteria

- Every example passes on every platform of D-074 and D-892 and on JS, in both debug and release profiles.
- The compile-speed budgets are met in CI.
- Builds are bit-identical across machines of the same platform (D-264).
