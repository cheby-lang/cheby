# M3: AOT output, build cache and cached code

Goal: native executables from `cheby build`, the global build cache with interface artifacts, cached code that lets `cheby run` meet its latency budget, foreign code from packages and the tier-3 stdlib on native (D-099, step 3; D-247, D-254).

Prerequisites: M2 done. Tier-3 stdlib specified. OQ-P9 (linking foreign code) settled. All three are met: M2's exit is `29848fe`, the tier-3 pages in `docs/stdlib/` follow D-981 to D-1024, and D-940 settles OQ-P9.

Out of scope: executables on Windows (M6, D-935) and for other platforms than the host (M6, D-936); the release profile, full debug info and direct calls between Cheby functions (M6, D-916, D-1037); a debug map on macOS (M6, D-938); remapping the toolchain's source paths that executables hold (M6, D-1162); embedding the runtime archive in `cheby` and a pre-filled std cache (M6, D-931, D-980); lazy compilation and our own loader, unless CP3's reading asks for them (D-914, D-923, D-974); the performance items D-912 left open (D-976); `cheby clean` and a size limit for the cache (D-961); process spawning (D-1024); an HTTPS server (D-1011); the `.mjs` files of tier 3 (M4, D-986); and the LSP core (M4, D-1029).

The design behind the tasks is logged in the [M3 design](../decisions/LOG.md#2026-10-21-m3-design) session, D-913 to D-1043, with ADRs 0063 to 0067. The panic backtrace's details were drafted after the first answers and logged in the same session (D-1038 to D-1043). [architecture.md](architecture.md) describes the code records, the cache and the runtime archive that M3 builds.

## Workstreams

The workstreams of the roadmap stay. The packages below deliver them.

### 3.1 Object output and linking

Packages: N1a to N9, H0.

- One code model for the JIT, the cache and executables. Code is compiled with `is_pic=false`, every generated symbol is colocated, and runtime and foreign symbols are reached through import words `cb$imp$<symbol>` (D-913, ADR-0064). One fixed CPU feature set per target serves the JIT and objects (D-921).
- Each module compiles to one code record. `cheby_link` replays records into Cranelift objects, one per module, and adds one generated program object (D-914, D-915). Calls between Cheby functions go through slots in executables too (D-916). Shared definitions are global and hidden, a slot whose borrow mask is not all-owned carries the mask in its name, and code fixed by its key is copied into each object (D-917, D-918).
- Executables link `libcheby_rt_exe.a`, a staticlib that holds mimalloc as its global allocator outside sanitizer builds and re-exports `cheby_runtime` (D-890, D-928). In M3 `cheby build` finds the archive next to the `cheby` binary and checks its runtime ID before linking. M6 embeds it (D-929 to D-932).
- `cheby build [module_path] [--target native|js] [-o PATH]` links with `cc` from `PATH`, with fixed flags and input order, for the host only, on macOS arm64, Linux x86-64 and Linux arm64. Windows keeps a "not available yet (M6)" error (D-088, D-261, D-933, D-935 to D-937). Executables are bit-identical for the same inputs, and the output's basename is an input (D-934).
- An executable's C `main` calls `cheby_rt_main`, which reopens closed standard streams on the null device as D-474 requires and ignores `SIGPIPE` (D-925). It exits with `cheby run`'s statuses (D-926), bakes `[runtime]` in at build time and honors `CHEBY_THREADS` (D-927). Module records are registered by one routine, and layout ids are assigned at start (D-919, D-920).
- DWARF line tables are written into every object, for debuggers and profilers. macOS executables carry no debug map until M6 (D-259, D-938). Full debug info comes with M6 (D-1037).
- An opt-in panic backtrace, turned on by an environment variable, is built from the frame walk and the call-site map of deadlock reports. It needs no DWARF, changes no golden, and works under `cheby run`, `cheby test`, the REPL and in executables. `CHEBY_BACKTRACE=1` turns it on, and the walk starts at assembly stubs of the runtime's panic entries (D-856, D-867, D-939, D-1038 to D-1043).
- Foreign code supplied by packages: a `[native]` table with `sources` and `libraries`, compiled by `cc` with fixed flags into cached C objects, and one shared library per package under the JIT (D-940 to D-942, ADR-0063). E0053 covers reached symbols wherever code runs, and E0055 every name the runtime exports (D-943, D-944). The `cheby.h` header gives C code its `cheby_ffi_` functions (D-187, D-945, D-946).
- Drop functions of user external types run inline from the finalizer slot of M2's handle kinds, and `@blocking` foreign calls from packages run on M2's blocking pool (D-101, D-647, D-683, D-703, D-949, D-950). NULL results, external values in results and output from foreign code follow D-947, D-948 and D-951.
- Executables unwind Rust frames with the platform unwinder. Cheby frames unwind by return-flag propagation, which keeps unwinding in the generated code itself, so the object writer and the loader carry nothing extra for them (D-733, ADR-0061).

### 3.2 Interface artifacts and the global cache

Packages: K1 to K5b, K8.

- `ModuleInterface` (M1, B8) is written as the interface artifact: D-460's canonical encoding, now decodable, and an unhashed section of spans (D-249, D-953, ADR-0044). Warm builds check dependents against decoded artifacts only (D-954).
- One content-addressed store per machine holds blobs and records, keyed by the build ID and the settings that change code (D-255, D-956 to D-958). It lives in `CHEBY_CACHE` or the OS cache directory, with a temporary cache as the fallback (D-959). Writers rename and nothing locks, since every command is its own process (D-268, D-960). Trimming, the package index and source hashing follow D-961 to D-963.
- Early cutoff: a dependent is recompiled only when the hash of an interface it uses changes. Hidden reads of D-260 are recorded in every phase, lowering included (D-955). Diagnostics and reports are replayed from the cache (D-964, D-965).
- A module that holds a reached item is compiled whole, and reach walks cached summaries (D-966, D-967). The scope of borrowing inference, the facts and masks records and the code keys make a body edit that changes no mask recompile only its module (D-968 to D-971).
- Constants: each constant's result is a cache entry of its own, evaluated on `plain` code, and stored as an image that every run installs before `main` (D-257, D-977 to D-979). Module code reads constants only through their slots.
- Blobs and records are artifacts under D-264, compared from two paths and two caches (D-972). Cache-hit tests check what a command recompiles (D-973).

### 3.3 Cached code for `cheby run`

Packages: K4c, K4d, K7, K9.

- Machine code is cached as one code record per module, kind and settings, shared with AOT (ADR-0047). Every host loads records into cranelift-jit, so D-254's own loader is built only if loading misses OQ-P11's budget (D-914, D-974).
- Cached and AOT code bakes in layout constants from `cheby_runtime::abi`, such as the list root's length offset `abi::list::ROOT_LEN_OFFSET` (D-910). The build ID hashes `abi` and the runtime ID, so the cache key changes whenever one of them does (D-930, D-957).
- A command loads its load set in one batch before its entry runs (D-922). Changed modules are compiled eagerly and whole. D-254's lazy compilation through the indirection table is built only if CP3's reading shows code generation missing the budget (D-923).
- OQ-P11 is read with D-974's protocol on the `wide` and `deep` shapes, on GitHub's `ubuntu-24.04` runner with the Apple M3 beside it (D-1035).

### 3.4 Precompiled `std`

Package: K6.

- Std is compiled into the global cache on first use, keyed by the build ID, through the same code path as any package. A pre-filled cache and std code for other platforms are M6's packaging, which is when D-256's "ships" applies (D-936, D-980).

### 3.5 Tier-3 stdlib on native

Packages: S0 to S9, H1.

- `std::time` with its submodule `std::time::instant`, `std::net`, `std::file`, `std::http` with the new module `std::url`, and `std::process` land in D-987's order ([stdlib.md](stdlib.md#tier-3-before-m3-and-m4)). Every public function is Cheby over private `sys_` kernels, whose JS bindings are declared now (D-985, D-986).
- Sockets register on M2's `mio` poller through the seam M2 left for them. They moved here from M2's workstream 2.6 (D-680, D-681, D-984).
- `std::http` is written in Cheby over `std::net`, with `httparse` kernels for heads only, and runs each request in a scope of its own (D-1003, D-1012, ADRs 0066 and 0067). Its client speaks HTTPS through `rustls`, except on Windows until M6 (D-1011).
- File writes are unbuffered (D-994, ADR-0065). `std::process` has `exit` and `until_interrupted`, and starts no process (D-1022, D-1024, D-1073, ADR-0071).
- The first part of the standard-library additions (D-1050 to D-1079) lands in the package that owns each module (D-1054): `std::time::instant`, `until` and `sleep_until` in S1; `read_bytes`, `write_bytes` and closing sockets in S2; scratch directories, exclusive creation and the standard-stream handles in S3; `std::url`, `add_header` and the client's URL encoding in S4a; the public `fiber::cancel` and `fiber::race` in S5; `std::io`'s `Source` and `Sink` in S7 (ADRs 0069 and 0070). Two small packages take what no package owns: S8, interpolation that appends to a leading `String` (D-1055), and S9, cancellation that abandons standard input's refills (D-1065). Both parts were merged from the branch `design/stdlib` before CP1: the session's pages with `int::floor_div` (D-1056), and the tier-1 and tier-2 additions of the second part (D-1080 to D-1102) with the tier-3 modules `std::base64` and `std::hex`. T1b still reformats them with the rest of std (D-1054). Their work after M3 is in [`m4-js.md`](m4-js.md) 4.7.

### 3.6 Differential fuzzing

Package: F1.

- The programs that M2's generator produces are also compared with expected values computed by a reference evaluator for the generator's subset, in `cheby_test_support`, in every CI run and in the nightly target (D-719, D-1028).

### The M5 lane

Packages: T1, T1b, T2.

- The formatter core and `cheby new`, which [m5-tooling.md](m5-tooling.md) placed with M2 and which did not land, run beside M3. After CP2 one change formats the examples and std and adds `cheby fmt --check` to CI. The LSP core lands with M4, no earlier than CP3 (D-1029 to D-1032).

## Packages

The work is split into 53 packages in six lanes and the M5 lane: A for design, harness and verification, N for native output and foreign code, K for the cache, S for tier 3, F for fuzzing, X for the exit, and T for the M5 lane. CP1's review added two: N5's registration of type tables and hooks moved forward as N5a, with the rest of N5 as N5b, and N4b sweeps the link directories a signal leaves. A package starts once the packages it depends on are merged, and packages that own disjoint files run in parallel. Each wave gets its own plan, written before it starts, with the files each package owns, the contracts between packages of the same wave and the gate list. Sizes are XS, a function and its test, S, under a day of agent work, M, one wave, and L, more than one wave. Every package fits one wave except T1, which no critical path waits for, and K9, which runs only if a CP3 gate triggers.

The working rules carry M2's over:

- Agents draft and the user answers before anything is logged. A question that the log and the spec do not answer is answered in code with the choice most consistent with them, marked and reported, and the user reviews it at the next checkpoint before it is logged. A gap that changes language behavior stops that part of the package (D-1034).
- Zero warnings, clippy clean, no panicking code outside tests, and a true `// SAFETY:` comment on every `unsafe` block (D-422).
- No output, artifact, object or executable depends on hash-map order, thread count, timing, addresses or absolute paths. A package that creates an artifact adds it to `check-determinism` (D-264, D-551).
- Everything builds and passes clippy for both Windows targets. Tests that build or run executables carry `#[cfg_attr(windows, ignore = …)]`, as JIT tests do (D-641, D-935).
- Nothing skips a test because `libcheby_rt_exe.a` is missing. Every CI job that runs `cheby build` builds the archive first (D-929).
- Only the crates D-1036 names land without a report. Any other crate is reported at the next checkpoint.
- The orchestrator commits on `aot` once per completed wave, after the build, clippy, the formatting check and the tests pass. Nothing is pushed by an agent; the user pushes and triggers `bench.yml` (D-1035).
- From each gate on, the harnesses run strictly with an allow list of the wave's carried tests. M1 and M2 tests are never allowed to fail, and `@aot` trials are allowed only until the package that makes them pass (D-288, D-567).

## Risks

- **Loading on `deep`.** cranelift-jit declares symbols by `String`. A few hundred thousand declarations may cost tens of milliseconds and trigger our own loader (D-914).
- **OQ-P11 misses.** Lazy compilation is the largest unplanned work in M3. The CP3 reading shows it early (D-923, D-974).
- **aarch64's call range.** Direct calls inside a module use `bl`, which reaches 128 MiB. A 1M-line load set in one 1 GiB arena may place a caller and its local callee farther apart, so K4d places a record's functions together or adds veneers.
- **Cold runs get slower,** since whole modules are lowered and compiled (D-966). The cold column shows it, and it is not budgeted. At CP1 a cold `cheby check` was 32% to 102% slower than wave 1, half of it in writing two files per module. The user accepted that until CP3, where it is read again with code records and std in the cache.
- **Throughput.** D-889 reads about 90k against 100k lines per second per core, and writing artifacts adds cost. The exit reading will likely miss, and the user revises the budget from the numbers, as D-644 did.
- **D-460's encoding may not decode,** and the borrowing facts may not split per unit. Both have fallbacks (D-953, D-969).
- **A nondeterministic artifact is cached and reused.** K8's cold-against-warm comparison is the main guard, and the recorded reads of every phase close the known hole (D-955, D-972).
- **The socket seam** is a runtime prerequisite of `std::net`, `std::http` and 031, so S0 is on CP4's critical path.
- **HTTP in Cheby** is several hundred lines of new std code, whose speed is unmeasured (D-1003).
- **TLS** adds `ring`'s C and assembly build to every non-Windows runtime archive. `ring` builds in both Linux containers. Windows stays gated until M6 (D-1011).
- **Drop functions and pool threads.** A drop function that writes deadlocks if the runtime frees under a stream lock, and an abandoned job keeps running C code after a give-up. N8b and N8c verify `io.rs`, the allocator and the pool before they rely on them (D-949, D-950).
- **ld64** derives `LC_UUID` and the signature's identifier from the output's name, so the basename is an input of determinism, and `cheby build` links under the final basename (D-933, D-934).
- **A stale runtime archive** is a tool error, never a silent miscompile, through the runtime ID check (D-930).
- **E0053 under `cheby build`** opens the archive's system libraries by recorded file names. A name that drifts with a system update gives a false E0053, so N4's xtask check opens each recorded file (D-943).
- **Formatter churn.** T1b moves lines in examples, so panic-location goldens change and need a careful review.
- **Disk.** Docker volumes and caches of hundreds of megabytes on 1M-line projects. Measurement caches are deleted after each window.
- **Scope.** The S lane's tail (the HTTP server, TLS, `std::process`) is the most likely to slip. S6 and N7b can move after M3 without touching an exit criterion, if the user agrees. S3 and S7 grow with the standard-library additions (D-1054). If S7 needs more than wave 10, `until_interrupted`'s runtime half splits into a package of its own in the same wave, with the user's consent (D-1073).
- **The backtrace's walk start** is hand-written assembly per ISA. A wrong register gives a wrong or empty backtrace, never a crash, since the walk checks every frame pointer against the fiber's stack (D-856). Windows x64 needs its own stub in M6.

## Exit criteria

M3 is judged on macOS arm64, Linux x86-64 and Linux arm64 (D-935). Every criterion is checked with `CHEBY_MILESTONE=M4`, so the tests of M3 count as required before `tests/milestone` is bumped (D-544).

- Every example that passes on the JIT also passes as an executable from `cheby build --target native`, through its `@aot` trial (D-1025).
- 020 and 031 pass, against the harness's local fixtures: 020's own C code and the HTTP fixture (D-952, D-1027). 031 imports `std::http`, so it is checked from this milestone (D-477). 030 needs its git dependency too, so it moves to M5 (D-446).
- After a one-function edit in the 1M-line `bench/gen` projects, `cheby run` reaches `main` within the D-247 latency budget, as revised by OQ-P11, on the CI reference machine, GitHub's `ubuntu-24.04` runner, with the Apple M3 reported beside it. OQ-P11 is read as D-974 says and settled (D-1035).
- Checking with code generation is measured again against D-247's 100,000 lines per second per core, on the `bench/gen` shapes of M1's measurement, by the same runner, in memory without the cache (D-975). Like every budget it stays reported, not enforced, until M6 (D-644).
- Two builds of the same inputs produce bit-identical artifacts and executables: the cache's blobs and records, and executables with the same basename (D-264, D-934, D-972).
- Editing a function body recompiles only its module, and the modules of its package that call a function whose borrow mask the edit changed (D-812), checked by a cache-hit test (D-973).
