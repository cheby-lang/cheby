# M5: Tooling

Goal: `cheby fmt`, `cheby lsp`, `cheby doc` and the package manager, all part of v1 (D-031). This work grows alongside M2 to M4 (D-099, step 5). M5 is the point where it is complete, not where it starts.

Detail level: workstreams with the milestone each slice lands next to.

The formatter core, the LSP core and `cheby new` were placed with M2 and did not land. The formatter core and `cheby new` run beside M3 in a lane of their own, as packages T1, T1b and T2 of [m3-aot-and-cache.md](m3-aot-and-cache.md). M3's second checkpoint chose the line width, 100 columns (D-1252), and in M3's ninth wave one change formatted `docs/examples/**/src` and `std/`, updated the goldens whose locations moved after a review by eye, and added `cheby fmt --check` to CI, with the layout changes of D-1274 to D-1276. Files written later are formatted by their authors. The LSP core sits on the driver's front-end APIs, which M3's cache rewrites, so it lands with M4, starting no earlier than M3's third checkpoint. LSP navigation and constant evaluation move behind it, and the protocol's open questions are settled in its own design step then (D-1029).

## Exit criteria

- Every example and every `std` source is a fixed point of `cheby fmt`, and the formatter passes the idempotence and meaning-preservation tests ([testing.md](testing.md#3-unit-and-property-tests)).
- The language server answers every request of §13.11 on all examples. When no file of a package has a phase-A error, its published diagnostics equal `cheby check`'s. E0069 and E0075 to E0078 arrive when the constants child finishes, are absent on Windows until M6, and are absent while a run is cut short by a new save, by `constants.childTimeoutSeconds` or by the 64 MiB limit on its stdout. When a file has a phase-A error, that file shows exactly its phase-A diagnostics, and other files follow D-1347.
- A package with git dependencies on two majors of one repository builds from its lockfile, and a checksum mismatch fails the build. `dyn` of an empty `List<T>`, a `List<dyn I>`, values with fields of different kinds and an external type of two packages of one `name` compare False (D-1313).
- 030 passes, with its git dependency served from a local fixture repository and its HTTP fixture started by the harness (D-446). The fixture repository has a stable URL that is not a `file://` path, so locations in the goldens contain no absolute path (D-468).
- `cheby doc` output for `std` matches `docs/stdlib/` module by module (D-220).
- All doc examples in `std` pass `cheby test`.

## Status

In progress. The formatter core and `cheby new` landed with M3. `cheby lsp`, `cheby doc`, `add`, `update` and `fetch` are still stubs, and doc examples are not run as tests.

The language server's design is logged: D-1347 to D-1426 in the [language server](../decisions/LOG.md#2026-11-07-the-language-server) session, ADRs 0076 to 0078, and §13.8, §13.11 and §13.11.1 of the spec. That session is the design step of D-1029, and D-1353 and D-1426 set the scope that the slices above list. The exit criterion on the server's diagnostics is D-1348's, which names `cheby check`, not `cheby build`.

The server is built in waves on the `lsp` branch, one commit per wave (D-1354). The first wave is this text and changes no code. The user reviews three checkpoints, each with a recorded session in Zed: after the protocol skeleton, after constant evaluation and after the memory marks. `tests/milestone` stays `M4` throughout, and the LSP harness fails CI from the day its tests land (D-1352).
