# 12. Targets and FFI

A Cheby program can be compiled for two families of targets: **native** code through Cranelift, and **JavaScript** (D-006). Both are compiled from the same mid-level IR (D-019). This chapter defines what each target supports, where their semantics differ, and how Cheby code calls foreign code.

## 12.1 Targets

A **target** is either `native` or `js`. These two names are used in `@external` and `@target` attributes ([§12.5](#125-foreign-functions), [§12.6](#126-target-specific-code)).

| Target   | Output                                                                               | Platforms                                                                           | Debug info           |
| -------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- | -------------------- |
| `native` | JIT code (REPL, `cheby run`) or object files linked into an executable (AOT) (D-007) | 64-bit macOS on aarch64, and Linux and Windows on x86_64 and aarch64 (D-074, D-892) | DWARF (D-074, D-184) |
| `js`     | ES modules                                                                           | Node, Deno, Bun and browsers (D-074)                                                | source maps (D-074)  |

32-bit native platforms are not supported, because fiber stacks rely on large virtual-memory reservations (D-124, ADR-0032).

There are no operating-system targets in v1: `native` covers macOS, Linux and Windows alike, and there is no `@target(windows)` or similar (D-214, ADR-0039). The standard library and runtime hide operating-system differences. Foreign code that exists only on some operating systems must handle its own portability, typically with a small C shim that is linked on every native platform.

Native debug info is DWARF on every platform in v1, including Windows. CodeView/PDB is added when the bundled linker lands ([§13.1](13-tooling.md#131-the-cheby-command)) (D-184, D-088). By default only line tables are emitted, for debuggers and profilers, and full debug info is opt-in ([§13.12.5](13-tooling.md#13125-build-profiles)) (D-259). The panic backtrace of [§11.6](11-errors-and-panics.md#116-panic-and-todo) needs no debug info (D-939).

_Note:_ the reference implementation writes line tables into the object file of every Cheby module it links (D-1172). Linux executables keep them. Until the bundled linker, macOS executables are linked without a debug map, which would name the link's temporary object files by absolute path, so debuggers find no line tables in them there (D-264, D-938).

## 12.2 Native

Native code is generated by Cranelift, either in-process by the JIT or as object files for ahead-of-time builds (D-007, D-019). There is no interpreter tier (D-019, ADR-0009).

- Tail calls use Cranelift's `tail` calling convention and `return_call` (D-015, ADR-0006). A tail call from code outside `std` to a wait of `std` that calls no function value, such as `channel::send`, `channel::receive`, `fiber::join` or `time::sleep`, is a call followed by a return instead, so a deadlock report finds its caller ([§5.15.3](05-expressions.md#5153-guaranteed-tail-calls)) (D-861, D-1059).
- Each function begins with a combined yield and stack-limit check ([§10.2](10-concurrency.md#102-scheduling), [§11.8.1](11-errors-and-panics.md#1181-stack-overflow)) (D-028, D-124).
- Panics and cancellation unwind by propagating a flag through returns ([§11.3](11-errors-and-panics.md#113-unwinding)) (D-733).
- Executables are linked with the system linker in early versions, and with a bundled linker before 1.0 (D-088).

## 12.3 JavaScript

The JS backend emits ES modules (D-006, D-074).

### 12.3.1 Fibers on JS

JavaScript has no stackful coroutines. The compiler performs a whole-program **suspension analysis** that finds every function that can transitively reach a suspension point: channel operations, scope waits, joins, IO, timers, `fiber::yield_now` and yield checks (D-014, ADR-0005, D-1102). Only those functions are compiled to generator functions, and calls between them become delegated yields. All other functions compile to plain JS functions.

- The coloring is internal to the generated code. Cheby source never shows it (D-003).
- Calls through function values and `dyn` interface values are treated conservatively: if any function that could be called there may suspend, the call site is compiled as suspending (ADR-0005).
- JS builds therefore require a whole-program step (ADR-0005). It runs at link time: each module exports a small summary of which functions suspend directly and its call edges, the link step computes which functions suspend transitively, and JS code is generated and cached per function, keyed on the function's IR and whether it suspends. An edit regenerates only the functions whose suspension status changed ([§13.12.3](13-tooling.md#13123-interface-artifacts-and-recompilation)) (D-258, ADR-0048).
- The runtime schedules fibers cooperatively on the single JS thread. Parallelism is not available on JS; concurrency semantics are otherwise the same as on native.

The JS backend inserts no yield checks at function entry, because they would make almost every function suspending and defeat the suspension analysis (D-185, ADR-0035). A fiber on JS runs until its next real suspension point, so a CPU-bound fiber can starve other fibers. Timeouts, timers and cancellation therefore take effect only at that suspension point (D-232). This is a documented difference between targets ([§12.4](#124-semantic-differences-between-targets)).

### 12.3.2 Tail calls on JS

Only some JS engines implement proper tail calls. The JS backend therefore compiles self tail calls to loops, and all other tail calls to trampolines (D-015, ADR-0006). The guarantee of [§5.15.3](05-expressions.md#5153-guaranteed-tail-calls) holds on JS too; the cost is some performance on non-self tail calls.

### 12.3.3 Values on JS

| Cheby                | JS representation (informative)                   |
| -------------------- | ------------------------------------------------- |
| `Int`                | number, checked to the safe-integer range (D-037) |
| `I64`, `U64`         | `BigInt`, checked to the type's range (D-106)     |
| other sized integers | number, checked to the type's range               |
| `Float`              | number                                            |
| `F32`                | number, rounded with `Math.fround`                |
| `String`             | string (D-038)                                    |
| `Bool`               | boolean                                           |
| `Nil`                | `undefined`                                       |

The handles of the concurrency modules, `Sender`, `Receiver`, `Fiber`, `Scope` and `Selector`, are external types ([§12.5.3](#1253-external-types)), so they are reference-counted on JS like any handle, and so is every value that can hold one ([§9.8](09-memory-model.md#98-memory-on-the-js-target)). A selector that holds the last `Receiver` of a channel therefore releases it when `select` returns, as on native (D-100, D-647).

The representation of ADTs, tuples, lists, maps, closures, `dyn` values, type descriptors and the function packages passed for bounds is unspecified. Type descriptors are nevertheless the same as on native, so `Int`, `I64`, `F32` and `Float` stay distinct inside `dyn` values ([§8.6.1](08-interfaces.md#861-type-descriptors)) (D-237). FFI code must only rely on the representations listed here and on values passed through as opaque ([§12.5](#125-foreign-functions)).

## 12.4 Semantic differences between targets

A program whose result does not depend on timing or scheduling order computes the same result on every target (D-232). Every failure that happens only on JS is a **panic on JS where native succeeds**, never a different value. Timing, scheduling and liveness may differ between targets, because JS fibers are not preempted (D-185).

| Difference                        | Native                                 | JS                                                                                                        | Decision            |
| --------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------- |
| `Int` range                       | 64-bit, panics on overflow             | panics outside ±(2⁵³−1)                                                                                   | D-037, ADR-0017     |
| Non-tail recursion depth          | limited by a large fiber stack         | limited by the engine, roughly ten thousand frames                                                        | D-094               |
| Parallelism                       | fibers run in parallel on many threads | fibers interleave on one thread                                                                           | D-012               |
| Preemption                        | yield check at every function entry    | only at real suspension points, so a CPU-bound fiber can starve others or keep the program from finishing | D-028, D-185, D-232 |
| Timeouts, timers and cancellation | take effect at the next function entry | take effect only at the fiber's next real suspension point                                                | D-103, D-185, D-232 |
| `Map`/`Set` iteration order       | random per process                     | random per process                                                                                        | D-093               |

The `Int` range and recursion depth rows are the failures that happen only on JS, and both are panics. The parallelism, preemption and timeout rows affect only timing, scheduling and liveness. On JS a CPU-bound fiber holds the thread until its next real suspension point, so a timeout cannot interrupt it, and `fiber::timeout` may return `Ok` after its deadline ([§10.8](10-concurrency.md#108-timeouts)). A program that needs a timeout to bound CPU work on JS must put suspension points in that work, such as calls of `fiber::yield_now` (D-232, D-1102).

Memory management differs in mechanism but not in observable behavior: handle drop functions and channel closing happen at the same points on both targets ([§9.8](09-memory-model.md#98-memory-on-the-js-target), D-100).

## 12.5 Foreign functions

```ebnf
external_attr = "@external" "(" target "," STRING [ "," STRING ] [ "," ] ")" ;
target        = "native" | "js" ;
```

A function declared without a body, with one or more `@external` attributes, is implemented in foreign code (D-030):

```cheby
@external(native, "cheby_sqlite_open")
@external(js, "./sqlite.mjs", "open")
@blocking
priv fn open_raw(path: String) -> Db

@external(native, "cheby_sqlite_open_error")
@external(js, "./sqlite.mjs", "openError")
priv fn open_error(db: Db) -> Option<String>

/// Opens the database at `path`.
pub fn open(path: String) -> Result<Db, String> {
  let db = open_raw(path)
  case open_error(db) {
    None => Ok(db)
    Some(message) => Err(message)
  }
}
```

Here `open_raw` and `open_error` are foreign functions, and `open` is ordinary Cheby code over them. Native foreign code returns a value of an external type such as `Db` only as a function's direct result, never inside a `Result` or an `Option`, so the Cheby wrapper builds the `Result` ([§12.5.1](#1251-native-abi)) (D-948).

- `@external(native, "symbol")` binds to a C-ABI symbol, linked into the program (D-030).
- `@external(js, "module", "name")` binds to the named export of an ES module. A relative module path is resolved against the Cheby source file's location (D-030).
- There may be at most one `@external` per target. A function with an `@external` for only some targets exists only on those targets, as if it had `@target` ([§12.6](#126-target-specific-code)).
- A function with a body may also have an `@external` for some target. The foreign implementation is used on that target and the body on the others. The body is checked as code restricted to the targets that have no `@external`, so it may use items marked `@target` for those targets ([§12.6](#126-target-specific-code)) (D-207).
- A relative module path in `@external(js, "./…", …)` names a file next to the source, usually under `src/`. Such files are not modules and are exempt from the file naming rule, and a JS build copies each of them into its output at the same location relative to the compiled module ([§7.2](07-modules-and-packages.md#72-modules-and-files)) (D-208).
- The declared Cheby signature is trusted. The compiler cannot check it against the foreign code, so a wrong signature is undefined behavior on native.
- Foreign functions may be generic, as in Gleam. Values cross the boundary in the uniform representation, so values whose type is a type parameter are passed as opaque references (D-186).
- In v1, the type parameters of a foreign function must not have bounds, because function packages and type descriptors have no foreign ABI. This also applies to a function that has a body and an `@external` for some targets (D-207), because the foreign implementation receives the same arguments. Such a bound is a compile error at the bound (D-554). Foreign code cannot build or inspect `dyn` values: they cross the boundary only as opaque values ([§12.5.1](#1251-native-abi), [§12.5.2](#1252-js-abi)) (D-237).

- Compile-time constant evaluation cannot call foreign functions, except the standard-library kernels that [§4.5](04-declarations.md#45-constants) lists (D-090, D-360, D-537).
- A constant's initializer is not target-checked and runs on the host, so a constant that exists on `js` may reach a function whose only implementation is `@external(js, …)`. On the native host this is the same compile error as reaching any other foreign function, and its note names the function's path. Checked native code never reaches such a function, because the cross-target check keeps it from calling it (D-591).

Native symbols follow three rules (D-455):

- Every symbol that an `@external(native, …)` of a reached function names, or of the drop function of a reached external type, must be defined when the program is loaded or linked. It may be defined by the Cheby runtime, by the package's native code or a library its `[native]` table names ([§12.5.4](#1254-native-code-in-packages)), or by the system libraries that every program links. Under `cheby run`, `cheby test` and the REPL, which run code in the `cheby` process, the process itself counts too (D-941, D-943). A function or type is reached when the `main` being run or built, a selected test or a REPL entry can use it, as code generation decides it (D-510). Otherwise running or building the program is a compile error at the `@external`, even if the reached function is never called at run time. The same rule decides for `cheby run`, `cheby test` and `cheby build`, before anything runs or is linked, and never from a linker's messages (D-943). Every missing symbol is reported, one error each, in the order of the `@external`s that name them (D-532). A missing symbol that only unreached functions name is not an error. `cheby check` does not report it, because which symbols exist is known only at load or link time. When `cheby check` evaluates constants, a missing symbol is bound to a stub, and only a constant whose evaluation calls the stub is an error, like any forbidden effect during evaluation ([§4.5](04-declarations.md#45-constants)) (D-532).
- All `@external(native, …)` attributes of a program that name the same symbol, in any module or package including the standard library, must give it the same C signature ([§12.5.1](#1251-native-abi)). In the REPL, the program is the session's current definitions ([§13.5.2](13-tooling.md#1352-redefinition)) (D-475).
- Symbols that start with `cheby_rt_` or `cb$`, and every other symbol that the runtime exports, belong to the runtime and to generated code. Outside the standard library, an `@external(native, …)` must not name them, and a package's native code must not define them, which is a tool error before anything is linked or loaded (D-944). Other names that start with `cheby_`, such as `cheby_sqlite_open`, stay free.

_Note:_ the reference implementation compiles every function of a module that the program reaches, so a module's code may name a missing symbol that only unreached functions use. It binds such a symbol to a stub of the runtime, which reach guarantees is never called (D-943, D-966). The `cheby` process may also define symbols, such as those of the toolchain's own libraries, that an executable does not link, so `cheby run` can accept a symbol that `cheby build` reports.

_Note:_ the reference implementation compiles each native external to an ordinary Cheby function that makes the foreign call, so callers call it like any other function, and whether a function is external is not part of its module's interface (D-455).

### 12.5.1 Native ABI

On native targets, foreign functions use the C ABI of the platform (D-030). Parameter and return types are mapped as follows:

| Cheby                                            | C                                                       |
| ------------------------------------------------ | ------------------------------------------------------- |
| `I8` … `I64`, `U8` … `U64`                       | `int8_t` … `int64_t`, `uint8_t` … `uint64_t`            |
| `Int`                                            | `int64_t`                                               |
| `F32`, `Float`                                   | `float`, `double`                                       |
| `Bool`                                           | `bool`                                                  |
| `Nil` (return only)                              | `void`                                                  |
| external types ([§12.5.3](#1253-external-types)) | a pointer                                               |
| any other type                                   | an opaque, reference-counted pointer to the Cheby value |

Values such as `String`, `Bytes`, `List` and `Result` cross the native FFI as opaque pointers. The toolchain provides a C header, `cheby.h`, with functions to inspect and build Cheby values and to increment and decrement their reference counts, which a package's C sources include ([§12.5.4](#1254-native-code-in-packages)). The runtime representation itself stays private (D-187). The header declares the opaque type `cheby_value` and these functions, all named with the prefix `cheby_ffi_` (D-945):

| Function                                                                                                                                            | Purpose                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `cheby_value *cheby_ffi_dup(cheby_value *v)`                                                                                                        | adds a reference to `v` and returns it                                                       |
| `void cheby_ffi_drop(cheby_value *v)`                                                                                                               | releases a reference                                                                         |
| `cheby_value *cheby_ffi_string_new(const char *bytes, size_t len)`                                                                                  | a new `String`, with invalid UTF-8 replaced by U+FFFD (D-311)                                |
| `const char *cheby_ffi_string_bytes(cheby_value *s, size_t *len)`                                                                                   | a `String`'s UTF-8 bytes, not NUL-terminated, valid while `s` is held                        |
| `cheby_ffi_bytes_new`, `cheby_ffi_bytes_data`                                                                                                       | the same for `Bytes`                                                                         |
| `cheby_ffi_int_new`, `cheby_ffi_int_get`, `cheby_ffi_float_new`, `cheby_ffi_float_get`, `cheby_ffi_bool_new`, `cheby_ffi_bool_get`, `cheby_ffi_nil` | scalars in generic positions, such as the elements of a list                                 |
| `cheby_ffi_some`, `cheby_ffi_none`, `cheby_ffi_option_get`                                                                                          | build an `Option`, or read its payload, which is NULL for `None`                             |
| `cheby_ffi_ok`, `cheby_ffi_err`, `cheby_ffi_result_is_ok`, `cheby_ffi_result_get`                                                                   | build a `Result`, or read which variant it is and its payload                                |
| `cheby_value *cheby_ffi_list_new(cheby_value **items, size_t n)`, `cheby_ffi_list_length`, `cheby_ffi_list_get`                                     | build a `List` from its elements, or read its length and an element                          |
| `int cheby_ffi_write_stdout(const char *bytes, size_t len)`, `cheby_ffi_write_stderr`                                                               | one write to standard output or standard error, returning `0`, or `-1` when the write failed |

The header has no functions for user-defined types, tuples, maps, `dyn` values, type descriptors or the function packages passed for bounds, so those values stay opaque (D-187, D-237, D-945). Later versions of the header only add functions (D-945).

Ownership follows one convention (D-187):

- Arguments are borrowed for the duration of the call. Foreign code that keeps a reference after returning must increment its reference count.
- Return values are owned by the caller. The foreign function transfers one reference to Cheby.
- The same holds for the functions of `cheby.h`, and a function of `cheby.h` that takes a payload, such as `cheby_ffi_some` or `cheby_ffi_list_new`, takes ownership of it (D-945). Values that a function of `cheby.h` reads out, such as an element or a payload, are borrowed from the value they were read from.

The functions of `cheby.h` follow these rules (D-945, D-946):

- Passing a value of another type than a function expects is undefined behavior, as a wrong `@external` signature is. Runtimes built with debug assertions check it and stop with a fatal runtime error.
- A NULL argument means no value. Functions that read return NULL or zero for it, and `cheby_ffi_drop` does nothing.
- A function of `cheby.h` that cannot allocate returns NULL. When the foreign function then returns, Cheby releases its result if it is not NULL and panics with `out of memory` ([§11.8.2](11-errors-and-panics.md#1182-out-of-memory)). Inside a drop function, the failure is a fatal runtime error instead ([§9.5](09-memory-model.md#95-handles-and-drop-functions)) (D-642, D-946).
- A function of `cheby.h` finds the running fiber itself, so foreign functions receive no context argument (D-946).
- `cheby_ffi_write_stdout` and `cheby_ffi_write_stderr` write their bytes at once, in order with the program's other output and inside `cheby test`'s capture of each test's output. Output that foreign code writes through C's own `stdio` has no such guarantee ([§10.10](10-concurrency.md#1010-program-entry-and-exit)) (D-951).

Results of foreign functions follow two more rules:

- A foreign function whose result type is an external type returns its handle, which Cheby wraps as a value of that type even when it is NULL. The type's drop function is never called with NULL ([§12.5.3](#1253-external-types)). A foreign function whose result type is any other type that is passed as a pointer must not return NULL: if it does, the call panics with ``foreign function `<symbol>` returned null``, located at the `@external` function's declaration ([§11.6](11-errors-and-panics.md#116-panic-and-todo)) (D-947).
- Native foreign code returns a value of an external type only as the function's direct result. Outside the standard library, an `@external(native, …)` whose result type holds an external type below its top level, such as `Result<Db, String>` or `Option<Db>`, is a compile error at the `@external`, because C code has no way to build such a value. Parameters may hold external types at any depth, as opaque values. A type parameter that a call instantiates with an external type is not checked (D-948).

### 12.5.2 JS ABI

On JS, arguments and results use the representations of [§12.3.3](#1233-values-on-js). Other values are passed as opaque JS values that the foreign code must not inspect or modify, except through helper functions exported by the Cheby JS runtime.

A JS foreign function declared with the ordinary `@external` form that returns a `Promise` is not awaited automatically: the `Promise` is the result.

The `@async` attribute marks a JS external as **asynchronous**, returning a `Promise` (D-188, D-200). It is allowed only on functions that have an `@external(js, …)` attribute, and it does not affect the native implementation. Its declared Cheby return type is the type of the resolved value. A call to an asynchronous external:

- is a suspension point, so the calling function is suspending for the analysis of [§12.3.1](#1231-fibers-on-js) (D-014),
- suspends the calling fiber until the `Promise` settles, while other fibers run,
- resumes the fiber with the resolved value if the `Promise` fulfills,
- panics the fiber if the `Promise` rejects.

Callers see an ordinary function call, because fibers hide the asynchrony (D-003). For example:

```cheby
@external(js, "./http.mjs", "fetchText")
@async
fn fetch_text(url: String) -> String
```

### 12.5.3 External types

A type declaration with no body declares an **external type**, whose values are foreign handles. It needs no `@external` attribute (D-491):

```cheby
@external(native, "cheby_sqlite_close")
@external(js, "./sqlite.mjs", "close")
pub type Db
```

- An external type has no constructors and no fields. Its values can only be created and inspected by foreign functions. Native foreign code creates one only as a function's direct result ([§12.5.1](#1251-native-abi)) (D-948).
- An `@external` on an external type names its **drop function** for that target, which is called with the handle when the last reference to it goes away (D-101, [§9.5](09-memory-model.md#95-handles-and-drop-functions)). Without one, the handle is simply forgotten. The exception is the handles of the standard library: `Sender`, `Receiver`, `Fiber`, `Scope` and `Selector` of the concurrency modules, `File` of `std::file`, and `Listener` and `Connection` of `std::net`. They are declared without an `@external`, and their drop functions are supplied by the runtime (D-647, D-703, D-982).
- A native drop function is a C function `void f(void *handle)`. It is called once, on the fiber that released the last reference, never with a NULL handle, and under the contract of [§9.5](09-memory-model.md#95-handles-and-drop-functions) (D-949).
- External types have no structural equality and do not compare by identity, because identity differs between targets. `==` or hashing on a value that contains an external type panics, like function values (D-070, D-189, D-233). A value of an external type debug-prints as its type name in angle brackets, such as `<Db>` (D-233).
- External types are handle types for reference counting on every target, including JS (D-100, ADR-0028).

### 12.5.4 Native code in packages

A package supplies the native code that its `@external(native, …)` functions name with the optional `[native]` table of its manifest ([§13.3](13-tooling.md#133-manifest)) (D-940):

```toml
[native]
sources = ["src/sqlite_ffi.c"]
libraries = ["sqlite3"]
```

- `sources` lists C source files by their paths relative to the package root. Each must end in `.c`, must name a file that exists, and must stay inside the package once `..` and symbolic links are resolved (D-1200). A C file may sit under `src/` next to the module that binds it, and it is not a module ([§7.2](07-modules-and-packages.md#72-modules-and-files)).
- `libraries` lists system libraries by the name that the linker takes after `-l`, such as `sqlite3` for `-lsqlite3`. Each is a non-empty string of ASCII letters, digits, `_`, `-`, `.` and `+`.
- The table has no other keys. A violation of these rules is a compile error, like every error in the manifest, and so is a `[native]` table in a package whose `targets` leave out `native` (D-444, D-940).
- Every command checks the table, but only the commands that run or link native code compile the C sources. `cheby check` compiles none (D-532, D-941).
- There are no build scripts, no prebuilt archives and no source languages other than C. Each package's C sources are compiled in that package, dependencies included (D-940).
- A C source includes `cheby.h` to build and inspect Cheby values ([§12.5.1](#1251-native-abi)) (D-945).

The package's native code is part of the program wherever the program runs. An executable links the package's compiled C sources and its `libraries`. `cheby run`, `cheby test` and the REPL run code in the `cheby` process, so they load the same compiled sources and `libraries` as a shared library, and the symbols it defines count for the rules of [§12.5](#125-foreign-functions) as they do in an executable (D-941). A REPL `:reload` that finds a changed C source loads its new code, and code compiled before keeps calling the old ([§13.5.3](13-tooling.md#1353-commands)) (D-712, D-941).

_Note:_ the reference implementation compiles each C source once, with the package root as the working directory, the environment variable `SOURCE_DATE_EPOCH` set to `0`, and fixed flags, so the object holds no path of the machine (D-942):

```sh
cc -c -O2 -fPIC -g0 -ffile-prefix-map=<package root>=. -ffile-prefix-map=<header dir>=cheby -I<header dir> -o <object> <source>
```

The compiler's output is shown only when it fails, which is a tool error that names the source. Compiled objects are cached, keyed by the source, the C compiler, the flags, `cheby.h` and every file the compile read (D-942). Under `cheby run`, each package with a `[native]` table becomes one shared library, built with `cc -shared -Wl,-z,defs` on Linux and `cc -dynamiclib` on macOS from the package's objects, its `libraries` and a small object that forwards the calls of `cheby.h` to the running `cheby`. It is loaded with `dlopen` and never unloaded (D-941). Until M6, on Windows, every command that would compile or load native code refuses a table that names sources or libraries with a tool error that says it is not available yet (D-1202).

## 12.6 Target-specific code

`@target(native)` or `@target(js)` on an item makes it exist only when compiling for that target (D-056):

```cheby
@target(native)
pub fn read_file(path: String) -> Result<String, io::Error> { … }
```

- An item with `@target(t)` is type-checked on every build, but compiled only for target `t`.
- Code that uses a target-specific item must itself be restricted to the same target, directly or through its callers. The compiler checks this and reports any use that would fail on some target, even when building for a target where it would work (D-056).
- The check reports each pair of a using item and a used top-level item once, at the first use, with uses in the signature before uses in the body. A use of a constructor counts as a use of its type, and a use of an interface function as a use of its interface (D-512).
- A constant's declared type is checked against the constant's targets. Its initializer is not, because it runs at compile time on the host ([§4.5](04-declarations.md#45-constants)) (D-090, D-512).
- Every item must exist on at least one target. An item whose `@target(t)` contradicts its module's `@!target`, and a function without a body that `@target(t)` or its module's `@!target(t)` restricts to a target `t` for which it has no `@external`, are compile errors (D-513).
- The body of a function that has an `@external` for some targets counts as restricted to the remaining targets, because it only runs there (D-207). This is how a function is written as "foreign code on one target, Cheby on the other":

```cheby
/// Returns a random number from 0 up to but not including `bound`.
@external(native, "arc4random_uniform")
priv fn below(bound: U32) -> U32 {
  // Runs only on JS, so it may call the JS-only `js_random`.
  let assert Ok(whole) = float::truncate(js_random() * float::from_u32(bound))
  let assert Ok(number) = u32::from_int(whole)
  number
}

@target(js)
@external(js, "./random_ffi.mjs", "random")
priv fn js_random() -> Float
```

- A whole module is restricted to a target with the inner attribute `@!target(t)`, written before the module's first item. It applies `@target(t)` to every item of the module (D-141).

A package may declare the targets it supports with the optional `targets` field in `cheby.toml` ([§13.3](13-tooling.md#133-manifest)), which defaults to both targets. The cross-target check of the second bullet covers only the declared targets, so a package that supports only `native` gets no errors for uses that would fail on `js` (D-190). `cheby check --target t` narrows it further to the one target `t` ([§13.1](13-tooling.md#131-the-cheby-command)) (D-550).

## 12.7 Blocking foreign calls

`@blocking` on an `@external` function marks it as possibly blocking the OS thread for a long time (D-042). On native targets, a call to it moves to the runtime's blocking thread pool, and the calling fiber is suspended until it returns ([§10.9](10-concurrency.md#109-blocking-io)). The call cannot be interrupted: a cancellation of the calling fiber is delivered when the call returns, and its result is then released ([§10.7](10-concurrency.md#107-cancellation)) (D-670, D-683). Without `@blocking`, a foreign call runs directly on the fiber's thread and should return quickly (D-042).

`@blocking` has no effect on JS.

A `@blocking` foreign function of a package runs on the pool as the standard library's do (D-950):

- It may use `cheby.h` ([§12.5.1](#1251-native-abi)) as any foreign function may. The values it builds belong to the calling fiber, which stays suspended until the call returns. An allocation that fails is raised as the `out of memory` panic on the fiber when it resumes.
- When the calling fiber was cancelled during the call, the fiber releases the call's owned result when it resumes, and then unwinds. A result of an external type is wrapped first, so its drop function runs on the fiber ([§9.5](09-memory-model.md#95-handles-and-drop-functions)) (D-171).
- A call that the runtime abandons, because it gave up waiting for the pool or because the program ends, keeps running on its thread. From then on its calls of `cheby.h` that allocate return NULL, `cheby_ffi_drop` does nothing and the output functions return `-1`. Its result is never released, and its borrowed arguments stay readable until the process exits ([§10.10](10-concurrency.md#1010-program-entry-and-exit)) (D-815, D-950).

_Note:_ no Cheby code runs on the pool's threads (D-191), so the reference implementation calls a `@blocking` function there through a generated shim that takes the arguments as machine words and returns the result widened to one word (D-818). While the call runs, the pool thread acts for the parked fiber, so the functions of `cheby.h` charge what they build to the fiber's memory (D-950). When the pool cannot take the call, as when the system refuses it a thread, the reference implementation runs the call on the fiber's own thread instead and blocks that thread ([§10.9](10-concurrency.md#109-blocking-io)) (D-815, D-817).

## 12.8 Tail calls

The tail-call guarantee ([§5.15.3](05-expressions.md#5153-guaranteed-tail-calls)) does not cover calls to foreign functions, nor calls from foreign code back into Cheby. A tail call to a foreign function compiles to an ordinary call.

## 12.9 Callbacks from foreign code

On JS, foreign code may call Cheby functions, for example as event handlers. Each such call runs in a new detached fiber ([§10.4](10-concurrency.md#104-detached-fibers)), so the foreign caller does not wait for its result (D-191).

On native targets, calls from foreign code back into Cheby are not supported in v1, because a foreign thread that calls in has no fiber or scheduler context (D-191).
