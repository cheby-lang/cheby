# E0038: construct the compiler does not support yet

No current toolchain emits this code. It reports an import of a standard-library module that the specification or the stdlib plan defines but the toolchain does not ship yet, and since `std::log` shipped, no module is planned: the toolchain ships every module that the stdlib pages describe (D-989, D-1633). The rule stays in the compiler for a later tier that plans a module before it ships, and unit tests with a made-up planned module keep it tested (D-1296).

Such an import is not an error in your program (D-451). It is reported once, at the import, and nothing that goes through the import is checked, so it causes no follow-up errors. It is not an unresolved import (E0039), and paths through it, such as `log::info`, report nothing more (D-480). An example that imports a planned module expects this error until the milestone that ships the module (D-477).

The modules shipped in steps. M2 shipped the six tier-2 modules, such as `std::selector` and `std::random`, and the seven tier-1 collections `std::multimap`, `std::sorted_*` and `std::ordered_*` (D-645, D-664). M3 shipped tier 3 whole: `std::time`, `std::net`, `std::file`, `std::url`, `std::http`, `std::base64`, `std::hex` and `std::process` (D-985, D-989). Tier 4's `std::context` and `std::log` shipped on native before M4's JS runtime (D-1049, D-1563, D-1614). Until then, `std::log` was the last planned module, and the toolchain's own probes imported it (D-1213, D-1575).

`cheby check`, `cheby run` and `cheby test` report it the same way, before any code is compiled. The back end does not emit E0038: since M1, MIR lowering compiles every construct the front end accepts, and a construct it could not compile would be an internal compiler error, not this code (D-554). Earlier M1 builds reported E0038 from `cheby run` for constructs such as `case`, closures and constants that the back end did not compile yet (D-510); none is left.

Example, from a toolchain before `std::log` shipped, which reported E0038 at the import and nothing for the paths through it. A current toolchain checks and runs it:

```cheby
//! Needs a planned module.

import std::io
import std::log

fn main() {
  log::info("started")
  io::println("done")
}
```

There is nothing to fix in the program. The code is temporary: a toolchain that ships every planned module does not emit it, and this file stays to say so (D-419, D-451, D-480).

Types that nothing in a function body fixes, such as the element type of `let xs = []`, are E0057, and a function used on a target where it does not exist is E0067. A name missing from a shipped standard-library module is E0042. All three were reported with this code in early M1 builds (D-480). A bound on a type parameter of a foreign function is E0045 (D-554).
