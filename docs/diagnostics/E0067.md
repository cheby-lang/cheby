# E0067: use of an item that does not exist on every target the using code runs on

An item marked `@target(native)` or `@target(js)` exists only on that target, and so does every item of a module marked `@!target(…)` (§12.6, D-056, D-141). A function without a body exists only on the targets of its `@external` attributes. Code that uses such an item must itself be restricted to the same targets, directly or through its callers. The compiler checks this on every build, for every target the package declares in `cheby.toml` (D-190), even when building for a target where the use would work. It reports each pair of a using item and a used item once, at the first use, and a use of a constructor counts as a use of its type (D-512). A constant's initializer runs at compile time, so only its declared type is checked (D-512).

The body of a function that has an `@external` for some targets runs only on the other targets, so it may use items of those targets (D-207).

REPL entries run on the native JIT, so they are checked for `native` only, whatever targets the package declares. In a package for `js` only, an item that exists only on `js` is this error at the prompt, as in "`alert` exists only on `js`, but the entry runs on `native`" (§13.5.1, D-628).

Example:

```cheby
@target(native)
fn read_config() -> String {
  "native settings"
}

pub fn settings() -> String {
  read_config()
}
```

`settings` exists on both targets, but `read_config` only on native. Restrict the caller as well, or declare `targets = ["native"]` in `cheby.toml` if the package supports only native:

```cheby
@target(native)
fn read_config() -> String {
  "native settings"
}

@target(native)
pub fn settings() -> String {
  read_config()
}
```
