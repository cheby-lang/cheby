# cheby_link

AOT object output and linking: what `cheby build` does after code generation. It replays the code records that `cheby_codegen_clif` captures (D-914) into relocatable objects (D-915), writes the program object, finds and checks the runtime archive (`cheby_rt_exe`, D-929, D-930), and links everything into an executable with `cc` (D-933).

## Place in the pipeline

`cheby_link` depends on `cheby_codegen_clif`, whose single lowering serves the JIT, AOT and constant evaluation (architecture §2.6), on `cheby_runtime` for the image's layout and the runtime ID, and on `cranelift-object`, `cranelift-frontend`, `object` and `gimli` at the workspace's versions (D-1036). `cheby_driver` (`cheby build`) and `xtask` (`check-native-libs`) depend on it. Its Cranelift crates have their default features only: an architecture feature here would reach `cheby` through `cheby_driver`, and M3 builds for the host only (D-936).

## What it holds

- `object::replay(record, isa, name)`: one code record into one ELF (Linux targets) or Mach-O (macOS) object. Every symbol keeps its recorded name and linkage, local ones included: `Local` is a local symbol, `Hidden` a global hidden one (ELF `STV_HIDDEN`, Mach-O private extern, D-917), `Import` an undefined one. Functions are defined with `define_function_bytes` and data with `define_data`, in record order, so the bytes depend only on the record, the ISA and `name`, the module path (D-264). Unwind info is off (D-913, D-733). Replay checks the record first, and refuses a relocation of another architecture or a format other than ELF and Mach-O (COFF is M6's, D-935), so it never panics on a record. A record with source positions (D-938) also gets, from `dwarf.rs` through `gimli::write`, DWARF 4 line tables: `.debug_line` (one file, the record's diagnostic path split into a relative directory and a name, one sequence per function with rows), a minimal `.debug_info` (one compile unit named by the diagnostic path, with producer, language, line program and code ranges, and one subprogram per function; no `DW_AT_comp_dir`), `.debug_abbrev`, `.debug_str` and `.debug_ranges`, with relocations against the functions' code (and, in ELF, against the sections for their offsets); Mach-O puts them in the `__DWARF` segment, which macOS executables drop with `-Wl,-S` until M6 (D-1112). A record without positions (`CHEBY_POSITIONS=off`) and the program object get none.
- `program::program_object(isa, spec, entries)`: the one object of a link that belongs to the program, never cached (D-964): the entries unit's record replayed with every definition local (D-1111), `cb$image` in the layout of `cheby_runtime::image`, the C `main` that returns `cheby_rt_main(argc, argv, &cb$image)` and is the only exported symbol (D-917, D-925), and an import of the runtime ID's symbol `cheby_rt_id$<hex>` (D-930). Text holds only PC-relative relocations (D-913).
- `gc`: linker GC of record entries (D-1253, D-1288). Replay moves each function's 40-byte entry and its call sites out of the module record, into an `SHF_LINK_ORDER` section `cbf_<key>` tied to the function's own section on ELF, or a live-support atom in the shared `__DATA,cb_fns` section, tagged with its record, on Mach-O, so the linker drops them with the function. The program object passes each record's bounds through `ProgramImage`'s `functions` table, and the runtime registers the entries within them. `gc::key`, `gc::tag` and `gc::bounds` name the sections, tags and bounds symbols.
- `archive::find_archive` and `archive::check_runtime_id`: `libcheby_rt_exe.a` next to the running `cheby`, or where `CHEBY_RT_ARCHIVE` says, and its symbol index must define this compiler's runtime ID. A missing or stale archive is a tool error that names `cargo build -p cheby_rt_exe` (D-929, D-930): `cheby build` needs the archive, and `cargo test` does not build it.
- `link::link(job)`: `cc` from `PATH` with `CC`, `LD`, `CFLAGS`, `LDFLAGS` and `MACOSX_DEPLOYMENT_TARGET` removed, fixed flags per platform, `-Wl,-z,start-stop-gc` among Linux's (D-1253, D-1288), the module objects in build order, then the program object, the package's C objects (`LinkJob::c_objects`, D-940), the archive, the package's `libraries` as `-l<name>`, and the archive's system libraries; the output is written under its final basename in a private directory inside the output directory and renamed into place (D-933, D-934, D-1112). The objects' directory `<tmp>/cheby-objects-<pid>-<n>` and the staging directory `<output dir>/.cheby-link-<pid>-<n>` are removed on every path that returns or unwinds; a signal that takes its default action leaves them, so before creating either one the link deletes that pattern's directories that the effective user owns and whose process is dead (`kill(pid, 0)` fails with `ESRCH`), ignoring every failure and never following a symbolic link; Windows sweeps nothing until M6 (D-1112, on D-1127's model). `link::check_copies` is D-918's check that local copies of one name agree, which debug toolchains run before linking.
- `cc`: a package's C source compiled once with D-942's fixed flags (`cc -c -O2 -fPIC -g0`, both `-ffile-prefix-map`s, `-I` the header directory, `SOURCE_DATE_EPOCH=0`), returning the object and every file the compile read in D-942's three forms; `cc::HEADER` is `cheby.h` (`include/cheby.h`, D-945), which holds only its include guard and `cheby_value`'s typedef until N8b. The driver caches the objects.
- `shlib`: a package's shared library for the commands that run code in the `cheby` process (D-941): the forwarder (`cheby_ffi_table`, no entries until N8b), the C objects and the `libraries`, linked with `cc -shared -Wl,-z,defs` or `cc -dynamiclib`; `defined_symbols` reads the names a C object defines, for D-944's check.
- `native_libs`: the archive's system libraries per target, each with the file the loader opens for it, and the macOS minimum version (D-1113); `undefined` is the last step of E0053's build resolver (D-943). `cargo xtask check-native-libs` checks the list against `rustc --print native-static-libs`.
- `LinkError`: a malformed record, an object `cranelift-object` refuses, or one of `cheby build`'s tool errors (D-1114).

The records themselves (`cheby_codegen_clif::record`: `RecordingModule`, `CodeRecord` and its encoding, `record_unit` with the module record `cb$mod$<path>`, D-919) live in `cheby_codegen_clif`, since the JIT loads them too (D-914).

## Status

M3, wave 3: `cheby build` links executables on macOS arm64 and Linux (D-935), from in-memory records; the cache stores records with K4c, and `cheby build` reads them with N9. Tests: `link_replay_*` (replay; Mach-O on aarch64 hosts only, D-892) and `link_program_*` (the program object read back with `object`, and a link against a stub archive without the runtime ID that fails). Wave 4b: `link_sweep_*` (the sweep of a dead process's link directories, D-1112, Unix only). Wave 5: `dwarf_*` (the line tables of ELF and Mach-O objects read back with `gimli`, D-938). Wave 6: `native_cc_*` and `native_shlib_*` (C compiles, two paths giving one object, shared libraries; they run `cc`). Wave 10: `cheby build` replays `cheby run`'s cached records (D-1285), and `link_gc_*` (the split of a record's entries, their ties to their functions, one section key per record and Linux's `-z start-stop-gc`, D-1288). See [`docs/plan/m3-aot-and-cache.md`](../../docs/plan/m3-aot-and-cache.md).
