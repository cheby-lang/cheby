# cheby_lsp

The language server behind `cheby lsp` (spec §13.11). It speaks LSP 3.17 over stdio through `lsp-server` and `lsp-types` (D-1351), and publishes the diagnostics `cheby check` reports for each package (D-1348). It also answers the requests that need only a document's text, such as outline and formatting, the requests that read names: hover, navigation, references, call hierarchy, document links, workspace symbols and semantic tokens, and the editing requests: completion, signature help and inlay hints. It evaluates a package's constants in a child process, so hover shows their values and the back-end diagnostics of `cheby check` are published too (D-1349).

Each run checks the package from its text, open documents and disk together, with no cache and no incremental reparsing: the server re-runs the whole front end after every edit (D-1361, D-1363). It neither reads nor writes the build cache.

## Place in the pipeline

`cheby_lsp` runs and reads `cheby_driver::analysis` (D-1350), and reaches no phase crate directly. It also names `cheby_syntax` and `cheby_fmt` in its `Cargo.toml` for the features of later waves. Only `cheby_cli` depends on it. Editor highlighting does not go through this crate: it comes from the sibling `tree-sitter-cheby` grammar, which `cargo xtask cross-check` keeps in step with the compiler parser (D-272).

## What the server does

- **Handshake and shutdown** are the server's own, not `lsp-server`'s helpers (D-1377). Before `initialize` a request is answered `ServerNotInitialized`. After `shutdown` every request is answered `InvalidRequest`. `exit`, or the end of input, ends the server with status 0 after `shutdown` and 1 before it. A frame whose body is not a JSON-RPC message ends it too, with status 1 and one line on stderr, since `lsp-server`'s reader stops there (D-1430).
- **Capabilities:** `positionEncoding`, `textDocumentSync`, the requests below, and workspace folders with change notifications. Completion triggers on `.`, `:`, `@` and `>` and resolves items, signature help triggers on `(` and `,`, and inlay hints have no resolve (D-1379). The server advertises a part of D-1379's surface only once it serves it, and a test checks that the advertised requests are exactly the routed ones. The encoding is UTF-8 if the client offers it, else UTF-32, else UTF-16 (D-1368).
- **Documents:** incremental sync. A document routes by its own path, never by `rootUri` or the workspace folders (A §6.4): a file under the materialized std directory is std's, and any other belongs to the package of its nearest `cheby.toml` when it is a module of that package or its manifest (D-1375). Each package root gets one `Session`. A workspace folder that is a package root starts its session at `initialized`. Any other session ends 120 s after its last document closes, and any session ends at once when its `cheby.toml` goes. Its files then get an empty publish, and the analysis thread drops its `Session`. Versions may restart at 0 on reopen, as Zed's do, since a text is named by its edit stamp, not its version (D-1445).
- **Single-file mode** (D-1371, A §6.4): a `.cheby` document with no `cheby.toml` above it, or inside a package without being one of its modules, gets a session of its own, keyed by its path. The driver checks it as the only module of a package with a synthetic manifest, as the REPL checks its entries, and never evaluates its constants. A file outside every package gets all of the run's diagnostics but W0005. A file inside a package gets its phase-A diagnostics only, since its imports of the package's modules cannot resolve. Its jobs and requests go as a package's do, and it is published as an open document of a package is. It ends when the document closes, with one empty publish. When a `cheby.toml` appears above it, the routing at the next open, close, save or watched manifest moves it into that package. Zed's window for a file outside its worktree, rooted at the file's directory with no workspace folders, is this case. Any other file that no package takes, such as a `cheby.toml` whose package is gone, gets no session and is never published.
- **Std documents** are never published, and formatting one answers `null` (A §6.3). Every other request on an opened std document reads the std base's snapshot, so hover and navigation work inside std (R-17). Once the document is edited, those requests answer their fallback.
- **Std** (A §6.2, §7): the std base checks every shipped std module once per process, with its plain index. `cheby lsp` starts it on the `cheby-std` thread as it starts, and a request that needs it before it is ready waits for it, so an answer never depends on timing. Std's sources are written read only on first need, under `<cache root>/lsp/std-src/<build id>`, so a location in std is a plain file (D-1369). A failure of either is logged once, and requests then answer without std.
- **Disk changes:** a client that registers watchers dynamically gets one for `**/*.cheby` and `**/cheby.toml` at `initialized`, and a package outside every folder gets relative patterns of its own (A §8). A package with no watcher is swept every 2 s by the `cheby-sweep` thread, which only stats files. An open, close or save sweeps as well (D-1374). A new or deleted `cheby.toml` routes the open documents again, and so does every open, close and save, for a client with no watcher.
- **Runs:** an edit starts a debounce, `analysis.debounceMs`. One thread, `cheby-analysis`, with a 256 MiB stack, runs every package's jobs, one at a time (D-601). A job is the Q run on live text, then the D run when the Q run plans one and no newer edit supersedes it (D-1347). A panic in a run ends that run only (D-1362). A panic while the session forgets changed files drops the session, and the next job starts a fresh one (D-1431).
- **Requests** go by class (A §3.3, D-1367). A `Text` request reads the document's live text and its own parse, so it never waits. A `Doc` or `Package` request waits for a snapshot of the exact text it names, by edit stamp (D-1445), answers `ContentModified` when the text moved on first, and `RequestFailed` after `analysis.requestWaitMs`. It waits for edits only, never for the job of a save, a settings change, a sweep or a watched file (D-1443). A `Workspace` request, `workspace/symbol`, reads the newest snapshot of every package as it is, and waits for none. Handlers run on the `cheby-query-N` threads, `clamp(cores / 2, 2, 4)` of them. A panicking handler is answered `InternalError`, and its thread goes on (A §3.7). `$/cancelRequest` answers a waiting request `RequestCancelled` at once and stops a running one at its next check.
- **Text requests:** `documentSymbol`, hierarchical or flat, `foldingRange`, `selectionRange`, `formatting` and `rangeFormatting`. Formatting runs `cheby fmt`'s formatter and answers its line diff, in LF, so a CRLF file is converted as `cheby fmt` converts it. Range formatting keeps the hunks that touch the range (D-1399). It compares lines with a CR before the LF ignored, so a CRLF file's hunks stay local, and writes a kept hunk with CRLF where the lines it replaces have it (D-1444). A kept hunk is taken whole, so it can reach a neighbouring line, such as the blank lines above a reformatted function. A file with a grammar error formats to `null`.
- **Name requests** read the occurrence index (F §5), built once per snapshot, one module at a time on first need. Each covers clean text, a type error and a grammar error.
  - `hover` (`Doc`): locals with their type at the use, items with an instantiated form for generic calls, fields, type parameters, `Self`, modules, the function behind an operator or `{x}`, holes, literals and a typed `todo`. Docs of std items come from the std index (D-1385). Markdown, or plain text for a client that takes no Markdown. A code block is fenced by more backticks than it holds, and a client that takes no Markdown gets a long stale value's block with no fence (D-1523). A package constant shows the value of the last evaluation in its header, or in its own code block below the header when the two would pass 80 columns, broken by its brackets as `cheby fmt` breaks a literal (D-1512). Numbers show as the runtime prints them, with no `_` groups, and a long value that is not current shows its block, then "when last saved." on the next line (D-1523). A value is current only while every module file its initializer reaches, as the child reports them, has the text the run read; otherwise it shows as "when last saved" (D-1510). A failed one names its code, and its note is in the published diagnostic, not in hover (D-1522). One not evaluated yet says that values come on save. While a run is due, waiting to start, or running, a constant with no value says that the constants are being evaluated, and a value that is not current shows "when last evaluated; the new save is being evaluated." (D-1511). A run that waits for unsaved buffers that do not check is not due (D-1523). One with no value after a run that failed or was cut short says so and points to `cheby/status` (D-1490). One with no value after a run skipped because the saved files have front-end errors says that the saved files have errors and values are computed on save (D-1497), and so does one after a save that left such errors on disk, so that the server started no run (D-1501). While that is so, every constant with a value shows it "when last saved", also one whose file has not changed, as after a run the child skipped (D-1503), and `cheby/status` reports `stale` then too (D-1505). Only a save or watched change sets that mark, so a session opened over saved files with errors says "not yet" until a save. The mark stays while a file it recorded as broken still has that text on disk, also when the file is open with unsaved edits, and clears when a run starts over saved files that check, when a run ends, or when a save with no run waiting brings back the last run's text. A save that fixes the files clears it only when its run starts (D-1504). A std constant shows its written initializer, and so does a dependency's, read again from its text through `Snapshot::const_initializer`, cut at 4,096 characters with `…` as a value is, as written, with no block (D-1496, D-1523). Where constants are never evaluated, in single-file mode, on Windows or with `constants.evaluate` off, hover shows no value line (D-1413, D-1414, D-1491).
  - `definition`, `typeDefinition` and `references` (`Package`), `declaration` and `documentHighlight` (`Doc`, plan §1.10). Go to works on `+` and on the braces of `{x}`. Links are sent where the client supports them. A reference list that may miss names says so in the log (F §5.5).
  - Call hierarchy (`Package`): `prepareCallHierarchy`, `incomingCalls` and `outgoingCalls`. A use as a value, through an alias, or by an operator counts as a call. An item's `data` names the document it was first prepared in, and `incomingCalls` and `outgoingCalls` are routed to that document's package, so the callers of a std function come from the package that asked.
  - `documentLink` (`Doc`): each import's module path links to its file, in the package or in std.
  - `workspace/symbol` (`Workspace`): every package's items, then std's for a query of two characters or more, at most 200.
  - `semanticTokens/full` and `/range` (`Doc`), no `delta` (D-1396): identifier tokens only, so tree-sitter stays the highlighter. `semanticTokens.enabled: false` turns them off, and both then answer `null`.
- **Editing requests** read the snapshot of the document's exact text, so they work on clean text, a type error and a grammar error.
  - `completion` (`Doc`, X §4.1 to §4.6): the context comes from the tree at the cursor. It offers locals, items, keywords and snippets, fields and functions after `xs.`, functions after `|>`, names after `::`, the items of the modules the file imports, written through the import's binding with no import edit and ranked above the items of modules the file does not import, at rank 30 with no type-driven rank, from a module of any package (D-1507, D-1521), and items of modules not yet imported. A name imported both by name and through its module is offered both ways (D-1521). An item written through a module path has the qualified name as its label, `list::map`, and the bare name as `filterText` (D-1508). A function offered after `xs.` keeps its bare label, since its text is the pipe form (D-1521). Text on several lines, such as the postfix `case` or a snippet, is written relative to its first line and carries `insertTextMode: 2` when the client lists `adjustIndentation`, never `asIs` (D-1506). Accepting a function after `xs.` replaces only `.partial` with the pipe form, ` |> list::map(_, f)`, so the edit stays on one line (D-1394). A new import gets an alias when its name is taken in the file (D-1395). A function is offered after `xs.` or `|>` only when the bounds of the type parameters it binds hold, so no item makes E0063. What follows the word is not written again: no argument list before `(` or `::`, no `::` after a module or an interface name before `::`, no `: ` before `:`, no fields before a constructor's own. Before a path's `::`, only what a path starts with is offered, as the file binds it: in an expression and after `|>`, the modules and the interfaces, bare or through an imported module, as `Compare` and `shape::Shape` (D-173), the interfaces only when one segment follows the `::`, as in `Comp‸::compare(a, b)` and not `sha‸::Shape::area(x)` (D-1539), a turbofish after that segment counting as one more, as in `sha‸::Square::<Int>(1.0)` (D-1544); in a type or a pattern, the modules; after `xs.`, nothing (D-1530). After `module::` in an expression or after `|>`, the module's interfaces come too, written `Shape::`, so the list of their functions opens next (D-1548), and they alone, written `Shape`, where a path's `::` follows, as in `shape::Sh‸::area(s)` (D-1538). In a type or a pattern, a later segment followed by `::` offers nothing (D-1547). After `|>`, `I::` and `m::I::` offer the interface's functions in the pipe form, the hole `_` at the first parameter of type `Self`, bare when that is the only one, as `xs |> shape::Shape::area` (D-1545). Where a function value is expected, as in `list::map(xs, Show::‸)`, an interface's function is written bare, `show`, as a module's function is (X §4.1, D-500). In an expression and after `|>`, where no `::` follows the word, the interfaces are offered too, written with the path's `::` as a module is written `shape::`: those in scope bare, as `Show::`, those of imported modules through the module for a partial of two characters, as `ops::Compare::`, and with `completion.autoImport` on those of modules the file does not import, with their import edit. Each ranks as the other items of its source. An interface imported both by name and through its module is offered both ways in an expression (D-1546), and after `|>` only by that name, `Compare::`: not again with an import edit, which would leave that import unused, and not through its imported module either, as a function imported by name comes once there (D-1550). So `Show::show(x)`, `ops::Compare::compare(a, b)` and `shape::Shape::area(x)` complete one segment at a time, in an expression and after `|>`. So accepting an item at `st‸::length` never writes `string::starts_with::length` (D-1521, D-1525). Only a `::` right after the word counts. A turbofish's `::` does not: before `::<`, as in `re‸::<Int>(xs)`, only names that take type arguments are offered, as with no `::`: functions and constructors, bare or through a module path, and locals. No keyword, snippet, constant, module name or interface function is offered there, since `list::<Int>` is no path (D-1525, D-1536). After `xs.` nothing is offered there (D-1537). A type keeps its names there with no `dyn`, and a pattern its constructors with no `_` (D-1544). The `<` is found as the parser finds it, past white space, comments and line breaks inside `(`, `[` or a type `<` (D-1529). After `let`, `let guard` and `let assert` the pattern's subject is the value after `=`, also with a type annotation (D-1531). An item's `data` names its symbol and document. `completion.autoImport` and `completion.typeDriven` turn those parts off. With `completion.autoImport` off, no item carries an import edit, after `xs.` and `|>` included: an item that would need one is left out (D-1486). The items of imported modules are offered whatever it says. With it on, in an expression, a type or after `|>`, and with it off when the file imports a module, in an expression or a type, or after `|>` when an imported module has an interface, a partial word shorter than two characters gives `isIncomplete: true`, since imports and the items of imported modules start at the second character (D-1487, D-1507, D-1521, D-1546). Before a path's `::`, the list is always complete, since nothing to import is offered there (D-1525, D-1530). Before `::<`, the mark is as with no `::`.
  - `completionItem/resolve` (`Workspace`): adds the item's docs, by the hover's path, and nothing else. The item names no document, so it reads the newest snapshot of the package its `data` names.
  - `signatureHelp` (`Doc`, X §4.7): the innermost argument list at the cursor, with the active parameter counted by its commas, so a pipe's `_` and a capture count. It labels functions, positional constructors, interface functions and function values. Parameter labels are offsets when the client takes them.
  - `inlayHint` (`Doc`, X §7.1): types after `let` names and pattern binders, `use` binders, closure and local function parameters and results, the stages of a multi-line pipeline, and implicit `dyn`. With `inlayHints.parameterNames` on, off by default, the name of the parameter each literal argument fills, a number, string or unit constructor, of a call to a top-level function, as a hint of kind `Parameter` (D-1515). A local function's call gets none, an interpolated string counts as a string, and a parameter named `_x` shows `_x: `. Where a comma is missing, the names stop at the second argument that shares a position, and the names before it stay (D-1524). Only hints in the request's range are sent. A plain `let` name's hint carries a text edit when the type can be written with no new import. Only a `let` bound to a record literal of a non-generic type skips its hint (D-1483). `inlayHints.enable` turns them off, and one key per row turns its row off: `letTypes` (a `let` of one name), `patternBinders`, `useBinders`, `closureTypes`, `localFnTypes`, `pipeStages`, `dyn` and `parameterNames` (D-1376, D-1480), and a change to them sends `workspace/inlayHint/refresh` to a client that takes it (A §12.3).
- **Constants** are evaluated by a child process, `cheby __backend --want constants`, started from the server's own executable, never in the server (D-1349, D-1410). It runs at the session's first clean report and after a save or watched change that changes the package's normalized text on disk, 300 ms later so that save-all gives one run, and only while the package's report is clean. A save of unchanged text, such as an editor's echo of its own save, leaves a running child and a due run as they are (D-1494). A package with no constant of its own starts none (A §11.4). It reads the saved files, so an unsaved buffer stops nothing, and a run waits for a clean report only while unsaved buffers alone keep it unclean. One runs at a time in the process, with half the cores, and with `--target` when `analysis.target` is set, so its E0078 follows the target as `cheby check --target` does (D-1489). A save that changes that text kills it. So do `constants.childTimeoutSeconds` (60 s), 64 MiB of output, the session's end and `shutdown`, and the child exits by itself when its stdin closes (D-1411). A run cut short is logged, and shown once per session with `window/showMessage`. It is not run again for the same text on disk, the text it read, so saving unchanged text does not loop and an unsaved edit neither blocks nor lifts it, until a settings change raises the time limit above the one that cut it short. Lowering the limit runs nothing (D-1493). A change of `constants.evaluate` applies at once, and a change of `analysis.target` makes a run due at once, as the first clean report does, killing a child that checks for the old target (D-1498), also after a run cut short over text that has not changed since (D-1500). The text a save is compared with is that of the last run that finished, failed or was cut short: a run killed by a save, a target change or the session's end does not count (D-1502). Every settings change owes each package a `cheby/idle`. A child diagnostic is published while its file's normalized text, with no BOM and `\r\n` read as `\n`, hashes as the text the child read, so an edit hides only that file's (D-1412). A failed evaluation keeps the old values, marked stale, and marks each failing constant (D-1413). Values are cut at 4,096 characters. Each value comes with the package's module files its initializer reaches, its own included. A value with no such list counts every module of the package, and `cheby/status` reports `stale` when any value reads stale against the newest snapshot (D-1510). A run shows as `$/progress` for a client with `window.workDoneProgress` (D-1415). Windows evaluates no constant until M6 (D-1414).
- **Custom protocol** (D-1378, D-1415): `cheby/status`, a request for debugging, lists each package's kind, generation, broken files, run state, parked requests and constants child, with its last outcome and why constants are not evaluated. A client with `experimental.chebyIdle` gets `cheby/idle`, `{ root, generation }`, once nothing is running or due for a package, its analysis job, parked requests and child included: `root` is the package root, or a single-file session's file, as a `file:` URI, and `generation` the root's generation (D-1492). The generation is the server's count of the root's snapshots, kept when a change of `analysis.target` rebuilds the session, so it never goes back (D-1495). It lasts for the server's life, also across a session that ends and a later one of the same root, so 0 means only that the root has had no snapshot since the server started (D-1499). It comes after every job, also a save's that starts nothing, with no sleep. The harness waits on it.
- **Publishing** follows D-1373 and D-1442. Every file of a package and `cheby.toml` are published, open or closed. A publish is skipped when the path's last one had the same version and the same list, so a save, a settings change or a sweep that changes nothing sends nothing. `didOpen` and `didClose` forget the path's last publish, so an opened document still gets a publish with its version, even an empty one. A file that leaves the package gets one empty publish. Only the nearest package publishes a nested package's files. A request waits only for the text it names (D-1367, D-1443), so it is no barrier for a run that a save, a settings change or a sweep starts: a test that needs one sends an edit and waits for that version's publish, since a package's jobs run in order. A client waits for those with `cheby/idle` (D-1415), the barrier D-1443 names. A file's list is the front end's, then the constants child's, as `cheby check` orders them. An empty range is widened to the character before it, so editors can show it. A diagnostic's `message` is `cheby check`'s text without its snippet (D-1509): the header, then one line each for the primary label when it is not empty, the related labels as `path:line:column: label` when the client takes no `relatedInformation`, each note as `note: …` and each help as `help: …`, a later line of a note or help indented under its text, as `cheby check` prints it (D-1522). Control characters in notes and helps are sent raw, and a related line's path uses the platform's separator (D-1522). `relatedInformation` is sent only to a client that supports it, and parity compares only the first line.
- **Settings** come from `initializationOptions`, then `workspace/configuration` with the section `cheby`, then `didChangeConfiguration`'s `settings.cheby` (D-1376). A later layer wins per key. A value of the wrong type is skipped with a warning, and the key keeps what the earlier layers gave it (D-1514). An unknown key is skipped with a warning too, and `null` means no opinion. A push that carries `settings.cheby` is used as it is. Only a push without that key makes the server ask with `workspace/configuration`, since Zed pushes to every server even when nothing changed.
- **Standard output** carries protocol frames only. The crate denies `clippy::print_stdout`.

## Handle confinement

The driver's generation handles, such as `Ty` and `DefId`, are valid for one run only, and a stale one gives a silent wrong answer (D-1366). `clippy.toml` in this crate bans their types everywhere, and the `features` module is the one place that may name them, under a single `#[expect]` in `lib.rs`. The lint sees written type names only, so a value held through inference is review's job. The driver's types have no `Serialize`, so a handle cannot become JSON either, which a `compile_fail` doctest in `lib.rs` shows. A crate-local `clippy.toml` replaces the root one, so it repeats the root's four settings.

`ServerOptions.child` is the `cheby` executable for child jobs, `Some(current_exe())` from `cheby lsp` and `None` in tests in process, so a test binary never runs as the child. A release build never reads it (S-24).

## Tests

- `cargo test -p cheby_lsp` runs the tests in process, through `run_on`: capabilities, settings, publishing and the message text (`publish_tests.rs`) and shutdown, requests and their waits (`request_tests.rs`), routing, sessions and watchers (`session_tests.rs`), single-file mode (`single_file_tests.rs`), and children (`child_tests.rs`: when runs start, kills, the time limit, the output cap and results, with a script standing in for `cheby` on Unix). `child/` has round trips of the wire format on every platform. The handlers have unit tests on clean text, a type error and a grammar error, and every example formats to no edit. Completion has a test for each broken form of X §4.1. `index_covers_every_identifier` checks that the index places or explains every identifier of every example and of std. The text module has property tests with fixed seeds: offsets to positions and back against a reference model, edits applied through positions, and paths through URIs and back.
