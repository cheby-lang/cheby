# cheby_driver

The build driver: it runs the compiler's phases over a package (spec §13.12). It is the only crate that depends on every compiler crate, and every tool builds on it rather than on the phases directly. `check`, `prepare_run` and `prepare_test` are what `cheby check`, `cheby run` and `cheby test` call, `session` is the driver side of the REPL, `analysis` is what the language server runs and reads, and `dump_mir`, `dump_clif` and `bench_build` serve the goldens, the determinism checks and `cargo xtask bench-compile`.

## Place in the pipeline

`cheby_driver` depends on `cheby_diag`, `cheby_syntax`, `cheby_package`, `cheby_resolve`, `cheby_iface`, `cheby_types`, `cheby_mir`, `cheby_codegen_clif`, `cheby_jit`, `cheby_runtime`, `cheby_consteval`, and on the M3 and M4 skeletons `cheby_link` and `cheby_js`. `cheby_cli`, `cheby_repl`, `cheby_lsp` and `cheby_doc` depend on it, as do `xtask`, `bench/gen` and the fuzz targets.

A build runs these steps, each in the crate named:

1. **Phase A:** `cheby_package` reads `cheby.toml` and discovers the modules, and `cheby_syntax` lexes, parses and validates every file. An error here stops the later phases (D-452).
2. **Front end:** `cheby_resolve` builds the import graph and resolves names, `cheby_types` builds interfaces in import order and checks bodies, independent modules in parallel on rayon's global pool (D-263), then the module-local and whole-package warnings run.
3. **Back end**, for `run` and `test`: `cheby_mir` lowers the items reachable from `main` or the tests across modules (D-510), the RC passes run over all units, `cheby_codegen_clif` and `cheby_jit` compile one batch, and `cheby_consteval` evaluates the constants the code reaches in a JIT of their own on `plain` code (D-978), writes each result as an image and installs the images into the program's JIT before anything runs (D-979); `cheby build` puts the images into the program object instead. Unresolved native symbols (E0053) and constant errors are reported like compile errors before anything runs.
4. **Running:** `main`, each test or each REPL entry runs as a root fiber of one `cheby_runtime::Runtime` per host run (D-690), with the exit statuses of §10.10 and the leak check of debug builds.

Every phase that reads other modules' interfaces, outside std, reads them through a recording view (D-955): `Checked::front_reads` holds what resolution and checking read beyond a module's imports, and the back end's `Lowered::reads` what lowering and borrow inference read beyond those, per code unit and tests unit. Debug toolchains decode every interface they build and compare it with the original (D-954).

`cheby check`, `cheby run`, `cheby test` and `cheby build` go through the build cache (`Cache`, D-955 to D-965). Each command first reads its package index (D-962), one hint per package root and command family that holds every module's keys and front record inline. Each package module is looked up by its front key and its recorded reads, through the index first; a miss is checked from source and its front record written, with its reference and use summaries (D-965, D-967), unless it has an error (D-964). In `cheby check` a hit is neither parsed nor checked: its interface hash comes from its record, its interface is decoded only when a checked module needs it (D-954), and its diagnostics, externals and use summary are replayed; W0005 runs over every module's use summary. The modules constant evaluation needs, those holding constants and what they import, are checked from source on fresh interfaces. A warm `cheby run` or `cheby test` checks only the modules whose code or tests records miss, whose warm facts are missing, or that constant evaluation needs, and reads the others' interfaces, diagnostics, warm facts and records from the cache; a build that then needs a hit's body starts again with every module checked (`warm_keys.rs`, D-1250, D-1256). A warm `cheby build` does the same over its own family's index, lowers through `cheby run`'s code records and takes its constants from their entries (`aot.rs`, D-1285, D-1286). No module is checked twice, except on an error path (D-1136) or when a warm command starts again (D-1256). The output never depends on the cache (D-268).

Output is deterministic whatever the number of threads (D-264): results are merged in a fixed order, the first error in build order is reported, and diagnostics are sorted by `SourceMap::sort`. `configure_jobs` sizes the pool for `-j`.

`analysis` runs the front end for the language server (D-1361 to D-1365, [architecture.md](../../docs/plan/architecture.md) §4.2). A `Session` loads a package from an `Overlay` of unsaved texts and its cached disk reads, and each `analyze_live` call is one tolerant run, `run_analysis` with `Retain::LIVE`: no cache, no phase-A gate, every import of one edge cut per import cycle, and an internal error contained to one body, pass or module. It gives a `Live`: an `Arc<Snapshot>` that holds the local trees, `ResolvedModule`s, facts and THIR and every interface, and plain `FileReport`s of `PlainDiagnostic`s. `Symbol` is the only identity that crosses snapshots. The module re-exports the phase crates' data types and pure helpers, never a phase function, so `cheby_lsp` needs no edge to them (D-1350). Batch commands pass `RunExtras::batch()`, so their behaviour does not change.

The session runs the two-track algorithm (D-1347, D-1356 to D-1360). When the manifest is clean, no file has a phase-A error, no import was cut and nothing was lost, the Q run is the check and `Live::report` holds every file's diagnostics as `cheby check` gives them. Otherwise `Live::phase_a` holds each broken file's phase-A diagnostics and `cheby.toml`'s, taken before the Q run, and `Live::plan` asks for a D run when the strict inputs changed or a file left the broken set. `Live::broken` names the broken files of every run, since a file that turns broken plans no D run when its last good text is the text just run, so the latest `Report::clean` alone does not say the package checks. `analyze_strict` runs it: `run_analysis` with `Retain::BUILD` and no cycle cut, over each clean file's live text, each broken file's last good text, or an empty stub. Its `Report` leaves out broken files, holds the files that import a stub (an empty list for one that just left the broken set), drops W0005 when a stub entered the run, and sets `substituted` when it read a last good text or a stub. A manifest that gives no manifest is replaced by the last good one, which `AnalysisStatus::manifest_is_last_good` records; with none, only the open files are parsed.

`StdBase::build` checks every shipped std module once per process with `Retain::STD`, keeping trees and facts, and fails on any error or loss (D-1370, D-1372). Its `StdIndex` is plain data that crosses generations: each pub item visible from another package, by `Symbol`, with docs, field docs, signatures and constant initializers. `Snapshot::head_of` gives a type's `TypeHead`, which is how a package snapshot's types meet the index, and `materialize_std` writes std's sources read only under the cache root, so a location in std is a plain file (D-1369).

`verify` checks an edit plan of rename, `willRenameFiles` or a refactor against a snapshot, statelessly on the caller's thread (D-1389, D-1393). It refuses any closed file that changed on disk, touched or not, and a move onto a file that appeared (`Stale`), gives `Blocked` when "before" cannot be trusted (a cut import, E0040, a loss) or an edit touches a file that is not UTF-8, then runs the edited texts with `Retain::VERIFY` on the snapshot's `Globals` and targets, and compares errors and W0007 with `Snapshot::baseline` as a counted multiset, reading a renamed name as its new one, or as it was for a binding the rename leaves alone. Constants are not evaluated, so a new E0075 or E0077 passes.

The standard library's sources in `std/` are embedded in the binary by `std_lib.rs` (D-450). `cheby check`, `cheby run`, `cheby test` and `cheby build`, with a cache that reads, take std's front and code records from the cache, and the REPL loads std's code records (`std_cache.rs`, D-980, D-1262, D-1264, D-1285). The first command that misses them, std's first use, checks and compiles every std module and stores them all (D-1266, D-1267). A front end that reads no std front record, as without a cache, in the REPL or after a warm command starts again (D-1256), parses and checks only the std modules its imports reach and the shipped home modules (D-447, D-450). Std's masks are inferred once per process over all of std (D-968, D-1264), and `test_std` runs std's own `test` blocks for `cargo xtask test-std` (D-479, D-599). A std module listed in `STAGED_STD_MODULES` is embedded but not loadable until it moves to `STD_MODULES` (D-486).

## Tests

`tests/golden/` holds the MIR and CLIF dumps of `001_hello_world` and of the packages under `tests/packages/`, which `cargo xtask check-determinism` compares across thread counts and paths. Many tests of the compiler crates build whole packages through this crate, so a change to its public functions is visible across the workspace.
